Abstract—Log parsing, as a process of extracting structured
information from semi-structured raw log data, is a crucial
step in log analysis workﬂows. Rule-based parsing methods
often overlook the rich semantic information contained in logs.
Recently, LLM-based methods face three major challenges: 1)
limited understanding of domain-speciﬁc logs due to lack of
professional domain knowledge; 2) signiﬁcant parsing costs and
potential data privacy risks associated with commercial LLMs
like ChatGPT; and 3) the Group Accuracy (GA) is highly
susceptible to individual anomalous data. To address these chal-
lenges, we propose LogExpertSolver, a multi-agent framework
for domain-specialized log parsing. This framework effectively
reduces manual intervention in log parsing through inter-agent
collaboration mechanisms. LogExpertSolver employs locally de-
ployed medium-scale language models to construct multiple
agents with diverse domain expertise. By decomposing complex
log parsing tasks into a series of ﬁne-grained subtasks, which are
handled by corresponding expert agents, the framework achieves
efﬁcient log parsing. Through evaluation on the LogHub2.0
dataset, LogExpertSolver achieves an average Parsing Accuracy
(PA) of 0.915, surpassing state-of-the-art parsers (LibreLog and
LILAC) by 6.2% and 7.3% respectively.
Index Terms —Log Parsing, Large Language Model, Multi-
Agent
I. I NTRODUCTION
Logs provide crucial runtime information for software sys-
tem debugging, monitoring, and maintenance [1]. However,
with the continuous expansion of software system scales,
log data exhibits characteristics of massive volume and high
complexity, posing signiﬁcant challenges to manual log anal-
ysis methods [2]. To improve the efﬁciency of log analysis,
researchers have proposed numerous automated solutions for
various log-related tasks, including anomaly detection [3]–
[7], log compression [8]–[10], and root cause analysis [11],
[12]. Among these log analysis tasks, log parsing is typically
regarded as the foundational step of the entire pipeline.
Log parsing aims to extract structured information from
semi-structured raw log data, converting raw log messages into
standardized log templates [13]. Each log message is generated
by corresponding log statements in the source code. The
Headers are uniformly standardized by the logging framework
adopted by the project, typically containing metadata informa-
tion such as timestamps, log levels. The Content section of log
messages primarily consists of two core components: 1) static
text strings that describe system events without any variable
parameters; 2) dynamic parameters that change in real-time
during system operation, used to record speciﬁc contextual
information and state data.
Although some studies have previously proposed various log
parsers [13]–[16], efﬁcient and accurate log parsing still faces
many challenges [2]. Huo et al. [16] pointed out that traditional
methods are primarily based on syntactic rules, ignoring the
rich semantic information contained in log content. Such
syntax-based parsing methods typically have limitations in
parameter identiﬁcation [17], [18]. Addressing this issue, Ma
et al. [2] proposed: log messages are essentially a hybrid
of natural language descriptions and code-like variables, and
it can be viewed as a "translation" task from raw logs to
structured templates. Based on LLMs’ advantages in semantic
understanding, recent researchers have begun to focus on
semantic information mining in logs, achieving signiﬁcant
progress in semi-structured log data parsing [13].
However, different log data typically represent runtime
information from components in different domains, such as
components responsible for databases and network connec-
tions, which differ in semantics and formats, and their charac-
teristics may be signiﬁcantly different. Therefore, approaches
that heavily depend on predeﬁned rules may lack ﬂexibil-
ity, are constrained to speciﬁc systems, and fail to handle
complex and variable log formats [15]. When directly using
general-purpose LLMs for parsing, due to the lack of domain-
speciﬁc professional knowledge, they often cannot meet the
requirements for parsing accuracy and domain adaptability in
practical applications.
Furthermore, many current LLM-based log parsing solu-
tions rely on commercial large models such as ChatGPT
[19], [20], where such commercial API services typically
charge high fees. Considering the large-scale batch processing
characteristics of log parsing tasks, the contradiction between
massive log data and LLMs’ limited context windows leads
to signiﬁcant computational overhead, including time costs
and economic costs. Large-scale parameter computation not
only reduces the overall efﬁciency of log parsing but also
causes token consumption to grow linearly with the number of
logs, making parsing costs rise rapidly. Therefore, reasonable
control of LLM invocation costs is of great signiﬁcance for
practical deployment applications [14]. Efﬁcient log parsing
systems should be able to meet large-scale batch processing
requirements while maintaining low resource consumption.
Additionally, using commercial models poses potential data

Moreover, many log parsers adopt clustering-based template
extraction strategies [19], [21], using GA as an important
performance evaluation metric. However, recent research [2]

on the Spark dataset, although PA reached 0.9995, just one

To address the above challenges, this paper proposes LogEx-
pertSolver, a multi-agent log parsing framework that integrates
domain expert knowledge. The framework fully leverages
the inherent language understanding and logical reasoning
capabilities of large language models [22], achieving automa-
tion of the log parsing process and reducing the cost of
manual intervention. To balance parsing performance with re-
source consumption, LogExpertSolver uses locally deployable
medium-scale open-source large models (such as Qwen3-14B)
to construct the multi-agent framework. Compared to large-
scale commercial models, open-source models with moderate
parameter counts not only reduce parsing time overhead,
but local deployment also enhances data privacy protection
capabilities and reduces token consumption costs.
The main contributions of this paper are as follows:
• LogExpertSolver ﬁrst combines domain expert knowl-
edge with multi-agent collaboration mechanisms and
overcomes the limitations of existing syntax-based and
LLM-based log parsers.
• To reduce manual intervention, LogExpertSolver designs
task decomposition mechanisms, achieving full automa-
tion of the parsing process through multi-agent collabo-
rative processing.
• To reduce parsing costs while meeting large-scale batch
processing and low resource consumption requirements,
we adopts locally deployed medium-scale open-source
LLMs to replace expensive commercial LLMs.
• Comparative experiments were conducted on 14 differ-
ent datasets contained in LogHub2.0. LogExpertSolver
demonstrates 6.2% and 7.3% higher PA compared to
state-of-the-art parsers.
II. B ACKGROUND
A. Large Language Model
Large Language Models (LLMs), as prominent represen-
tatives of deep neural network technologies, are built upon
the Transformer architecture and demonstrate exceptional lan-
guage understanding and generation capabilities through pre-
training on large-scale, diverse text corpora.
With the continuous expansion of model scales and the
increasing diversity of training corpora, In-Context Learning
enables LLMs to achieve rapid task adaptation and effective
generalization based on limited demonstration samples [2].
In log parsing scenarios, this characteristic helps models
extract key information from diverse log formats, including
dynamic variable identiﬁcation, structured feature extraction,
and semantic pattern understanding.
B. Multi-agent Systems
Independent LLMs inherently possess the basic characteris-
tics of simple agents since they can receive text inputs and
generate corresponding text outputs, making the boundary
between LLMs and LLM-based agents relatively blurred [23].
Compared to single LLM-based agent systems, multi-agent
systems provide enhanced capabilities [24]: 1) specializing
general-purpose LLMs into specialized agents with different
capabilities, achieving functional division; 2) establishing ef-
fective interaction mechanisms among agents, enabling more
realistic simulation of collaborative patterns in complex real-
world environments. The dynamic mechanism combining col-
laboration and competition enables multi-agent systems to
possess stronger adaptability and problem-solving capabilities.
III. M ETHOD
A. Overview of LogExpertSolver
The LogExpertSolver method proposed in this paper con-
structs expert agents with specialized knowledge in different
log domains, enabling automatic extraction of domain classiﬁ-
cation lists from source code and identiﬁcation of the domain
afﬁliation for each log entry, thereby achieving high-quality
log parsing without the need for targeted model ﬁne-tuning.
As shown in Figure 1, the LogExpertSolver framework
consists of four phases: Domain Component Extraction Phase,
Domain Filtering and Optimization Phase, Log Domain Classi-
ﬁcation Phase, and Log Processing and Standardization Phase.
LogExpertSolver is executed by a speciﬁc group of special-
ized agents. In total, the framework deﬁnes six core agents:
(1) a Domain Extraction Expert, (2) a Domain Filtering and
Optimization Expert, (3) a Log Domain Classiﬁcation Expert,
(4) a Log Preprocessing Expert, and (56) two Log Standardiza-
tion Experts (text and numerical). These agents communicate
and coordinate through the CrewAI, which manages task
delegation, result passing, and workﬂow sequencing via JSON-
based message exchange. Each agent receives structured task
instructions, processes data independently, and outputs results
in standardized JSON format, enabling seamless inter-agent
communication.
In terms of technical implementation, LogExpertSolver
adopts Qwen3 as the foundational LLM. We selected the
relatively smaller instruction-tuned model Qwen3-14B as the
experimental foundation.
CrewAI Framework Integration. CrewAI is an open-
source multi-agent coordination framework that provides task
scheduling, role deﬁnition, and inter-agent communication. It
enables multiple specialized agents to collaborate efﬁciently
within a uniﬁed workﬂow. In LogExpertSolver, CrewAI acts
as the coordination backbone: the framework manages the
initialization of expert agents, assigns speciﬁc preprocessing
and standardization tasks, and synchronizes data exchange

B. Domain Component Extraction Phase
The ﬁrst core phase is the Domain Component Extraction
Phase, which comprises three key steps. First, LogExpert-
Solver traverses the candidate logs, extracting the System
Details. For acquiring metadata information of log projects,
the system provides two distinct input processing approaches.
Approach 1: Direct URL Input Processing. The approach
involves directly inputting the project URL to the LLM,
enabling it to autonomously read and analyze webpage content
to extract project information. Through real-time access and
analysis of external web resources, LLMs can obtain richer
and more up-to-date project information [25]. However, due to
the diversity, dynamicity, and structural complexity of website
content, as well as the strict limitations imposed by token con-
straints on LLM output capabilities [26], LLM cannot perform
complex webpage interactions and deep content parsing like
real browsers.
Approach 2: Markdown Format Conversion Processing.
The approach adopts a more LLM-friendly Markdown format
for information input. For projects that only have textual
descriptions without source code, LogExpertSolver uses the
Markdowner to extract webpage content from URLs and
convert it into structured Markdown format, thereby improving
LLM’s understanding.
For project logs with clearly available source code, Log-
ExpertSolver employs a more in-depth strategy: the system
ﬁrst downloads the complete Git repository of the project,
then uses the git2md to extract README ﬁle and directory
tree structure, integrating this information into a Markdown
ﬁle. As shown in Figure 2, this example demonstrates the
process of inputting a project Markdown ﬁle with clearly
available source code to agents for domain extraction. Taking
the Spark as an example, the generated Spark.md ﬁle contains
description information extracted from the GitHub homepage
in the ﬁrst half, while the second half includes hierarchical
directory structure extracted from the local Git repository.
Compared to the direct URL input approach, while the
Markdown ﬁle extraction method shows improvements in
information processing efﬁciency, it may result in the loss of
information. Particularly due to the limitations of LLM input
context length, the tree-like ﬁle structure shown in Figure 2
requires appropriate ﬁltering and compression processing to
ensure that key information can be effectively conveyed within
the limited context window.
Next, the system inputs the original URLs and Markdown
ﬁles containing project information into the Domain Extraction
Expert for processing. Considering that extracting domain lists
from source code is a critical and complex task requiring deep
code comprehension capabilities, unlike other expert modules
in the framework that use Qwen3, the Domain Extraction
Expert employs Claude-3.5-Sonnet as its foundational model.

C. Domain Filtering and Optimization Phase
LogExpertSolver inputs the two domain list options into the
Domain Component Filtering Expert. By designing prompts
that meet speciﬁc scenario requirements, this expert can com-
prehensively evaluate the applicability of the two candidate
lists, ultimately selecting Better Domain List to serve as the
standard classiﬁcation basis for subsequent log classiﬁcation
and processing tasks.
Taking the Zookeeper as an example, the system inputs
two candidate lists: the list extracted from URL "[’Server’,
’Client’, ’ZooKeeper Session’, ’Quorum’, ’Storage’]" and the
list extracted from Markdown ﬁles "[’Server’, ’Client’, ’Quo-
rum’, ’Persistence’, ’Watch’]". After analysis by the Domain
Component Filtering Expert, Claude-3.5-Sonnet ultimately
selected the domain list extracted from the Markdown ﬁle
"[’Server’, ’Client’, ’Quorum’, ’Persistence’, ’Watch’]" as the
basis.
D. Log Domain Classiﬁcation Phase
LogExpertSolver uses the Better Domain List as the clas-
siﬁcation standard, inputting it together with system log into
the Log Domain Classiﬁcation Expert, which executes the log
domain classiﬁcation task. Figure 3 demonstrates an example
of the expert performing log classiﬁcation.
To improve classiﬁcation processing efﬁciency, LogExpert-
Solver adopts a batch processing strategy, setting the batch
size to 5 logs. The system inputs every 5 logs as a batch
to the classiﬁcation expert, and the expert module returns
structured JSON format output after processing. The JSON
output contains 5 list items, with each list item corresponding
to one log record in the batch, speciﬁcally including three key
ﬁelds: log index ("index"), the component domain to which the
log belongs ("domain"), and the original log content ("log").
E. Log Processing and Standardization Phase
In the Log Processing and Standardization Phase, LogEx-
pertSolver performs domain-aware log parsing and normal-
ization. This phase consists of three main steps: domain-
speciﬁc preprocessing, variable standardization, and template
generation.
To achieve this, the system conﬁgures two expert agents
based on the CrewAI collaborative framework a Log Prepro-
cessing Expert and a Log Standardization Expert. Each expert
focuses on distinct but complementary tasks. The Preprocess-
ing Expert extracts key message content from raw logs, while
the Standardization Expert normalizes textual and numerical
variables to produce uniﬁed templates.
This design allows LogExpertSolver to leverage domain
knowledge effectively, ensuring structured and consistent pars-
ing results. The entire workﬂow operates through CrewAIs
multi-agent coordination mechanism, where each agent exe-
cutes its domain-speciﬁc tasks deﬁned by role-based prompts
and standardized task schemas. Each prompt deﬁnes the agents
expertise and expected JSON-formatted output, enabling reli-
able downstream integration.
Following the domain classiﬁcation process (Figure 3), each
log is assigned to a corresponding functional domain and then
passed to the two specialized agents for further processing.
For instance, given the log message Dec 10 07:07:45 LabSZ
sshd[24206]: Failed password for invalid user test9 from
52.80.34.196 port 36060 ssh2, the system determines that it
belongs to the Authentication domain. Figure 4 shows the
complete processing pipeline for this entry.
First, the Domain Log Preprocessing Expert extracts the
core content Failed password for invalid user test9 from
52.80.34.196 port 36060 ssh2. Then, the Domain Log Stan-
dardization Expert replaces numeric and textual variables with
placeholders, transforming it into a standardized log template.
This phase concludes the parsing process and provides struc-
tured log templates for subsequent analysis tasks.

V. E VALUATION
A. Dataset
To comprehensively evaluate our proposed LogExpertSolver
method, we ﬁrst need to select appropriate benchmark datasets.
Based on the raw log data and ground truth provided by
the selected dataset, we will conduct experimental evaluations
from three dimensions: the overall effectiveness of our method,
the contribution of functional modules, and the impact of
various base LLMs on system performance. When selecting
benchmark datasets, we focus on two key factors: the dataset
should contain diverse log data from real-world systems and
provide accurate templates as evaluation ground truth. After
in-depth analysis of existing datasets, we chose LogHub2.0 as
our experimental dataset for the following reasons.
Zhu et al. [28] constructed a log parsing benchmark dataset
called LogHub, which contains real log data from 19 different
software systems. It has been widely used for evaluating and
comparing the accuracy of log parsers [29]–[31]. However,
subsequent studies [17] discovered instances of incorrectly
labeled log templates, which affected the reliability of bench-
mark testing.
LogHub2.0 [32] is the latest large-scale log parsing annota-
tion dataset constructed by the LogPAI team based on LogHub,
collecting high-quality real datasets from 14 software systems.
Consistent with LogHub, each system similarly contains 2,000
log messages along with their corresponding log templates.
Currently, LogHub2.0 has been widely adopted in related
research on log parser evaluation and comparison [19], [33].
Given that LogHub2.0, as an updated version, possesses
higher data quality, while the annotation errors in some logs of
the original LogHub dataset require substantial manual costs
for correction, this paper selects LogHub2.0 as the benchmark
testing dataset for experiments in order to obtain more reliable
benchmark testing results and minimize manual intervention
in the testing process to the greatest extent possible.
It is worth noting that the Loghub2.0 dataset is derived from
operational logs of real-world systems such as Hadoop, HDFS,
and Spark, thus sufﬁciently capturing the characteristics of
practical log parsing scenarios.
B. RQ1: What is the effectiveness of LogExpertSolver?
Motivation. Accuracy is the most crucial metric for eval-
uating the effectiveness of log parsers, as it signiﬁcantly
impacts downstream tasks [21]. In RQ1, we investigate the
effectiveness of LogExpertSolver.
Method. We compare LogExpertSolver with other parsers.
AEL [34], Drain [35], and UniParser [30] perform log parsing
based on syntax and semantics, demonstrating superior per-
formance among traditional log parsers. LogPPT [13], LLM-
Parser [2], and LibreLog [21] are recently proposed LLM-
based parsers that offer enhanced semantic understanding and
higher PA.
Result. As shown in Table I, LogExpertSolver achieves the
highest PA on most systems. It achieves an average PA of
0.915, outperforming other parsers.
T5Base and LILAC show relatively weaker performance
among LLM-based parsers. Compared to LogExpertSolver,
T5Base and LILAC exhibit notable performance gaps. While
these parsers all use demonstrations to help language models
understand the log parsing process, the key difference lies in
how expert knowledge is applied. LILAC relies on contextual
learning for demonstration, while T5-base uses few-shot ﬁne-
tuning, showing limited capability in capturing complex log
patterns, as evidenced by their poor performance on systems
like BGL and Spark. In contrast, LogExpertSolver incorporates
domain parsing rules and thinking patterns through a multi-
agent expert system, enabling it to analyze and understand
logs like professionals. The effectiveness of this strategy is
reﬂected in parsing results across various systems, achieving
extremely high accuracy in different types of system logs
such as Apache, Zookeeper, and BGL. This indicates that
systematic incorporation of expert knowledge is more crucial
than mere example demonstrations in log parsing tasks.
Notably, despite LILAC’s use of the powerful commercial
model ChatGPT as its foundation model, its performance still
falls behind LogExpertSolver, which uses locally deployed
smaller models, on systems like Hadoop, Zookeeper, and BGL.
According to Ma et al. [21], when LILAC replaces ChatGPT
with smaller open-source models, its parsing capability sig-
niﬁcantly decreases, and LogExpertSolver surpasses LILAC
to achieve the highest PA in systems like Spark. This not
only demonstrates the crucial role of expert knowledge in log
parsing but also shows that well-designed agent systems can
effectively compensate for capability gaps due to model size
limitations, enabling even smaller models to achieve efﬁcient
and accurate log parsing. This ability to maintain high perfor-
mance despite model size constraints gives LogExpertSolver
stronger deployment advantages and broader applicability in
practical applications.

(2) Superior Performance of Cluster Approach in Cer-
tain Systems. In HDFS, OpenStack, and Linux datasets, the
Cluster approach achieves higher PA. One possible explanation
is that these datasets contain fewer contents and have more
regular formats, allowing the Drain algorithm to effectively
and accurately group logs, and a single template extraction
Agent is sufﬁcient to complete the extraction task. In such
cases, the direct process of clustering and template extraction
might be a straightforward and effective method.
Overall, the proposed log processing and standardization
phase is an effective component in the LogExpertSolver.
Compared to the traditional process of clustering followed by
template extraction, ﬁne-grained processing of individual log
entries can bring performance improvements across multiple
datasets, especially in scenarios with richer log content and
more diverse formats.
D. RQ3: What is the effectiveness of LogExpertSolver with
different LLMs?
Motivation. Unlike log parsers such as LILAC [13] that use
commercial LLMs, LogExpertSolver employs open-source,
smaller LLMs to mitigate parsing costs. Different LLMs ex-
hibit varying capabilities due to their unique architectures and
pre-training data [21]. In RQ3, we evaluate LogExpertSolver’s
performance across various open-source local LLMs.
Method. In addition to Qwen3-14B, we selected two other
models with similar parameter sizes to compare the perfor-
mance of log parsing using different LLMs. These models
include Qwen2.5-14B and DeepSeek-R1-14B, which are com-
monly used in research and practice.
Result. Table III shows the parsing performance of LogEx-

Table III, Qwen3-14B achieved the best performance on 9 out
of 14 datasets, with an average accuracy of 0.915. Notably,
it achieved perfect PA 1.000 on Zookeeper, Apache, and
Proxiﬁer datasets. Qwen2.5-14B, as the second-best model,

accuracy of only 0.451, signiﬁcantly lowering its overall per-
formance. DeepSeek-R1-14B showed relatively weaker overall
performance with an average accuracy of 0.718. Although
it achieved the best score 0.791 on the HDFS dataset, its

primarily based on three approaches: frequent pattern mining,
clustering, and heuristic methods [15].

Clustering Methods. Templates and variables are extracted
by comparing common and different parts within groups.
Ofﬂine modes such as LKE [38], LogSig [39], and LogMine
[40] perform batch clustering; online modes such as SHISO
[41] and LenMa [42] process new logs in real-time using
streaming approaches.
Heuristic Methods. Leverage structural characteristics of
log messages, encoding rules for template extraction. Typical
methods include parsing tree structures that guide the log
matching process by constructing ﬁxed-depth parsing trees [2].
Drain [35] constructs ﬁxed-depth parsing trees to efﬁciently
organize log patterns, achieving SOTA performance among
traditional unsupervised parsers [15]. Improvements based on
Drain include: POP [43] enables distributed deployment, and
SPINE [31] introduces human feedback mechanisms.
2) Supervised Log Parsing Parsers: Supervised log parsers
extract log templates by training deep learning models on
annotated datasets. Traditional unsupervised parsers primarily
rely on syntactic analysis, treating log messages as strings and
using statistical features to extract common parts, while ignor-
ing semantic information contained in parameters and tem-
plates [13], [16], [30]. To address this issue, researchers have
proposed supervised methods to mine semantic information
from logs. SemParser [16], as the ﬁrst semantic-based parser,
breaks through the key bottleneck of log semantic mining;
UniParser [30] effectively captures common log behaviors in
heterogeneous log data by learning patterns of log tokens and
their neighboring contexts.
3) LLM-based Log Parsing Parsers: Deep learning-based
log parsers have validated the feasibility and effectiveness of
utilizing pre-trained models for log parsing [15].
Early work LogPPT [13] employed prompt-based few-shot
learning to ﬁne-tune RoBERTa [44] for capturing log patterns.
As a preliminary attempt to apply LLMs to log parsing, it
demonstrated higher accuracy than traditional syntax-based

features, or ﬁne-tuning on speciﬁc training data. This method
is based on a Multi-Agent framework, reasoning capabilities
to directly mine semantic information from target logs and
parse log templates.
VII. T HREATS TO VALIDITY
External Validity. We discovered issues in the truth of
certain logs within the LogHub-2.0 dataset. For instance, in
the BGL system, we found missing template symbols: the 10th
log template "ciod: failed to read message preﬁx on control
stream (CioStream socket to <*>:<*>" lacks a closing ")"
symbol, which LogExpertSolver correctly preserved. Similar
issues were observed in Mac system logs: for log entry 1875,
"vmware-usbarb-25037.log", the truth parses it as "vmware-
usbarb-<*>.log", while LogExpertSolver treats it as a complete
variable and replaces it entirely with a placeholder; in log
entry 1937, for "bssid 5c:50:15:36:bc:03", the truth provides
a difﬁcult-to-understand template "bssid <*>:<*>:<*>:<*>",
whereas LogExpertSolver more reasonably parses it as "bssid
<*>". These issues not only affect the accuracy of performance
evaluation but also increase the manual effort required for
result veriﬁcation.
Internal Validity. Logs still retain natural language proper-
ties, which can lead LLMs to produce different yet reasonable
parsing results for the same log entry. An example is the
timestamp handling in log entry 521 of the Mac project, "RTC:
Maintenance 2017/7/3 21:47:58": the truth is "RTC: Main-
tenance <*>/<*>/<*> <*>:<*>:<*>", replacing each number
with individual placeholders, while LogExpertSolver treats
the entire timestamp as a semantic unit, generating a more
concise template "RTC: Maintenance <*>". These different
interpretations of complex log structures reﬂect the subjective
nature of log parsing tasks and pose challenges for accuracy
evaluation.
To ensure experimental reproducibility and result stability,
we implemented several technical measures. Speciﬁcally, we
set LogExpertSolver’s model generation temperature to 0
to eliminate randomness, ensuring consistent parsing results
under identical input conditions. While this setting might limit
the model’s creativity, it is appropriate for log parsing tasks
that require high consistency.
To further ensure reproducibility and transparency, all
prompt templates and conﬁguration ﬁles used in LogExpert-
Solver have been released in a public GitHub repository:
https://github.com/maochenxi/logexpertsolver-prompts.
Construct Validity. As LogExpertSolver relies on project
metadata (e.g., GitHub README ﬁles) for domain knowledge
extraction, inaccuracies or incompleteness in such metadata
may affect domain classiﬁcation and parsing accuracy. Future
work will explore adaptive strategies to mitigate this depen-
dency.
VIII. C ONCLUSION
In this paper, we introduce LogExpertSolver, a multi-agent
framework for domain-specialized log parsing, which com-
bines domain expert knowledge with multi-agent collaboration
mechanisms to reduce manual intervention in log parsing. Our
comprehensive evaluation on LogHub2.0 demonstrates that
LogExpertSolver achieves an average PA of 0.915, outper-
forming state-of-the-art log parsers (LibreLog [21] and LILAC
[19]) by 6.2% and 7.3% respectively. Furthermore, LogEx-
pertSolver addresses the high parsing cost issue associated
with commercial large-scale LLMs, meeting the requirements
for large-scale and resource-efﬁcient log parsing in practical
applications.
