RCAgentBench: An Agent-Oriented Benchmark for
Multimodal Root Cause Analysis in Microservices
Hengyue Jiang 1, Zexin Wang 2*, Xiaohui Nie 2, Di Gao 1, Jingjing Li 2, Changhua Pei 1 2
1Hangzhou Institute for Advanced Study, University of Chinese Academy of Sciences
2Computer Network Information Center, Chinese Academy of Sciences
Abstract—Root Cause Analysis (RCA) is pivotal for ensur-
ing the reliability of microservice systems. Traditional RCA
approaches are often limited by the scarcity of labeled data
and insufficient interpretability. Recently, Large Language Model
(LLM)-based agents have emerged as a promising direction
for automated RCA, thanks to their broad knowledge, strong
reasoning, and orchestration capabilities. However, the absence
of diverse labeled datasets, standardized tools, and systematic
assessment of agent patterns hinders the rigorous evaluation of
RCA agents. To address these issues, we propose RCAgentBench,
the first agent-oriented benchmark tailored for microservice
RCA. First, we construct a multimodal RCA dataset, covering
metrics, logs, and traces, and manually annotate each case with
reasoning keywords to enable comprehensive evaluation of agent
performance. Second, we introduce standardized tools and agent
patterns to support reproducible evaluation and decouple tool
capabilities from agent reasoning power. Finally, we explore dif-
ferent experimental settings across a diverse spectrum of LLMs,
spanning from small-scale open-source models to frontier closed-
source models, and provide actionable insights for the future
design of RCA agents. All evaluation framework code has been
made publicly available at: https://github.com/CSTCloudOps/
RCAgentBench.
Index Terms —Microservice System, Root Cause Analysis,
LLM-based Agent, RCA Agent
I. I NTRODUCTION
The transition from monolithic architectures to microser-
vices has become the standard for modern software engi-
neering, driven by the need for scalability and fault isola-
tion [1] [2]. However, as the scale of services grows, system
complexity rises dramatically, making the microservices sys-
tem prone to failures caused by misconfigurations, resource
contention, and hardware faults [3] [4]. In this context, Root
Cause Analysis (RCA) is critical for minimizing Time-To-
Mitigation (TTM) and ensuring system reliability [5].
Traditional RCA approaches generally fall into event-based
or sequence-based categories [6]. These methods typically
employ graph-based models, such as Graph Neural Networks
(GNNs) [7] or Graph Attention Networks (GATs) [8], to
infer causal relationships from multimodal observability data.
Despite their effectiveness in specific scenarios, they suffer
from two major limitations: heavy reliance on large-scale
labeled data, which is scarce in production, and a “black-box”
nature that provides a final prediction without an interpretable
reasoning process.
*Corresponding authors.
Recent advances in Large Language Model (LLM)-based
agents offer a paradigm shift [9]. With inherent reasoning
capabilities and the ability to orchestrate external tools, agents
can perform complex, step-by-step diagnostics similar to hu-
man site reliability engineers (SREs). However, while numer-
ous studies have proposed specific RCA agent architectures,
the field lacks a standardized framework to rigorously evaluate
and compare these agents. Constructing a benchmark that is
truly “Agent-Oriented” faces three substantial challenges:
• Lack of Reasoning-Oriented RCA Data: Existing RCA
datasets focus primarily on the final classification of
fault location and type. Relying solely on accuracy is
misleading when evaluating agent performance. The ra-
tionality of the diagnostic path is paramount. There is a
dearth of datasets annotated with “reasoning traces” or
key observations required to evaluate the logic integrity
of an agent.
• Absence of Standardized, Decoupled Tools: The per-
formance of an RCA agent is heavily coupled with the
diagnostic tools it accesses. Current approaches often mix
powerful tools with specific agent designs, making it
impossible to determine whether success stems from the
agent’s intelligence or the tool’s capability. A fair bench-
mark requires standardized, multimodal tool interfaces
that decouple tool performance from model reasoning.
• Lack of Systematic Evaluation of Agent Pattern:
Agent pattern, how the LLM plans, acts, and reflects, sig-
nificantly influences performance. Existing benchmarks
(e.g., OpenRCA [10]) primarily compare LLM backbones
within a single pattern (usually ReAct), neglecting the
interaction effects between diverse agent patterns (e.g.,
Multi-Agent vs. Single-Agent) and model scales.
To address these challenges, we propose RCAgentBench,
the first agent-oriented benchmark tailored for microservice
RCA. First, we construct a high-fidelity benchmark envi-
ronment where authentic faults are injected into a realistic
microservice system. Unlike previous datasets that only label
the final root cause, we engaged expert SREs to meticulously
annotate the entire diagnostic trajectory: from initial symptom
detection to final localization. These annotations encompass
all necessary intermediate information and reasoning logic
required to bridge the gap between symptoms and root causes.

II. BACKGROUND
With the rapid development of microservice systems, mod-
ern software architectures now consist of a large number
of highly interdependent components. As system scale and
structural complexity increase, identifying the root cause of
failures becomes significantly more challenging. Effective root
cause analysis therefore relies on extensive observability data
to gain deep insights into system runtime behavior.
A. RCA Task F ormulation
A root cause analysis task typically specifies thestart
timeandend timeof a failure event. InRCAgentBench,
we formulate the task input as a concise natural language
description and monitoring data:
1)Natural Language Query:A natural language query
containing theUUIDof the fault case and the anomaly
time window. For example:“The system experienced
an anomaly from2025-06-13T14:11:24Zto2025-06-
13T14:21:24Z. Please identify the root cause. ”
2)Monitoring Data:In addition to this description, the
agent is granted access to multimodal observability data
from the microservice system, which will be detailed in
Section II-B. The agent is not provided with pre-filtered
root cause information. Instead, it must invoke tools
to retrieve relevant metrics, logs, and traces from the
monitoring dataset based on the specified time window.
Given the input, the RCA agent is required to produce a
structuredJSONoutput consisting of three key elements:com-
ponent,reason, andreasoning trace. Thecomponentspecifies
the faulty service or module, thereasondescribes the under-
lying cause of the failure, and thereasoning traceprovides
an interpretable explanation of the diagnostic process.
B. RCA Multimodal Data
Observability data in microservice systems generally com-
prise three modalities: metrics, logs, and traces [12](Fig. 1).
a) Metrics:Metrics are time-series data collected at
discrete intervals during system execution. They typically
include system-level measurements and key performance indi-
cators (KPIs), such as CPU utilization, memory consumption,

request latency, and error rates. Metrics provide a quantita-
tive overview of system performance and are often used for
anomaly detection.
b) Logs:Logs are textual records generated by service
components, including error logs, access logs, and debug
logs. Through log collection and processing pipelines, these
records are aggregated, parsed, and transformed into structured
formats to facilitate querying and analysis. Logs often contain
fine-grained contextual information about system events and
configuration states.
c) Traces:Traces capture end-to-end execution infor-
mation across distributed services. They record sequences of
related events and system state transitions, such as function
calls, inter-service requests, CPU execution steps, memory
access, and I/O operations. Traces provide detailed insights
into the causal relationships and performance characteristics
of distributed workflows.
Many existing RCA approaches only relate to one or two
data modalities, which may result in incomplete diagnostic
information. For instance, network latency anomalies are typ-
ically reflected in metrics and traces but may not appear ex-
plicitly in logs, whereas configuration errors are often revealed
primarily through log messages. Due to the heterogeneous
manifestations of faults across different modalities [13], mul-
timodal fusion is essential for constructing a comprehensive
fault profile through complementary information integration.
This requirement introduces new challenges for RCA algo-
rithms.
C. RCA Agent
With strong generalization ability and interpretability [9],
LLMs appeared in RCA tasks but lack inherent capabilities
for directly parsing and reasoning over multimodal observ-
ability data. To address this limitation, recent research has
increasingly adopted agent paradigms. By leveraging external
tools to access and interpret system observability data, agents
can integrate heterogeneous modalities and perform more
automated and intelligent RCA [14].
Nevertheless, prior studies have largely focused on im-
proving individual agent architectures without systematically
comparing different agent design patterns [15] [16]. To better
understand the limitations and capabilities of RCA agent, we
adopt a principled approach by formulating a set of scientific
research questions for empirical evaluation. We then introduce
theRCAgentBenchframework to rigorously test.

IV. AGENTPATTERNS ANDTOOLS
In this section, we present the design principles and imple-
mentation details ofRCAgentBench.
A. Agent Patterns
To systematically evaluate the effectiveness of different
agent paradigms in addressing RCA tasks,RCAgentBench
standardizes five single-agent patterns and three multi-agent
patterns, as illustrated in Fig. 3. These are representative
patterns in modern agent systems.
1) Single-Agent Patterns:We choose five classical single-
agent pattern as our baselines.
ReAct[17] adopts an iterative reasoning and acting frame-
work. The agent repeatedly invokes multimodal diagnostic
tools based on current observations and accumulated evidence
until sufficient information is gathered to produce the answer.
Building upon ReAct, theChain-of-Thought (CoT)[18]
pattern incorporates step-by-step reasoning. The agent alter-
nates between intermediate reasoning steps and tool invoca-
tions, making its analytical process transparent and structured.
TheReflection[19] pattern introduces a self-reflection
phase. After forming an initial hypothesis, the agent re-
examines the collected evidence, identifies potential gaps or
inconsistencies, and considers alternative explanations before
finalizing the diagnosis. This additional verification stage aims
to enhance robustness and reduce premature conclusions.
ThePlan-Executepattern separates planning and execution
into two explicit stages. The agent first formulates a structured
investigation plan based on the fault description, all tool
information and subsequently executes each step through tool
calls to synthesize the final root-cause result.
TheWorkflow[20] pattern follows an event-driven, three-
phase process: (1) understanding the problem and extracting
the timeline of abnormal events, (2) collecting evidence via
tool invocation, and (3) analyzing the collected information to
generate the final diagnosis. This pattern emphasizes procedu-
ral organization and task decomposition.
2) Multi-Agent Patterns:To further explore collaborative
mechanisms, we design three multi-agent configurations.
RMAgent(Robust Multi-Agent) employs a four agents
collaboration. TheDataCollectorgathers relevant evidence
using standardized tools; theDiagnosticAgentcorrelates multi-
source signals and proposes candidate root causes; theV al-

B. Standardized Tools
To ensure fair and reproducible comparisons across different
agent models, we design a set of standardized diagnostic
tools, including a Metrics-based Tool, a Logs-based Tool, and
a Traces-based Tool. Building these tools provides unified
consistent detection logic across all agent patterns and helps
decouple tool capabilities from agent reasoning abilities.
a) Metrics-based Tool:The Metrics-based Tool performs
anomaly detection based on dynamic baseline comparison.
Given an anomaly time window defined by start and end
timestamps, the tool uses the preceding 30 minutes as the
default baseline period.
By default, anomaly detection follows the classical3-sigma
statistical rule. Specifically, the mean and standard deviation of
the baseline data are computed, and any data point exceeding
the range(µ±3σ)is labeled as anomalous. We adopt this rule-
based method due to its computational efficiency, interpretabil-
ity, and practical robustness in production environments.
In addition, the tool supports a flexible plugin-based archi-
tecture that enables alternative detection modes. For example,
a threshold-based method can be applied when predefined met-
ric thresholds are available, eliminating reliance on historical
baselines. This modular design allows flexible combinations of
detection strategies tailored to different metric characteristics,
thereby balancing efficiency and accuracy.
b) Logs-based Tool:The Logs-based Tool improves the
signal-to-noise ratio of application logs through rule-based
filtering and deduplication. It firstly loads all application logs
within the specified time window. Using a predefined keyword
list (e.g., “error”, “fail”, “exception”), the tool performs case-
insensitive regular expression matching on the message field
of each log entry.
Subsequently, logs are grouped by pod name. For each
pod, the tool extracts unique error messages and records the
timestamp of their first occurrence. By eliminating repetitive
log entries and highlighting distinct failure patterns, this design
enables the agent to efficiently identify the primary fault types
without being overwhelmed by redundant log information.
c) Traces-based Tool:The Traces-based Tool adopts a
baseline comparison approach based on aggregated tracing
data, analyzing anomalies along two dimensions:latencyand
request ratio.
Instead of examining individual spans, the tool aggregates
trace data by operation name and pod. It then computes the
average latency and request count during both the anomaly
and baseline periods. A latency anomaly is flagged if the
average latency increases by more than 100% relative to the
baseline. Similarly, a request ratio anomaly is identified if the
proportion of a service’s requests relative to the total exceeds
100% compared to the baseline period.
This two dimensional detection strategy enables the identi-
fication of both performance degradation (“becoming slow”)
and traffic imbalance issues, such as those caused by retries or
routing misconfigurations. By integrating latency and request
signals, the tool provides a comprehensive view of trace
anomalies relevant to RCA tasks.

VI. EXPERIMENTRESULTS
The primary objective of constructingRCAgentBenchis to
systematically evaluate the performance of autonomous agents
on RCA tasks under diverse experimental configurations. By
providing a rigorous and reproducible evaluation framework,
RCAgentBenchestablishes a standardized benchmark for the
design of RCA agents. Through controlled experimentation
and comprehensive ablation studies, this benchmark aims to
offer principled insights into effective agent design, thereby
facilitating sustained progress in automated RCA research.
To comprehensively evaluate RCA agents, we organize
our experimental analysis around the following four research
questions:
•RQ1: How do different agent patterns affect performance
on RCA tasks?
•RQ2: To what extent does the capability of the large
language model influence RCA agent performance?
•RQ3: How do different detection modalities impact agent
performance in RCA tasks?
•RQ4: What is the effect of incorporating additional con-
textual information into prompts on RCA performance?
A. RQ1: Agent Patterns
Insight 1
Smaller models benefit from simpler agent patterns,
while larger models are more effective with more
complex agent patterns.
Table III presents the performance comparison across dif-
ferent agent patterns and backbone models. For relatively
small-scale models (e.g., Qwen3-8B), single-agent architec-
tures consistently outperform multi-agent designs in terms of
localization accuracy (LA Top-1, LA Top-5) and task accuracy
(TA). Among the single-agent approaches, the ReAct pattern
achieves the strongest overall performance.
This trend can be attributed to the limited reasoning capacity
of smaller models. Single-agent patterns typically involve
fewer steps, as reflected in APL metric, thereby reducing
prompt complexity and context length. In contrast, multi-agent
architectures require coordination and intermediate reasoning
exchanges, leading to longer contexts. Smaller LLMs are more
susceptible to context fragmentation and information dilution
(e.g., the “lost-in-the-middle” phenomenon), which degrades
performance in complex reasoning pipelines. Consequently,
simpler architectures are preferable when the backbone model
only has constrained ability.
However, this pattern shifts as model scale increases.
For larger models such as Qwen3-32B and DeepSeek-
V3 [21], multi-agent architectures exhibit substantial perfor-
mance gains, particularly in LA Top-1 and LA Top-5 metrics.
These models possess stronger long-context reasoning and
memory integration capabilities, enabling them to effectively
coordinate multi-step interactions across agents.
Multi-agent systems consistently achieve higher explain-
ability across scales. This stems from role specialization and
perspective decomposition, encouraging sufficient reasoning
traces and explicit justifications. This suggests a trade-off
between precision and reasoning for smaller LLMs. While
single-agent systems offer efficiency for smaller models, multi-
agent designs provide superior interpretability and scalability.
B. RQ2: LLM Scales
Insight 2
RCA agent performance appears to be tool−bounded
rather than model−bounded.
Table IV reports performance comparisons across models
of varying parameter scales using the ReAct pattern as a uni-
fied agent backbone. Surprisingly, we observe no monotonic
performance improvement as model size increases. In several
cases, smaller models (e.g., Qwen3-4B) achieve competitive or
even superior localization accuracy compared to significantly
larger counterparts (e.g., Qwen3-235B-A22B).

small models can effectively integrate evidence and infer the
correct root cause. This highlights the critical importance of
tool design and information extraction quality in RCA tasks.
C. RQ3: MultiModal Tools
Insight 3
Quality of tools matters more than quantity and high
−signal, low−noise tools drive performance.
We initially hypothesized that incorporating more detection
modalities would monotonically improve RCA performance
by providing richer evidence. However, the ablation results in
Fig. 4 contradict this assumption to some extent.
When using Qwen3-8B with the ReAct architecture, remov-
ing the Metrics-based tool leads to an improvement in LA Top-
5 accuracy. This suggests that metrics data, although compre-
hensive, may introduce substantial noise. Time-series metrics
often reflect symptomatic anomalies without clearly indicating
causal structure. Furthermore, the complex interdependencies
among metrics can overwhelm smaller models, increasing the
difficulty of precise localization.
In contrast, logs and traces are more directly associated with
specific components and execution paths. These modalities
provide semantically dense and contextually grounded evi-
dence, which enables faster and more precise fault localization
than metrics. For models with limited context management
capacity, such structured and component-level signals are
easier to integrate.
However, metrics remain essential for comprehensive RCA.
Although removing the Metrics-based tool may improve lo-
calization in certain settings, Explainability and overall task
robustness decline. Metrics provide quantitative symptom ver-
ification and causal corroboration, enabling agents to justify
why a component is faulty rather than merely identifying it.
Thus, while metrics may introduce complexity, they contribute
significantly to diagnostic completeness.

D. RQ4: Additional Information
Insight 4
System information and fault level hierarchy hints
have vital instruction significance for RCA agent.
Table V demonstrates that removing Fault Level Hierarchy
information results in substantial performance degradation,
particularly in localization accuracy. In microservices architec-
tures, cascading failures are common and a pod-level malfunc-
tion may also trigger service-level anomalies. Without explicit
hierarchical guidance, agents may correctly detect anomalous
components but fail to precisely identify the true root-level
cause.
Notably, Explainability does not degrade proportionally,
suggesting that agents still detect anomalous behaviors but
struggle with precise hierarchical attribution. This observation
aligns with operational practices in real-world workflows,
where engineers rely heavily on hierarchical system decom-
position to isolate faults.
Similarly, removing System Information, such as Kuber-
netes interdependencies, service call chains, and pod states,
leads to marked declines in LA Top-5 performance. When
direct anomaly signals are incomplete or ambiguous, agents
leverage dependency graphs to infer plausible fault propaga-
tion paths. System information thus provides structural priors
that guide evidence collection and tool selection.
In summary, contextual information serves as structural in-
ductive bias for RCA agents. Incorporating system information
and fault hierarchy not only improves localization accuracy
but also enhances the strategic coordination of detection tools.
This underscores the importance of domain-informed prompt
engineering in practical RCA agent design.

VII. CASESTUDY
In this section, we present representative cases observed
during the evaluation process and conduct an in-depth analysis
based on these empirical results.
For RQ3, we present a case generated by the ReAct agent
pattern with Qwen3-8B as the backbone model to illustrate
why the metrics modality may introduce redundant or less
informative signals for the RCA task. As shown in the Fig. 5,
the information extracted from the metrics modality is com-
plex and often lacks explicit relational cues between specific
metrics and fault instances. This increases the cognitive burden
on the agent when attempting to infer causal relationships.
In contrast, trace and log modalities provide more direct and
localized evidence of anomalous behavior, enabling the agent
to identify failure instances without exhaustively reasoning
about low-level metric fluctuations. This case demonstrates
that, although metrics contain rich system-level information,
they may not always provide the most discriminative signals
for fine-grained root cause localization in RCA agent tasks.
For RQ4, we further provide a case study to demonstrate
the role of system auxiliary information in the RCA task. As
illustrated in Fig. 6, frontend and currencyservice are all de-
tected with anomaly, but the true root cause “checkoutservice”
isn’t detected by the tool successfully.
Fig. 6: A case of the ReAct agent (Qwen3-8B) with system-

However, when service call chain information in this case
(“frontend→checkoutservice→currencyservice”) is incor-
porated into the prompt, the agent is able to reason over the de-
pendency structure and infer additional components potentially
involved in the fault propagation process. By leveraging this
structured system knowledge, the agent can produce a more
comprehensive root cause prediction, which contributes to
improved performance under the LA Top-5 evaluation metric.
VIII. DISCUSSION
One limitation ofRCAgentBenchlies in the diversity of
integrated diagnostic tools. In the current version, we do
not extensively compare alternative machine learning or deep
learning diagnostic tools that may offer competitive or com-
plementary capabilities. The selection of more effective and
robust tools could influence the quality of extracted fault
information and, consequently, the overall validity of RCA
performance evaluation in microservice environments.
Furthermore, the dataset labels provided byRCAgentBench
enables the definition of reward functions that can support
AgenticRL[22] [23] methods. By leveraging reinforcement
learning techniques, agents can iteratively improve their rea-
soning and decision making strategies for RCA. In future
work, we plan to explore reinforcement learning approaches
to further enhance the adaptability of RCA agents.
IX. RELATEDWORK
A. RCA Agent
Agents are widely used to execute RCA tasks [24] [25] [26].
Flow-of-Action [27] applies Standard Operation Procedure
(SOP) enhanced multi-agent system to guide the RCA process
towards to the correct way. mABC [28] incorporates seven
expert agents and utilizes blockchain vote mechanism to
reduce the risk of hallucination in LLMs. However, above-
mentioned RCA agent didn’t evaluate different agent patterns
systematically. Hence,RCAgentBenchoffers these comparison
and gives insights.
B. RCA Benchmark
Benchmarks are essential frameworks for evaluating and
comparing agent models. Widely recognized RCA bench-
marks, such as RCAEval [29], AIOpsArena [30] provide
accesss to evaluate relatively traditional algorithm performance
on the RCA task, without a suitable platform for agent execu-
tion. OpenRCA [10] builds dataset and benchmark for RCA
agent evaluation. However, it only relates to ReAct pattern and

X. CONCLUSION
In this paper, we address the critical gaps in evaluating
agents for microservice RCA by introducingRCAgentBench,
the first systematic framework that integrates a diverse mul-
timodal labeled dataset with standardized detection tools. By
decoupling tool capabilities from LLM-based agent reasoning,
our comprehensive evaluation reveals that simpler single-agent
patterns are effective for smaller models, while multi-agent
architectures offer superior interpretability and scalability for
larger LLMs. Crucially, we find that RCA performance is cur-
rently “tool-bounded”, suggesting that information extraction
from observability data is a more significant bottleneck than
model scaling. These insights provide a principled foundation
to guide the future development of reliability RCA agents.
