Harness Resilience:
From LLM Availability to Toolchain Continuity in Agentic AI
Engineering
John Cheung
College of Professional and Continuing Education
Abstract
By early 2026, the practical value of artificial intelligence in software engineering is no longer deter-
mined solely by the reliability of the underlying large language model (LLM). Increasingly, productivity
depends on an execution harness: the surrounding runtime of prompts, tools, sandboxes, permissions,
memory, repositories, connectors, model-routing policies, observability, and user-interface affordances
that turn a model into an operational coding or general-purpose agent. Popular systems such as Codex,
Claude Code, Gemini CLI, Cursor-like development environments, and general agents such as Manus
demonstrate that the “AI product” is not only a model but a socio-technical toolchain. This paper argues
that AI resilience must therefore be extended into harness resilience: the ability of an engineering team
to continue safe and effective work when a preferred AI agent harness changes behavior, loses access,
degrades, is rate-limited, is withdrawn from a plan, suffers a security incident, or becomes unavailable.
Using an illustrative X.com post by Peter Gostev about a Claude Code user being humorously shown
as opted out after a code-quality review, this paper motivates a broader resilience agenda: portability
of context, tool abstraction, reproducible agent workflows, fallback harnesses, audit trails, and human
recovery procedures. The paper contributes a reference architecture, a failure-mode taxonomy, measur-
able resilience objectives, a connector threat model, and an evaluation plan that turns the concept from a
practice guide into a testable engineering framework.
Keywords: AI resilience, agentic AI, harness resilience, coding agents, Codex, Claude Code, Manus, MCP,
AI engineering, software development lifecycle, provenance, agent testing
1 Introduction
The first wave of enterprise AI resilience focused on model-level questions: whether an LLM was accu-
rate, safe, available, cost-effective, and compliant. This was natural when most use cases were chat-based
or retrieval-augmented generation systems. However, by early 2026, the center of gravity has shifted. AI
systems used by engineers increasingly act through rich harnesses that read codebases, edit files, run com-
mands, call tools, coordinate multi-step tasks, and integrate with local or remote development environments.
In this setting, resilience cannot be limited to the LLM. A powerful model accessed through a fragile
harness may be less useful than a slightly weaker model embedded in a reliable, auditable, portable, and
well-governed workflow. The practical unit of dependency is no longer “the model” but the model-harness
combination.
This paper defines a harness as the operational layer that surrounds a foundation model and enables
it to act. In coding and agentic tools, this layer commonly includes system prompts, repository context,

The key claim is simple: AI engineering teams need business-continuity planning for their AI harnesses.
If a harness disappears tomorrow, changes its behavior, loses a connector, changes its policy, or becomes
untrusted, the team should still be able to build, debug, test, and ship software.
1.1 Contributions
This position paper makes five contributions:
1. defines harness resilience as a distinct layer between model reliability and application reliability;
2. proposes a reference architecture and boundary criteria for the model, harness, application, and gover-
nance layers;
3. introduces measurable objectives for functional, context, tool, governance, and human resilience;
4. provides a connector-oriented threat model and failure-mode taxonomy;
5. outlines an evaluation plan using golden tasks, failure injection, provenance metrics, and cost-latency
analysis.
2 Background: From LLMs to Harnesses
Agentic coding tools in 2025–2026 demonstrate a major design transition. Claude Code is commonly used
as an agentic coding tool that can read a codebase, edit files, run commands, and integrate with development
tools [1]. Gemini CLI similarly popularizes an AI agent in the terminal and documents a reason-and-act
style loop using built-in tools and local or remote MCP servers [2]. Codex has expanded from a coding
model brand into a broader software engineering assistant and enterprise workflow [3]. General agents such
as Manus further popularized the idea that an AI system should bridge ideation and execution rather than
merely answer questions.
These systems are not interchangeable chat windows. They embody distinct assumptions about how
context is collected and compacted, how files are edited, how shell commands are approved, how secrets
are protected, how plans are revised, how sub-agents are delegated, how tool failures are surfaced, and how
much control the user retains. Thus, the harness is a source of productivity, but also a source of lock-in and
fragility.
3 Boundary and Reference Architecture
A precise boundary is needed because the terms “harness”, “agent”, and “application” are often used in-
terchangeably. In this paper, the model is the statistical inference service or local model. The harness
is the orchestration and execution substrate that packages context, invokes the model, exposes tools, man-
ages permissions, records traces, and applies policy. The application is the user-facing product or business
workflow that embeds the harness. The governance layer is the organizational control plane that sets data,
access, procurement, incident, and audit requirements.

The boundary criterion is operational: if replacing a component requires changing context packaging,
tool permissions, workflow traces, approval gates, or user interaction patterns, that component is part of the
harness or tightly coupled to it. This distinction matters because a model can be healthy while the harness
is degraded, or a harness can be portable while the application remains vendor-specific.
3.1 Boundary Contract Checklist
For automated governance, each component can publish a small boundary contract. The contract declares:
(i) inputs and outputs; (ii) state it can read or mutate; (iii) external tools or connectors it can call; (iv)
credentials and privileges it can access; (v) trace fields it emits; (vi) failure modes and fallback path; and
(vii) replacement interface. A component is classified as harness-critical when it satisfies any of four tests:
replacing it changes tool authorization, changes context assembly, changes state mutation, or changes audit
evidence. This contract converts the intuitive harness/application distinction into a checklist that can be
reviewed in architecture governance and CI.
4 The Early 2026 Status of Harness Dependence
By early 2026, harness dependence has become visible in three ways.
4.1 Adoption at Scale
Coding agents have moved from experimental tools to mainstream engineering infrastructure. Public dis-
cussion around Codex, Claude Code, Gemini CLI, Manus, and related products shows that agentic coding
tools are no longer side utilities; they are becoming part of organizational software delivery systems.
4.2 Product-Level Degradation
The Claude Code performance discussions in 2026 illustrate why harness resilience matters [4]. In an
agentic product, user experience can degrade even when the base model remains strong. A change in prompt
policy, cache behavior, context packaging, tool execution, default reasoning level, or user-interface workflow
may reduce practical reliability.
For engineering teams, this means that monitoring only model benchmarks is insufficient. Teams should
monitor the end-to-end harnessed workflow: instruction loading, repository reading, tool invocation, shell
execution, patch quality, test execution, reviewability, and rollback.

4.3 Protocol and Connector Risk
The rise of MCP-style tool integration makes harnesses more powerful but also increases the attack surface.
MCP standardizes how agents connect to external tools and data sources [5]. This improves interoperability,
but it also creates dependency on connector security, tool schemas, command execution boundaries, and
permission models. A harness that can call tools can also misuse tools, over-trust tool output, leak context,
or execute unsafe operations if its governance layer is weak.
5 Illustrative Case: When a Harness Relationship Breaks
A post on X.com by Peter Gostev, AI Capability Lead of Arena.ai, dated 26 April, presents a humorous
Claude Code scenario in which the user is shown as being opted out after a review of code quality [6]. This
paper does not treat the post as authenticated evidence of an actual vendor policy. Instead, it is useful as a
cultural signal: developers increasingly perceive AI coding tools as active participants in the development
workflow, not passive utilities.
The joke works because it exposes a real anxiety. If a coding agent learns from, evaluates, stores, filters,
or governs user work, then the user is dependent not only on model quality but also on the rules and policies
of the surrounding harness. A vendor may change who can access a tool, which plan includes it, whether
user data is retained, how code is routed or stored, which tools are permitted, or whether a workflow is
considered abusive, risky, or unsupported.
The resilience question is therefore: what can an AI engineer do when the harness is no longer avail-
able?
6 Related Work
Harness resilience sits at the intersection of software reliability engineering, agent testing, provenance, se-
curity governance, and context management. AgentAssay gives a statistical foundation to the “golden task”
idea by treating agent regression testing as a stochastic process with pass, fail, and inconclusive outcomes,
behavioral fingerprints, and sequential probability ratio testing (SPRT) to control error and trial cost [7].
More general work on AI-agent reliability argues that a single success rate hides important operational
failures and decomposes reliability into consistency, robustness, predictability, and safety [8]. Harness re-
silience complements this line of work by focusing not only on whether an agent succeeds, but whether the
organization can recover when the harness, connector, memory, or policy layer changes.
Trust, Risk, and Security Management (TRiSM) for agentic multi-agent systems emphasizes gover-
nance, explainability, ModelOps, and privacy/security [9]. Harness resilience can be read as the business-
continuity counterpart to TRiSM: it converts trust and risk concerns into operational targets such as time-to-
fallback, provenance coverage, connector replacement ratio, and recovery time.
Auditability and provenance work provides a second foundation. Claim-level auditability work intro-
duces provenance metrics such as provenance coverage, soundness, contradiction transparency, and audit
effort for deep research agents [10]. R-LAM proposes structured action schemas, deterministic execution
policies, and explicit provenance tracking for replayable action workflows [11]. For engineering harnesses,
these ideas can be adapted from research claims to software actions: every file edit, tool call, command,
approval, and generated explanation should be traceable to a context state, model invocation, and human de-
cision. W3C PROV defines a domain-agnostic model for entities, activities, and agents [12]; OpenTelemetry
traces represent operations through spans that can be exported to observability backends [13]. These stan-
dards offer practical building blocks for harness trace schemas.

Context portability is addressed by Git-Context-Controller, which treats agent memory as a persistent,
versioned hierarchy inspired by Git operations such as commit, branch, merge, and context [14]. The Agen-
tic File System abstraction similarly treats context artifacts as governed, mounted, traceable resources [15].
Lore proposes structured knowledge atoms embedded in Git commit metadata, offering a lightweight mech-
anism for preserving implementation rationale with code changes [16]. Context-compression and memory-
action systems, including empirical work on repository-level context compression and autonomous mem-
ory operations, are also relevant because they move context selection and forgetting into the harness itself
[17, 18]. These modules can improve latency and token cost, but they should be governed as resilience-
sensitive components because they affect what the agent remembers, omits, and can export.
Systems work on persistent multi-agent orchestration, such as TheBotCompany, demonstrates milestone-
driven strategy, execution, and verification loops for longer software-development tasks [19]. SWE-Skills-
Bench shows that injected software-engineering skills may have limited or even negative marginal value
when mismatched with project context, which supports the need for harness-level compatibility checks, ver-
sioned skill registries, and regression gates [20]. Automated Self-Testing further suggests evidence-driven
release gates with promote, hold, and rollback decisions for LLM applications [21]. Together, these works
make harness resilience measurable rather than only aspirational.
7 Defining Harness Resilience
Harness resilience is the ability of a team to maintain acceptable engineering productivity, safety, and gov-
ernance when an AI harness fails, changes, or disappears. It has five dimensions.
7.1 Functional Resilience
The team can still perform core tasks: code search, code generation, refactoring, test creation, debugging,
documentation, migration, review, and release support.
7.2 Context Resilience
The team can preserve and reuse project context, including architecture notes, coding standards, repository
maps, API contracts, testing instructions, deployment procedures, and known failure modes.
7.3 Tool Resilience
The team can switch between harnesses without rewriting every tool integration. This requires abstraction
of tool schemas, stable command wrappers, documented permissions, and fallback execution paths.
7.4 Governance Resilience
The team can maintain auditability, security, privacy, and compliance even when moving between vendors
or local alternatives.
7.5 Human Resilience
Engineers remain capable of understanding, reviewing, and completing work manually. The harness may
accelerate engineering, but it must not become the only holder of operational knowledge.

A concrete CES example illustrates the intended scoring. Suppose a repository has eight required arti-
facts with equal weights: AGENTS.md, architecture map, test commands, deployment notes, tool schema
manifest, permission manifest, memory export, and golden-task list. If five are directly portable, two require
minor rewriting, and one is missing, then CES = (5 + 2 × 0.5 + 0)/8 = 0 .75. A regulated team may set a
release threshold of CES ≥ 0.85, P Cov ≥ 0.95 for production-impacting actions, and p90 TTF below one
working day. A small research prototype may accept lower targets but should still record the denominator
and scoring basis.

11 Practical Actions for AI Engineers
11.1 Maintain a Harness-Agnostic Project Context
Every repository using AI coding agents should contain a vendor-neutral context package. This may include:
• AGENTS.md or equivalent project instructions;
• architecture overview and repository map;
• development setup and test commands;
• coding conventions and security constraints;
• deployment notes and rollback procedures;
• examples of good changes and known anti-patterns;
• exported tool schemas and connector permissions.
When a harness is unavailable, the same context can be loaded into another agent or used by humans.
Appendix-style artifacts that should be released with a practical implementation include an extttAGENTS.md
template, a context-manifest schema, a fallback checklist, and a KPI calculator.
11.2 Separate Model, Harness, and Tool Layers
Teams should avoid designing workflows in which the model, harness, and tools are inseparable. A resilient
architecture separates the model provider, agent runtime, tool protocol, execution environment, project
memory, and audit/governance layer. This makes replacement possible. For example, a team may use
Claude Code for one class of tasks, Codex for another, Gemini CLI for open-source terminal workflows,
and a local model for restricted code review, provided that common instructions and tools are portable.
11.3 Build an Agent Runbook
A harness resilience runbook should answer: which tasks depend on which AI tools; what the manual
and secondary AI fallbacks are; what data is allowed in each tool; how secrets are protected; how agent-
generated changes are reviewed; how an agent action can be reproduced; and who decides when to disable
a harness.

11.4 Use Golden Tasks for Regression Testing
Teams should maintain a small benchmark of internal “golden tasks” that represent real engineering work,
such as fixing a known bug, adding a small endpoint, refactoring without behavior change, writing unit tests,
explaining a legacy subsystem, or detecting a security issue in a pull request. To avoid anecdotal testing,
each task should define expected artifacts, pass/fail/inconclusive criteria, trace fields, and a token budget.
Sequential testing methods such as AgentAssay can be used where repeated stochastic runs are necessary
[7].
11.5 Capture Provenance and Traces
Harness actions should produce trace records that can be stored alongside CI logs and commits. A minimal
record contains the task ID, context version, model/harness version, tool calls, files changed, commands
executed, approvals, test results, and final human reviewer. OpenTelemetry spans can represent the tem-
poral execution trace, while W3C PROV-style entities, activities, and agents can represent causality and
responsibility [12, 13].
11.6 Design for Human Review and Rollback
Harness resilience depends on ordinary software engineering discipline: small commits, branch isolation,
code review, test coverage, CI gates, reproducible environments, and rollback procedures. The more au-
tonomous the harness, the stronger these controls must be.
11.7 Control Tool Permissions
Agent tools should follow least privilege. A coding agent may need to read a repository and run tests, but
it rarely needs unrestricted production credentials. Sensitive operations should require explicit approval,
separate identities, sandboxed environments, dry-run modes, or policy-as-code checks.
11.8 Keep a Local or Open Alternative
A resilient AI engineering team should maintain at least one fallback path that does not depend on a single
vendor account. This may be an open-source CLI harness, a locally hosted model for basic coding support,
or a minimal scriptable workflow that provides repository search, context packing, and patch generation.
The fallback does not need to match the primary harness in quality; it only needs to preserve continuity
during incidents.
12 Evaluation Plan and Initial Study Design
A stronger validation program should combine controlled experiments with field case studies. The evalua-
tion should instantiate the KPIs rather than merely list them.
12.1 Cross-Harness Golden-Task Protocol
A minimal study can use 20–40 tasks sampled from three classes: code modification, debugging/test repair,
and repository understanding. Each task should be pinned to a repository commit, include acceptance cri-
teria, and define deterministic verification where possible. The study should run each task under: primary
harness, secondary harness, and manual fallback. For stochastic harnesses, repeated runs can be stopped

12.2 Failure Injection
Failure injection should simulate at least five events: access loss, connector outage, rate limit, prompt-

path used, TTF, MTTHR, error rate, provenance completeness, and whether the runbook was sufficient. A
successful drill is not one in which nothing fails; it is one in which the team detects the failure, moves to an
approved fallback, preserves auditability, and completes or safely stops the task.
12.3 Security and Provenance Exercises
Security exercises should seed prompt-injection payloads in issues, README files, dependency documen-
tation, and tool outputs; introduce canary secrets; and mock a malicious connector that attempts unexpected
side effects. Measurements include true positives, false positives, false negatives, containment rate, approval
latency, and rollback success. Provenance audits should sample completed agent actions and compute PCov
using Table 3. A trace should be considered incomplete if it lacks context version, tool arguments, permis-
sion record, output hash, or reviewer disposition for a state-changing action.
12.4 Synthetic Example of Metric Reporting
A small pilot could report the following synthetic format: 30 golden tasks, two harnesses, one manual
fallback, three injected incidents. Results might be presented as “primary harness p90 TTF under connector
outage = 3.8 hours; secondary harness p90 TTF = 1.1 hours after runbook update; PCov improved from
0.62 to 0.94 after trace instrumentation; ROR = 1.18x token cost and 1.07x wall-clock latency.” Such a table
would not prove universal validity, but it would ground the framework and make future replication possible.
12.5 Cost, Latency, and Developer Experience
Resilience controls should be right-sized. High-criticality workflows should record complete traces, en-
force approvals, and test redundant harnesses. Low-risk exploratory coding can use sampled tracing and
lightweight fallbacks. Teams should track developer approval time, false-positive security blocks, and
survey-based friction scores. A control that improves PCov but doubles cycle time for low-risk changes
may be inappropriate; the same control may be mandatory for production-impacting automation.
This evaluation plan does not require every team to publish academic benchmarks. It requires opera-
tional evidence that the harness can fail without stopping the engineering organization.

14 Implications for Enterprises
For enterprises, harness resilience should become part of AI governance and business continuity planning.
Procurement should evaluate not only model accuracy and price, but also exportability of project mem-
ory, support for open standards, audit logging, administrative controls, sandboxing options, data residency,
incident communication, contractual change notice, and the ability to run controlled regression tests.
Controls should be right-sized. Redundancy and provenance carry cost, latency, and developer-experience
overhead. High-criticality workflows, regulated data, and production-impacting automation justify stronger
gates. Low-risk exploratory coding may use lighter logging and fewer repeated tests. The goal is not to slow
every developer; it is to prevent a fragile harness dependency from becoming a single point of organizational
failure.
15 Discussion
The phrase “AI resilience” should now include three layers:
1. Model resilience: quality, safety, latency, cost, and availability of the LLM.
2. Application resilience: reliability of the AI-enabled product or workflow.
3. Harness resilience: continuity of the execution layer that turns model output into action.
The third layer is becoming increasingly important. Coding agents and general agents are effective
precisely because they are not just chatbots. They hold context, execute tools, modify state, and shape
engineering practice. Therefore, their failure is not merely an inconvenience; it can interrupt the software
delivery lifecycle.
The Gostev X.com post is humorous, but the underlying lesson is serious. AI engineers should not ask
only, “Which model is best?” They should ask, “Can our team still work if this harness changes tomorrow?”
16 Limitations
This paper is primarily a position paper and practice framework. It does not yet report a controlled empirical
study, multi-organization case evidence, or statistically powered comparison of harnesses. Its proposed
KPIs and evaluation plan require calibration in real engineering environments. Future work should publish
open templates, reference harnesses, reproducible golden-task suites, and anonymized incident studies that
measure effect sizes, costs, and failure recovery outcomes.

17 Recommendations
We recommend that AI engineering teams adopt the following minimum practices:
1. Maintain a vendor-neutral project instruction file and context package.
2. Keep architecture and operational knowledge outside proprietary agent memory.
3. Define measurable KPIs such as TTF, MTTHR, context exportability, and provenance coverage.
4. Test at least two AI harnesses on critical development tasks.
5. Record agent-generated changes through normal version control and trace logs.
6. Require human review for production-impacting modifications.
7. Sandbox command execution and restrict secrets.
8. Maintain a manual fallback for release-critical workflows.
9. Track harness incidents separately from model incidents.
10. Rehearse a “no preferred AI tool” day once per quarter for high-dependency teams.
18 Conclusion
The current agentic AI landscape marks a transition from model-centric AI adoption to harness-centric AI
operations. Codex, Claude Code, Manus, Gemini CLI, and similar tools show that the productivity frontier
lies in systems that can plan, act, call tools, and manage context. However, this also means that engineering
teams inherit new dependencies.
Harness resilience is the discipline of surviving those dependencies. It asks teams to make context
portable, tools replaceable, actions auditable, permissions constrained, and humans capable of recovery.
The most resilient organizations will not be those that depend on no AI tools. They will be those that can
use powerful AI harnesses without becoming trapped by them.
