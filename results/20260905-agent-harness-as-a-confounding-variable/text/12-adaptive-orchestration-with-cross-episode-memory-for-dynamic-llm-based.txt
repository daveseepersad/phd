Abstract
Multi-agent systems are moving toward open
ecosystems in which agents may appear,
change, or disappear at runtime. Orchestra-
tors must therefore discover relevant black-box
specialists from large pools and learn how to
coordinate them across repeated tasks. Exist-
ing methods typically either maintain cross-
episode memory for fixed, well-known teams or
retrieve agents without accumulating reusable
coordination knowledge. We propose an adap-
tive orchestration architecture with an exter-
nal memory layer that enables in-context learn-
ing over dynamic agent pools without param-
eter updates. This layer combines agent play-
books, which store per-agent evidence, with
delegation blueprints, which capture reusable
workflows distilled from successful episodes.
On OfficeBench with a 50-agent pool includ-
ing distractors, we show that the adaptive sys-
tem achieves the strongest overall performance
across all evaluated configurations when oper-
ating with its own Agent Cards, outperform-
ing both sparse-card and rich-card stateless
baselines while requiring fewer orchestrator
turns. Ablations show that blueprints drive the
main end-to-end gains, whereas playbooks are
most useful when descriptions are sparse. A
dynamic-pool experiment further shows that
the memory layer incorporates newly added
specialists and prunes obsolete capability evi-
dence without manual intervention.
1 Introduction
Large language models (LLMs) increasingly serve
as autonomous agents that reason, plan, and act
across diverse tasks without task-specific training
(Fang et al.). For complex tasks, multi-agent sys-
tems distribute work across specialized agents and
have shown improvements over single-agent base-
lines on challenging benchmarks (Guo et al., b).
Open interoperability protocols such as Anthropic’s
Model Context Protocol (MCP) 1 and Google’s

Agent-to-Agent Protocol (A2A)2 are making agent
ecosystems more modular: agents can expose ca-
pabilities through standardized interfaces and be
discovered at runtime. This shift turns orchestra-
tion from a problem of coordinating a fixed team
into one of discovering, selecting, and coordinat-
ing unfamiliar specialists. Despite these advances,
current multi-agent systems face two limitations
that prevent them from fully exploiting more open
and registry-based ecosystems.(i) Rigidity.Most
systems are manually composed and statically con-
figured at design time, requiring substantial human
intervention to introduce new capabilities or inte-
grate unfamiliar agents (Hong et al.).(ii) State-
lessness.Each task is solved from scratch without
retaining knowledge from prior episodes (Fourney
et al.). This absence of memory prevents orchestra-
tors from improving their coordination decisions
over time, forcing them to repeatedly rediscover
which agents to select and how to combine them
for similar tasks. Existing approaches address
parts of this challenge but not their intersection.
Experience-driven multi-agent methods equip or-
chestrators with cross-episode memory but assume
fixed agent pools with well-known capabilities (He
et al.). Capability discovery and retrieval methods
address selection from large or changing pools but
focus on the retrieval process itself rather than on
learning how to coordinate retrieved agents across
tasks (Guo et al., a). The combination of both has
received limited systematic study.
This work makes four contributions. First, we
propose an adaptive orchestration architecture for
dynamic pools of black-box specialist agents, us-
ing a dual cross-episode memory layer that com-
bines per-agent playbooks with reusable delega-
tion blueprints. Second, we show that the adaptive
system achieves the strongest overall performance
across all evaluated configurations when operating

2 Related Work
This work builds on two lines of research: non-
parametric cross-episode adaptation and capability
discovery. The first studies how agent systems im-
prove across tasks without updating model param-
eters. The second addresses how an orchestrator
identifies suitable agents or tools from large candi-
date pools.
Non-Parametric Cross-Episode Adaptation.In
single-agent settings, a number of systems com-
press past trajectories into reusable knowledge that
is stored persistently in memory. ExpeL (Zhao
et al.) extracts generalized insights by compar-
ing successful and failed attempts and reuses them
with retrieved trajectories at test time. Reason-
ingBank (Ouyang et al.) accomplishes this while
avoiding dependence on ground-truth labels by em-
ploying an LLM judge, which distills successful
traces into strategies and transforms failed traces
into cautionary examples. Agentic Context Engi-
neering (Zhang et al., a) takes a related but dis-
tinct approach by adapting the agent’s prompt it-
self. The prompt is treated as an evolving play-
book of bullets. In later runs, a generator marks
which bullets were useful or misleading; a reflec-
tor extracts lessons from the traces, and a curator
adds delta updates to the playbook. A grow-and-
refine mechanism updates bullets in place, merges
semantically similar entries, and removes harm-
ful bullets. Multi-agent systems shift adaptation
to orchestration, decomposing tasks and routing
work among specialized agents. They have evolved
from static, role-based workflows (Hong et al.) to-
ward in-episode adaptive planning. Magentic-One
embeds planning and recovery into the orchestra-
tor’s control loop via task and progress ledgers,
gaining 31% on GAIA (Fourney et al.). Verified
Multi-Agent Orchestration (Zhang et al., b) adds an
LLM verifier that checks result completeness and
replans when gaps remain, improving complete-
ness at the cost of higher resource use. These sys-
tems achieve in-episode adaptivity but reset all ac-
cumulated state between tasks. A complementary
line learns across episodes. ALMC (He et al.) uses
a Judge Agent to evaluate each task and persists
successful role-phase-workflow configurations in
RAG-backed memory. LEGOMem (Han et al.)
splits successful trajectories into orchestrator- and
agent-level memories retrieved by semantic sim-
ilarity, showing on OfficeBench that orchestrator
memory alone yields 12-13% over stateless base-
lines. Across all of these, the agent set is controlled
internally or fixed at design time; none assumes
an external pool of agents whose capabilities are
unknown or shift during evaluation.
Capability Discovery and Retrieval.As AI
agents are developed across independent frame-
works and platforms, discovering potential col-
laborators and assessing their capabilities at run-
time has become a fundamental challenge (Guo
et al., a). The A2A Protocol addresses capa-
bility announcement through Agent Cards that
declare an agent’s skills and invocation require-
ments. As agent pools grow, curated registries
serve as central catalogs against which clients is-
sue queries based on declared skills or provider
metadata (A2A Project). At larger scale, the In-
ternet of Agents paradigm (Chen et al., a) en-
visions cross-organisational collaboration where
embedding-based retrieval becomes the only prac-
tical selection mechanism. Guo et al. (a) formalize
the resulting problem as agent capability discov-
ery, proposing semantic matching in which agent
descriptions and task requirements are jointly em-
bedded for similarity-based retrieval. This casts
agent selection as a retrieval problem structurally
analogous to tool retrieval, where an agent selects
suitable APIs or functions from a large candidate
pool (Haque et al.). A key limitation shared by
both settings is that static descriptions such as tool
documentation or Agent Cards do not necessar-
ily align with the retrieval queries formulated at
task time. Recent work addresses this gap through
indexing-time enrichment, where a tool’s index
entry is augmented with synthetic content so that
retrieval becomes query-to-query matching. Re-
Invoke (Chen et al., b) generates a diverse set of
hypothetical user queries per tool at indexing time,
against which incoming requests are matched. Be-
yond indexing-time enrichment, ToolMem (Xiao

et al.) stores observed strengths, weaknesses, and
usage experiences of tools in memory, enabling fu-
ture selections to be informed by past performance.
All capability discovery and retrieval approaches
reviewed here share a common limitation. They
either rely on fixed descriptions or build one-shot
enrichments at indexing time. ToolMem advances
this idea with experience-driven memory, but still
its update mechanism is only accumulative, and
does not consider changes in capability.
3 Methodology
This section introduces an adaptive orchestra-
tion system that selects and coordinates specialist
agents from a dynamic agent pool. The orches-
trator is implemented as a dedicated LLM-based
agent operating in a ReAct-style control loop (Yao
et al.). Specialist agents are treated as black boxes
that announce their capabilities at registration time,
but their underlying models, prompts, and tools
remain opaque to the orchestrator. Agents may be
added, removed, or updated between episodes with-
out requiring changes to the orchestrator itself. All
adaptation occurs through in-context learning at the
orchestrator level, backed by an external memory
layer. To isolate the effect of accumulated mem-
ory on task performance, our evaluation separates
a warm-up phase, during which the full curation
cycle is active, from a held-out evaluation phase in
which memory is frozen.
Figure 1 illustrates the overall architecture, in-
cluding its control loop. The full procedure is pro-
vided as pseudocode in Appendix D.
3.1 Agent Registration
Specialists are decoupled from the orchestrator
through an agent registry. Any LLM-driven agent
can enter the pool by providing an Agent Card
containing a natural-language description and a
list of tools, including tool-level descriptions. As
the registry grows, loading all cards into the or-
chestrator’s context becomes impractical. Each
card is therefore indexed with dense text embed-
dings, and only a semantically relevant subset is
retrieved per task. However, retrieval quality de-
pends on how well cards match the orchestrator’s
capability-oriented queries. Following indexing-
time enrichment methods for tool retrieval (Chen
et al., b), each card undergoes a capability profil-
ing step at registration time. A LLM generatesN
synthetic capability queries that the agent could
plausibly address, conditioned on the card content.
Each query is evaluated against the card’s current
retrieval representation, and queries for which the
agent is not retrieved under the configured similar-
ity threshold indicate coverage gaps. For identified
gaps, up to Nb capability-oriented bullets are de-
rived and added to the retrieval index. These bullets
are created as playbook entries (Section 3.2) with
confirmation and contradiction counts initialized to
zero, representing unvalidated hypotheses about the
agent’s capabilities. These can later be confirmed,
contradicted, or pruned by the curation loop.
3.2 Memory Layer
The external memory layer persists two forms of
knowledge across episodes. Agent playbooks store
agent-level evidence about individual specialists,
while delegation blueprints store workflow-level
patterns for composing multiple agents. Both struc-
tures are populated and revised through the post-
episode curation loop described in Section 3.4.
Agent playbooks.For each registered agent,
the system maintains an ACE-inspired play-
book (Zhang et al., a). Unlike ACE’s global play-
book, we keep one playbook per specialist. Each
entry records a rule, its type (capability, limitation,
or strategy), and how often it has been confirmed
versus contradicted. At task time, capability entries
are indexed alongside the Agent Card for retrieval.
The selected agent’s full playbook is then injected
into the orchestrator context to guide delegation.
Entries are pruned once the number of contradic-
tions exceeds a predefined threshold.
Delegation blueprints.A delegation blueprint
abstracts a successful coordination episode into a
reusable pattern. It includes a retrieval-oriented
task summary and a sequential list of delegation
steps. Each step records which agent was assigned
to which sub-task, what input it received, and what
output it produced for downstream use. A short ra-
tionale captures why the overall coordination strat-
egy was chosen.
3.3 Task Execution
At task time, the orchestrator operates a control
loop in which it retrieves context from memory,
optionally formulates a plan, delegates sub-tasks
to specialists, and produces a final answer. Each
of these actions is implemented as an explicit tool
call within the loop.

Retrieval.The retrieval tool constructs the task-
specific context that the orchestrator calls before
making its initial delegation. The orchestrator pro-
vides a task description along with a list of capa-
bility queries that specify the skills likely needed
to complete the task. Each query is scored against
every registered agent through two channels. The
first channel computes a cosine similarity on em-
beddings against the agent’s card text. The second
channel matches the same query against the learned
capability bullets in the playbook store. The agent’s
final score is the maximum of the two channels:
if either the card text or a learned bullet matches
the query, the agent enters the candidate pool. In
parallel, the task description is embedded and com-
pared to stored delegation blueprints as well. If
the best-matching blueprint exceeds a similarity
threshold and all agents it references are currently
registered, it is returned. Agents referenced in the
blueprint that were not surfaced through the ca-
pability queries are added to the candidate pool,
allowing previously successful delegation patterns
to highlight agents whose relevance is not apparent
from the current task description alone.
Planning.Planning is implemented as an op-
tional tool that the orchestrator may invoke for
complex or long-horizon tasks. For simpler tasks
requiring only a few delegations, the orchestrator
may proceed directly to delegation.
Delegation.The delegation tool dispatches a sub-
task to a specialist agent by name and returns its re-
sponse. Instructions are self-contained and include
all context the agent requires, since specialists have
no access to the broader task state. To support mem-
ory updates, each delegation optionally includes a
list of the specific playbook bullets the orchestrator
relied on when composing the instruction. These
bullets serve as citations. They document which
evidence informed the delegation and provide a
direct attribution signal for subsequent curation.
Completion.Once all sub-tasks are resolved, the
completion tool submits the final answer. During
warm-up, a stronger judge LLM assesses the final
response against the task requirements and the exe-
cution trajectory. If the judge rejects the answer, it
returns targeted feedback, and the orchestrator may
revise and resubmit. After one allowed revision at-
tempt, the episode terminates. The judge decision
is retained as the success/failure label for curation.
3.4 Cross-Episode Curation
After each warm-up episode, the system updates
memory from the executed trajectory and the judge
decision. Each trajectory records the task descrip-
tion, delegation instructions, agent responses, and
the playbook bullets cited by the orchestrator. Cu-
ration operates at two levels. At the workflow level,
successful episodes may be distilled into reusable
delegation blueprints. At the agent level, both suc-
cessful and failed episodes may update the play-
books of agents that were actually delegated to. To
prevent redundant curation of near-duplicate expe-
riences, both levels are controlled by a semantic
familiarity criterion. If a sufficiently similar task
has been previously processed, the curation step
is skipped. In contrast, all failed episodes always
trigger agent-level curation, as they may reveal ob-
solete or overstated capabilities.
Workflow-level curation.If the episode is
judged successful and is not semantically familiar
to existing blueprints, the curator distills the trajec-
tory into an idealized delegation sequence. This
sequence contains the minimal chain of agents, in-
puts, and outputs needed to solve the task. Failed
attempts, corrective detours, and redundant delega-
tions are removed so that future executions do not
reproduce accidental or inefficient behavior. The re-
sulting sequence is stored as a delegation blueprint
together with a retrieval-oriented task summary.

Agent-level curation.For each agent that re-
ceived at least one delegation, the curator per-
forms a separate playbook update using only agent-
specific evidence: the instructions sent to that agent,
the agent’s responses, and the playbook bullets
cited by the orchestrator. The curator may con-
firm or contradict cited bullets and may introduce
new capability, limitation, or strategy bullets when
they are supported by observed behavior. Profiling-
derived bullets are treated as unvalidated assump-
tions. If they have never been confirmed, a single
contradiction removes them. Bullets derived from
runtime observations are pruned only after contra-
dictions exceed the harm threshold τ. When an
agent’s playbook exceeds the size limit, semanti-
cally redundant bullets are consolidated to keep the
memory compact.
4 Experiments
The evaluation tests whether cross-episode mem-
ory improves orchestration and remains robust over
a dynamic pool of agents. The design of the exper-
iments is presented first, followed by the results.
4.1 Experimental Setting
Benchmark.We evaluate on OfficeBench (Wang
et al.), an office-automation benchmark of 300
tasks across three difficulty tiers. Each task re-
quires a multi-step workflow over several office
applications in an environment that marks the task
as solved when it reaches the designated target
state. We construct three independent splits by
shuffling the tasks within each tier using different
fixed seeds, then partitioning them into a memory-
building warm-up phase and a separate evaluation
phase, in a 40/60 ratio. Memory is formed from
the warm-up episodes of each split and is assessed
only on the held-out tasks. Warm-up episodes are
not included in any reported metrics. Final results
are obtained by averaging across the three splits.
Agent pool.The pool combines 8 task-relevant
OfficeBench agents with 42 synthetic distractors
whose descriptions are semantically close to the
real agents, creating realistic retrieval competition
(Appendix A). All agents, including distractors,
undergo registration-time profiling to ensure that
their capability bullets compete for retrieval on
equal terms.

agent playbooks and delegation blueprints are fixed

4.2 Results and Discussion
The following analysis evaluates the adaptive sys-
tem across three dimensions: end-to-end task suc-
cess, the individual contributions of playbooks and
blueprints, the pipeline stage at which failures oc-
cur, and robustness to changes in the agent pool.
4.2.1 End-to-End Performance
Table 2 reports end-to-end results for all configura-
tions across both Agent Card settings.
Under rich Agent Cards, cross-episode mem-
ory matches BL-Upper while using fewer turns.
The adaptive system achieves 41.2% overall, which
is well above the stateless BL-Lower and within
range of BL-Upper, but with 46% fewer turns per
task. It matches or outperforms BL-Upper on Tier
1 and Tier 2, but falls behind on Tier 3, where
delegation chains are longer and early mistakes
can no longer be identified and corrected with-
out the in-episode judge.Under sparse Agent
Cards, cross-episode memory outperforms the
BL-Upper.Shortening the descriptions degrades
both baselines, whereas the adaptive system im-
proves to 47.4%, exceeding even the rich-card BL-
Upper. Its distractor-delegation rate stays low while
the baselines’ rates roughly double, indicating that
memory influences agent selection. The reason for
this improvement is interpreted in the next section.
4.2.2 Component Contributions
The two memory components matter in different
ways depending on how informative the Agent
Cards are (Table 2). When cards already describe
an agent’s capabilities in detail (rich cards), adding
agent-level playbooks brings only small gains over
using workflow blueprints alone. In this setting,
playbooks often repeat what is already in the card
and can even hurt: the extra evidence increases
the amount of generic agent information in con-
text, which makes the orchestrator more likely to
pick the wrong agent (Section 4.2.3). When cards
are brief (sparse cards), both components are ben-
eficial, and the full system outperforms Blueprint-
only, demonstrating that they complement each
other. Blueprints provide task-level workflow guid-
ance that cards typically do not include. Since we
retrieve only the single most relevant workflow per
task, this guidance is inexpensive in context. Play-
books offer agent-specific evidence. This evidence
scales with the number of agents retrieved, but un-
der sparse cards, it substitutes for missing Agent
Card descriptions.
4.2.3 Retrieval and Error Decomposition
Memory changes orchestration by shifting where
the pipeline fails. Each task outcome is decom-
posed into three failure types: aretrieval miss,
where at least one gold agent never enters the candi-
date set; aselection miss, where all gold agents are
retrieved but the orchestrator delegates elsewhere;
and anexecution failure, where a gold agent is se-
lected but the task still fails. Tables 3 and 4 report
retrieval quality and this decomposition.
Memory improves retrieval but reduces pre-
cision.Recall and AllGold rise sharply under both
card regimes (e.g., recall increases from 0.755 to
0.953 under rich cards). However, precision de-
creases for both the playbook-only and adaptive
systems because learned capability bullets expand
the retrieved candidate set (Table 3).
The use of these recovered agents depends on
the Agent Card.Under rich cards, the bottleneck
shifts from retrieval to selection.Retrieval misses
fall from 39.3% to 9.0%, but selection misses rise
from 6.1% to 22.9%. The gold agents are now
surfaced but are no longer chosen reliably.
This is caused by two generalist agents, shell
and llm, whose playbooks expand their retrieval
surface. Therefore, they match many tasks through
broad descriptions. Under the Playbook configu-
ration, shell appears in 63.6% of retrieval calls
and llm in 75.1%, against 12.7% and 5.2% un-
der BL-Lower. Moreover, shell is delegated in
42.0% of episodes where it is not a gold agent, up
from 17.2%. This over-selection coincides with
lower success. Episodes that delegate to shell
or llm succeed in 24.3% of cases against 41.6%
for those that do not, whereas under BL-Lower the
same split shows no gap (28.9% versus 29.1%) (Ap-
pendix C, Table 7). Qualitative inspection of trajec-

5 Conclusion
Cross-episode memory can improve orchestration
in dynamic multi-agent pools without updating
model parameters. On OfficeBench, the mem-
ory layer substantially outperforms a stateless or-
chestrator, matches BL-Upper under rich Agent
Cards while using fewer orchestrator turns, and
exceeds it under sparse cards. Reusable delega-
tion blueprints drive most of the gain, while agent
playbooks add complementary value mainly when
card descriptions are weak and can become redun-
dant when cards are already detailed. Improved
retrieval alone is not sufficient; under rich cards,
many eliminated retrieval errors reappear as down-
stream selection errors. Therefore, agent-discovery
mechanisms should be judged by end-to-end suc-
cess and pipeline-level error decomposition rather
than by retrieval metrics alone. The dynamic-pool
experiment shows that the memory layer can adapt
online, integrating new specialists and pruning ob-
solete evidence without supervision. 3 The main
open challenge is attribution: outcome-based cura-
3All code is released at https://github.com/mlukei/adaptive-
multi-agent-orchestrator-benchmarks.
tion should reward causal agent contributions rather
than mere co-occurrence in successful trajectories.
Limitations
Several factors limit the generalizability of these
findings. First, the results rely on a single bench-
mark, whose highly regular task structure may ex-
aggerate blueprint effects. These effects may be
weaker on less workflow-like benchmarks. Sec-
ond, the orchestrator uses a relatively small back-
bone model, so the Tier 3 regression might shrink
with a stronger model. Third, the curation signal
comes from an LLM judge rather than environment-
level ground truth. Although a separate analysis
finds 68–81% agreement between the judge and
environment-based evaluation, the judge produces
more false positives than false negatives, allow-
ing failed trajectories to enter the blueprint store.
Finally, the setup is controlled: all agents are syn-
thetic and registered within a benchmark environ-
ment rather than real, independently provided ser-
vices. The results thus reflect a controlled pool, not
an open ecosystem of heterogeneous third-party
agents.

file_transformer.We add file_transformer to study capability shift detection. During
Phase 2, we deliberately remove file-conversion capabilities from excel, word, and pdf agents (e.g.,

system can adapt to environmental capability changes.
env_explorer.We add env_explorer to address observed failure patterns: the generic shell agent
frequently fails at workspace discovery tasks, and the orchestrator often misunderstands task requirements
due to incomplete situational awareness. env_explorer is a reconnaissance specialist that systematically
scans /testbed to enumerate data files, detect email accounts, discover calendar artifacts, and preview
text-based content. By providing early, structured discovery, it reduces exploration errors and clarifies
task context before delegating to downstream agents.
image_creator.We add image_creator to test whether the system learns to shortcut inefficient dele-
gation chains. In test runs, image-creation tasks require multi-agent sequences, where the adaptive system
tends to fail (Tier 3). image_creator consolidates this chain into a single delegation step. We observe
whether the orchestrator’s memory system captures this efficiency gain and prefers image_creator over
the longer chain in Phase 2.

This appendix reproduces all LLM-facing prompts used in the system. Each prompt is presented exactly
as supplied to the model, with template variables shown as{variable}.
In this implementation, the effective prompt seen by the model is the concatenation of three sources:
(i) the system prompt (Sections E.1 and E.3), (ii) the tool-call schema, whose argument descriptions and
docstrings are automatically extracted from the Python function signatures and included in the model’s

E.1 Orchestrator System Prompt
Orchestrator (executor) — system prompt
# Role
You are an orchestrator coordinating stateless specialist agents to solve a task.
You discover agents, delegate work, and synthesize a final answer.
Agents are black boxes: they see only the instruction you send and share no context
with each other.
This system is single-turn with no user in the loop.
You operate in a ReAct loop: reason -> act -> observe -> repeat, until you call
task_complete.
# Workflow
## 1. Discover gather_context
Your first action must always be gather_context. It returns:
- Agents: each with a description, skills, and a Playbook holding learned
capability/limitation/strategy bullets from past episodes.
- Each bullet has an ID (e.g., agent-1) you can cite in delegations.
- Workflow blueprint (if found): a step-by-step template from a similar past task
that succeeded.
- Use it as your plans starting draft.
- Adapt instructions to the current task and deviate as needed.
- Unmatched capabilities: queries where no agents were found.
Call retrieve_context again with different capabilities if you later discover you need
a type of agent you haven’t searched for yet.
## 2. Plan or execute
After discovery, decide based on what you received:
- Blueprint retrieved OR multi-phase task:
- create_plan
- execute steps with delegate + update_step
- Simple task (one or two delegations):
- delegate directly
## 3. Delegate
Every delegation must be self-contained:
- State the operation.
- Pass input data inline.
- Specify output format.
- Include constraints.

Delegation metadata:
- reasoning: 12 sentences explaining why this agent and this instruction.
- Stored for learning; not sent to the agent.
- cited_bullets (optional): comma-separated playbook bullet IDs that motivated this
delegation.
## 4. Finish task_complete
Call task_complete with:
- final_answer: the concrete answer.
- justification: map each deliverable to evidence from delegations.
The judge may reject with structured feedback.
Address the specific feedback and do not just reword.
# Recovery
A STEP_FAILED or inadequate result is not an endpoint. Work through these
strategies:
1. Retry the same agent with a sharper, less ambiguous instruction.
2. Try a different agent for the same sub-task.
3. Reframe the blocker as a capability-discovery problem and call gather_context

4. Re-orient: view_plan to review progress, or create_plan to restructure.
Exhaust multiple strategies before concluding a sub-task cannot be done.

E.3 Verification Gate (Judge)
The judge receives a system prompt followed by a user message containing the task, candidate answer,
and execution trajectory.
Judge — system prompt
You are a mentor evaluating whether your student AI orchestrator correctly completed a
task.
Your role is to push the orchestrator toward success.
Be accurate in your judgment; the orchestrator relies on your feedback to learn and
improve.
You are given the original TASK, the orchestrator’s execution TRAJECTORY, and the
CANDIDATE ANSWER.
## Evaluation Criteria (apply in order)
1. Give-up check
- Is the answer a refusal, deferral, or request for help?
- If yes: reject immediately.
- Every task IS solvable.
2. Requirement coverage
- Extract every concrete requirement from the TASK.
- For each requirement, check: does the answer address it, backed by trajectory
evidence?
- Missing or unaddressed requirements: reject.
3. Factual consistency
- Does the answer match the trajectory evidence?
- Only reject when the answer directly contradicts what the trajectory shows.
- Do NOT reject for missing trajectory details (agents may return more data than
fits in the trajectory summary).
## Rules
- The TASK is ground truth. Judge the ANSWER against the TASK (not the trajectory’s
interpretation of it).
- You are not an execution engine. Trust agent outputs as evidence.
- Ignore minor formatting quirks, tool messages, or intermediate wording
inconsistencies. Focus on substance.
- If the answer satisfies all criteria above, accept it.
## Orchestrator capabilities (for writing recovery feedback)
The orchestrator has access to the following actions. Reference these when writing
actionable recovery feedback on rejection:
- gather_context(capabilities=[...]) -- discover NEW agents
- delegate(agent, instruction) -- send work to a discovered agent
- create_plan / update_step -- create or revise an execution plan
The orchestrator can retry with different agents, rephrase instructions, split tasks
into smaller sub-tasks, or search for agents with different capability descriptions.

### Reflection
Compare what was EXPECTED (from the card description + existing playbook) vs. what
ACTUALLY happened.
Only gaps between expectation and reality are worth recording.
A successful delegation that does exactly what the card describes is confirmation of
existing knowledge and not a new discovery.
### Playbook delta rules
confirmed_ids:
Bullets that were actively relevant AND demonstrably helped this execution.
Do NOT confirm bullets that were merely "not violated".
contradicted_ids:
Bullets that this execution disproves or that gave harmful guidance.
Be strict and actively unlearn incorrect assumptions.
new_bullets:
02 per novel step.
An empty list is the CORRECT output when nothing transferable was learned.
Most executions confirm existing knowledge rather than creating new bullets.
Before proposing any new bullet, it must pass ALL THREE quality gates:
1. Counterfactual gate
If this bullet had existed BEFORE this episode, would it have changed any
delegation decision or instruction wording?
If no: discard.
2. Discriminative gate
Could this bullet plausibly match tasks intended for a DIFFERENT agent in the
system?
If yes: too generic; discard.
3. Additive gate
Does this bullet add information BEYOND what the card description already
communicates?
If the card already implies this capability: discard.
### Section guidelines
- capability (<= 15 words): "Can <specific action>".
Describes a narrow, non-obvious skill.
Write in the vocabulary a future task description would use so embedding similarity
is HIGH for matching tasks and LOW for non-matching tasks.
- limitation (<= 15 words): "Cannot <action/scope>".
A hard boundary that prevents future misrouting.
Most valuable when discovered through a failure or unexpected refusal.
- strategy (<= 35 words): an actionable instruction-writing pattern.
Must reference concrete behaviors observed in this execution.
Must help someone who has never seen the current task.
HARD RULE: This system is single-turn and there is NO user in the loop.
Never reference "the user" in any output.

- limitation: "Cannot <action/scope>" (<= 15 words).
The inverse of a capability a hard boundary.
- strategy: a deep, actionable insight about HOW to work with this agent
effectively (<= 35 words).
Must be grounded in observed behavior from this execution (not speculation).
Quality rules (all sections):
Must help someone who has NEVER seen the current task.
Must reference a concrete command/tool/format/behavior.
Must NOT mention task-specific names, paths, or entities.
Must NOT be replaceable by "give clear instructions".

## Approach (systematic coverage)
1. Read the description and skills carefully.

2. For EACH identified aspect, write at least one query.

## Rules

- some broad ("manage my schedule")
- some narrow ("move the 3 PM meeting to Thursday")
