Abstract— The proliferation of Large Language Models 
(LLMs) driving autonomous agents has introduced significant 
software engineering challenges to enterprise automation, 
particularly concerning the fragility, governance, and long-term 
maintainability of the services (tools) they invoke [3]. Current 
Model Context Protocol (MCP) standards are often basic. They 
lack necessary context, enumerable intents, and discoverability 
features. Consequently, they neglect the critical non-functional 
requirements essential for production-grade agent services [6]. 
This paper introduces the OpenMCPSpec Framework, a novel, 
extensible specification that formally embeds governance 
metadata, service lifecycle policies, and LLM reliability hints 
directly into the service contract [7]. We demonstrate the 
specification's structure through a formal schema and a 
Python-based reference implementation [9]. We propose 
validation metrics—Argument Correctness Improvement (ACI) 
and Compliance Pre-emption Rate (CPR)—to quantify the 
framework's effectiveness in enhancing LLM tool-calling 
reliability and maintaining enterprise compliance [15]. 
Keywords— LLM Agents, Tool Calling, Agentic AI, Artificial 
Intelligence, Specification, Governance, Lifecycle Management, 
Model Context Protocol (MCP), Software Engineering. 
I. INTRODUCTION 
A. Contextualising the Shift to Autonomous LLM Agents 
The integration of Large Language Models (LLMs) into 
autonomous software agents signals a major transition in 
enterprise automation, moving from scripted workflows to 
dynamic, goal-oriented processes. To execute real-world 
tasks—ranging from database lookups and content retrieval to 
complex transactional processing—these agents must interact 
reliably with external software components, which this paper 
refers to as Machine Communicable Processes (MCPs) [9]. 
This agentic paradigm shift requires a rethinking of how 
external services are defined and consumed [1]. LLMs possess 
inherent limitations, notably their knowledge cutoff (which 
fixes their internal knowledge at a specific training date) and 
their inability to directly access real-time, private, or complex 
operational systems. Robust tool-calling mechanisms are 
essential to bridge this gap, often utilising approaches derived 
from Retrieval-Augmented Generation (RAG) paradigms or 
direct, secure API invocation to provide dynamic, relevant 
context. The success of an autonomous agent hinges entirely 
on its ability to accurately select the correct tool, map the 
natural language intent to rigid parameters, and execute the 
service reliably [5]. 
B. The Deficiencies of Current Tool Specification Standards 
The Existing standards, like OpenAPI excels at 
documentation and client SDK generation for human-centric 
applications, but lack native support for conversational 
elements crucial for agent-model interaction [7], such as LLM 
prompt augmentation or explicit data sensitivity flagging. 
The Model Context Protocol (MCP) emerged to 
specifically address the needs of AI agents, providing a 
capability-centric focus where the server self-describes the 
tools it offers. However, basic MCPs typically offer only 
simplified function definitions (name, description, 
parameters). While functional, they remain critically deficient 
[5][15] in addressing essential Non-Functional Requirements 
(NFRs) and contract or specification-driven strategy required 
for enterprise deployment: 
1. Fragility in Tool-Calling: LLMs struggle to translate 
nuanced natural language intents into rigidly defined tool 
parameters without sufficient external context, resulting in 
unreliable tool execution. 
2. Governance Debt: Enterprise requirements for security 
(Role-Based Access Control, RBAC), data sensitivity 
(PII/GDPR), and auditing are generally implemented 
outside the service contract. This decoupling leads to 
"governance debt," where security policy is implemented 
reactively in middleware or custom agent logic, resulting 
in compliance gaps and difficult, inconsistent 
maintenance across the agent mesh. 
3. Lifecycle Management: Service evolution, continuous 
deployment (AgentOps), and version updates frequently 
lead to brittle integrations because agents lack a 
standardised, runtime mechanism for discovering version 
compatibility. 
C. The OpenMCPSpec Solution and Key Contributions 
The OpenMCPSpec framework is proposed as a 
comprehensive schema standard designed to rectify these 
shortcomings by integrating NFRs directly into the service 
contract, thereby elevating Machine Communicable Processes

II. RELATED WORK AND THE AGENT PROTOCOL 
LANDSCAPE 
A. Foundational Work in LLM Reasoning and Tool 
Utilisation 
The development of OpenMCPSpec is anchored in 
foundational research showing that LLMs can overcome 
inherent limitations by leveraging external tools [3]. LLMs 
inherently excel at rapid, intuitive decision-making (akin to 
System 1 thinking) but often lack the depth for complex, 
multi-step logical processes (System 2 reasoning). 
Early work, such as Toolformer [2] , demonstrated that 
language models could be trained in a self-supervised manner 
to decide when to call external APIs (e.g., calculators or 
search engines), what arguments to pass, and how to 
incorporate the results. Building on this, the ReAct [4] 
(Reasoning and Acting) framework synergised internal 
reasoning traces with external actions, significantly improving 
the LLM’s capability to perform complex tasks with higher 
success rates and better efficiency, often requiring only a 
handful of few-shot prompts for guidance. 
Despite these advances, a significant vulnerability persists: 
tool-calling fragility. LLMs, even with advanced reasoning 
frameworks, are susceptible to errors when translating highly 
nuanced user requests—expressed in natural language—into 
the rigid constraints of API parameters. External factors like 
prompt injection attacks, which can trick the LLM into 
specifying internal API keys or triggering unauthorised 
requests, further demonstrate the need for robust defence 
mechanisms beyond the model’s internal safety alignment. 
The integration of structured protocols that provide explicit, 
domain-specific context is necessary to counteract this 
systemic fragility. 
B. The Emerging Model Context Protocol (MCP) Ecosystem 
The Model Context Protocol (MCP) has rapidly become a 
focus area in AI research, aiming to standardise the context 
exchange between AI clients (Hosts) and external tool servers. 
Recent surveys published in 2025 confirm this accelerated 
push toward standardisation [1][12], exploring the 
architecture, state-of-the-art implementations, and future 
challenges of MCPs. 
A crucial challenge in the growing agentic landscape is 
interoperability. Researchers are actively surveying various 
agent communication standards, including MCP, the Agent 
Communication Protocol (ACP), the Agent-to-Agent Protocol 
(A2A), and the Agent Network Protocol (ANP) [10][11][13]. 
While these protocols define how agents communicate with 
each other, MCP focuses specifically on how agents interact 
with external services. 
A key scalability concern for the entire ecosystem is the 
overhead of tool discovery. Providing an LLM with full tool 
definitions for hundreds or thousands of services consumes 
excessive tokens, dramatically increasing latency and cost, a 
recognised problem in high-volume deployments. This 
concern has spurred the development of solutions 
like MCP-Zero, which focuses on active tool discovery to 
efficiently select tools from large candidate pools. 
OpenMCPSpec addresses this architectural challenge by 
making the enumeration section mandatory, ensuring the 
specification structurally supports efficient [9][6], 
token-saving tool discovery methods from the outset, rather 
than relying on the LLM to process a massive initial context 
window. 
C. Protocol Comparative Analysis: Defining the 
OpenMCPSpec Gap 
The problem addressed by OpenMCPSpec is not merely 
descriptive accuracy but achieving production readiness and 
compliance. Traditional software engineering places 
governance and lifecycle management in external 
infrastructure layers (API gateways, monitoring systems). 
OpenMCPSpec integrates these non-functional concerns 
directly into the protocol definition, enforcing policy and 
reliability constraints at the service interface itself.

The rapid proliferation of Agentic AI naturally introduces 
an interoperability challenge, evidenced by the existence of 
multiple communication protocols (MCP, ACP, A2A). 
OpenMCPSpec addresses this by offering a structural superset 
standard. While other protocols ensure communication 
between agents (interoperability), OpenMCPSpec guarantees 
that the agents' interaction with external systems is secure,

regulatory compliance. 
III. THE OPENMCPSPEC FRAMEWORK: CORE 
ARCHITECTURE AND SCHEMA 
A. Specification-Driven Architecture (SDA) for Agent 
Services 
The OpenMCPSpec framework operates on a core 
principle of Specification-Driven Architecture (SDA). SDA 
dictates that the static specification—typically a JSON schema 
file—is the definitive source of truth for all aspects of the 
service, including functionality, governance, and operational 
metadata. This approach eliminates configuration drift, a 
common problem where external configurations (security 
policies, deployment settings) fail to synchronise with the 
service's declared capabilities. 
B. OpenMCPSpec Schema Structure and Requirements 
The OpenMCPSpec schema is meticulously structured into 
eight sections, five of which are mandatory [9], reflecting the 
framework’s priority on machine-readability and governance 
enforcement. The structure ensures that the protocol definition 
caters not only to the functional needs of tool-calling but also 
to the operational needs of large-scale AgentOps deployments.

guides development teams toward comprehensive monitoring 
and dependency management. This prepares the standard for 
scaling beyond initial proof-of-concept deployments, offering 
a framework that explicitly supports continuous iteration & 
high-reliability operations necessary for production 
environments. 
IV . NOVELTY I: DECLARATIVE ENHANCEMENTS FOR LLM 
RELIABILITY 
A. Mitigating Tool-Calling Fragility via NLP Hints 
A fundamental weakness in agent systems is the semantic 
gap between a user’s complex, often ambiguous natural 
language command and the rigid, specific requirements of a 
service API (the tool-calling fragility). Even highly capable 
LLMs often struggle to accurately map these linguistic 
nuances to parameter names or function descriptions, leading 
to execution failures. 
OpenMCPSpec addresses this directly through the novel 
integration of the nlp_hints [7] array within the intent 
metadata. This array allows the service owner—the domain 
expert—to declaratively specify a list of common natural 
language phrases, synonyms, or domain-specific vocabulary 
associated with that intent. 
The agent’s orchestration layer utilises these hints to 
augment the prompt provided to the LLM during tool 
selection. Instead of relying solely on the LLM’s general 
knowledge to infer the correct tool and parameters from a 
basic description, the system injects highly targeted, 
domain-specific semantic context. This process formalizes a 
crucial prompt engineering technique into a machine-readable 
service contract requirement. The declarative nature of this 
mechanism reduces the necessity for the LLM to perform 
extensive contextual reasoning to resolve ambiguity, thereby 
lowering the "inference tax" (computational and token cost)

To quantify the direct benefit of using nlp_hints, the

(ACI) metric. ACI specifically measures the reduction in 
argument hallucination and the resulting gain in tool-calling 
accuracy [6] when OpenMCPSpec is used compared to a basic

isolates the framework’s impact at the most fragile point of the 
tool-calling process: the translation of intent to parameters.

is often more informative than general end-to-end success 
rates in diagnosing LLM orchestration quality.

V . NOVELTY II: CONTRACT-ENFORCED GOVERNANCE AND 
COMPLIANCE PRE-EMPTION 
A. Addressing Governance Debt through Explicit Metadata 
Enterprise systems face substantial pressure to maintain 
compliance with strict regulatory frameworks such as GDPR 
and HIPAA. The conventional architecture, which separates 
governance policies (e.g., RBAC, PII handling, data 
sanitisation) from the service contract, inevitably accumulates 
"governance debt". This separation results in compliance gaps 
and requires constant, complex manual synchronisation across 
disparate systems. 
OpenMCPSpec mandates the embedding of governance 
metadata [15] directly into the service contract, transforming 
security from an implementation detail into a specification 
requirement. Key declarative governance fields include: 
● pii and gdpr_sensitive: Boolean flags within the 
Parameter object that explicitly label inputs or outputs 
containing sensitive data, allowing data owners to dictate 
necessary handling procedures. 
● roles: An array within the intent metadata that defines the 
minimum access level or permission set required to 
invoke the operation. 
This structural integration ensures that every service 
adhering to the specification is inherently self-governed and 
auditable, aligning the technical design with the critical needs 
of regulated environments. 
B. The Mechanism of Compliance Pre-emption 
The most profound contribution to enterprise readiness is 
the enablement of Compliance Pre-emption. Because 
governance rules are machine-readable and mandated in the 
specification, the OpenMCPSpec binding layer gains the 
capability to intercept incoming requests and validate them 
against the defined contract rules before the application’s 
business logic is executed. 
This capability shifts the security boundary. Instead of 
relying on post-execution logging or asynchronous audit 
checks, the system enforces policies proactively. The 
interceptor can perform checks, such as: 
1. Access Control: Verifying the agent's credentials against 
the required roles array. 
2. Data Policy: Blocking requests containing sensitive data 
if the intent definition prohibits PII handling. 
By enforcing policy at the contract layer, the framework 
mitigates significant security risks associated with LLM 
vulnerabilities, such as prompt injection, inducing 
unauthorised data access or internal reconnaissance. This 
provides a robust, standardised defence against malicious or 
accidental policy violations. 
C. Validation Metric: Compliance Pre-emption Rate (CPR) 
The efficacy of this architectural security enhancement is 
quantified by the Compliance Pre-emption Rate (CPR) [6]. 
The CPR measures the system’s success in blocking 
unauthorised or non-compliant calls at the specification layer 
before they reach the core service logic.

referred to as AgentOps, service endpoints are subject to 
constant updates. When a back-end service evolves with 
breaking changes, agents configured using static definitions

OpenMCPSpec addresses this brittleness by making the 
enumeration section mandatory. This section is a lightweight 
summary of available intents, providing crucial 
machine-readable information necessary for dynamic 
discovery. Crucially, the enumeration endpoint contains a 
versioning object with a compatibility field (e.g., >= 0.1). 
This architectural constraint transforms service version 
negotiation from a reliance on static configuration files to a 
robust, runtime negotiation between the agent and the MCP 
server. 
To prevent context window exhaustion with massive 
toolsets, the mandatory enumeration section enables tiered 
discovery. Agents first query a lightweight manifest to filter 
capabilities, subsequently fetching detailed parameter schemas 
only for explicitly required intents. 
B. Supporting the Agentic AI Mesh 
The ability to perform dynamic compatibility checks is 
vital for managing fluid, evolving architectures. An agent 
operating within a mesh of interdependent services can query 
the MCP server's enumeration endpoint and dynamically filter 
the available capabilities based on its known version 
requirements. 
This mechanism grants the agent significant autonomy. If 
an agent requires protocol version v0.2 but the server only 
advertises compatibility up to v0.1, the agent can gracefully 
handle the mismatch—potentially performing a controlled 
downgrade to a compatible older intent version or flagging the 
deprecation without human intervention. 
The overall effect of the mandatory enumeration and 
compatibility fields is to transform the MCP server from a 
static API definition into a dynamic service catalogue [8][9]. 
The server continuously publishes its operational state, 
required version parameters, and change history. This is 
fundamental for having stability & scaling in production 
where tool availability & specifications are fluid, subject to CI 
& delivery cycles [14].

B. OpenMCPSpec Roadmap 
The current schema provides a foundational structure; 
however, the roadmap includes several extensions necessary 
for achieving full industrial maturity. The planned evolution 
signals a transition from merely defining a protocol to building 
a complete platform that supports the entire Software 
Development Lifecycle (SDLC) for agent services. 
● Advanced Parameter Constraints: Future iterations will 
expand the Parameter definitions to include robust JSON 
Schema validation keywords. 
● Standardised Errors: A critical area for improvement is 
defining richer, standardised error handling schemas and a 
catalogue of error codes. 
● Testing Tooling Integration: The optional testing section 
will be integrated with tool generators designed to 
automatically create a test harness. 
● Community Standard: The long-term objective involves 
transitioning the schema toward a community-driven 
standard. 
IX. CONCLUSION 
OpenMCPSpec introduces a necessary evolution in Model 
Context Protocols by fundamentally changing how 
non-functional requirements are integrated into the service 
definition. By mandating declarative governance metadata 
(roles, pii), explicit reliability hints (nlp_hints), and dynamic 
lifecycle controls (compatibility), the framework addresses the 
systemic challenges of fragility, governance debt, and 
integration brittleness that currently hamper the deployment of 
production-grade LLM agent systems. 
The proposed architectural solutions—Declarative 
Reliability, Compliance Pre-emption, and Dynamic Lifecycle 
Management—are not merely theoretical constructs but 
provide quantifiable, structural benefits. These benefits can be 
empirically measured using the defined Argument Correctness
