A Survey for LLM Agent Trajectory Analysis:
From Failure Attribution to Enhancement
Junjie Wang, Y awen Wang, Mengzhuo Chen, Xiaofei Xie, Chunyang Chen,
Fangwen Mu, Zhe Liu, Qing Wang
Abstract—Large language model (LLM) agents have emerged as a transformative software paradigm, enabling autonomous task
execution through natural language reasoning, multi-agent collaboration, and tool integration. However, their non-deterministic decision-
making and complex interaction patterns introduce unprecedented challenges for failure diagnosis and system improvement. Unlike
traditional software, where failures often manifest as code defects, agent failures are embedded in lengthy, language-heavy execution
trajectories that include natural language reasoning, obscuring root causes and complicating repair. This survey provides a systematic
review of the burgeoning field of trajectory analysis for failure attribution and system enhancement in LLM agents. We collect 55 papers
published between early 2025 and April 2026, spanning software engineering, artificial intelligence, and human-computer interaction.
We organize the literature along five key dimensions: failure taxonomy, failure attribution, system enhancement and optimization,
trajectory monitoring and analysis tools, as well as datasets and benchmarks. Our analysis reveals that while the field has progressed
rapidly from simple LLM prompting to causal inference, fine-tuned tracer models, and dynamic intervention, the step-level attribution
accuracy remains limited, and benchmark diversity is still a bottleneck. We identify four complementary taxonomic perspectives, four
methodological paradigms for attribution, and three families of enhancement strategies. We also critically assess existing benchmarks,
highlighting a recent shift toward full observability and unrecoverable failure annotation. This survey serves as both a structured overview
for current research and a strategic guide for advancing robust, efficient, and self-improving agent ecosystems. We further call upon
the software engineering community to engage more deeply with this emerging class of software, bringing expertise in fault localization,
program repair, and empirical methods to bear on the unique challenges posed by LLM agents.
Index Terms—LLM Agent, Failure Attribution, Trajectory Analysis, Agent Operations, AgentOps, Quality Assurance

1 INTRODUCTION
With the advancement of large language models (LLMs), we
are witnessing a fundamental transformation in the nature
of software itself. As Andrej Karpathy conceptualized in
his “Software 3.0” framework [1], software is evolving from
deterministic, manually coded programs (Software 1.0) and
neural network weights (Software 2.0) toward a new era
where natural language becomes the primary programming
interface and LLMs function as the core reasoning engine.
In this new paradigm, prompts effectively act as programs,
and systems are built around LLM agents that can reason,
plan, and execute tasks autonomously.
On the other hand, software failures are an inevitable
aspect of any software product. Consequently, within soft-
ware engineering research community, failure localization
and repair to improve software quality are critical and
highly active areas [2]–[5]. This holds equally true for LLM
agents, where users frequently encounter issues such as
unexpected execution breakdown and outputs that deviate
from expectations [6]–[10]. Similar to traditional software,
repairing these failures to restore correct system behavior

requires a non-trivial process of failure attribution, root
cause identification, and subsequent fix derivation. For
LLM agents, this process is even more challenging.
Unlike traditional software, where business logic is
explicitly encoded in control flow and data structures, the
behavior of an LLM agent is largely determined at runtime
through model inference, guided by system prompts and
inter-agent orchestration. Consequently, failures in such
systems are not easily traceable to specific code locations;
instead, they manifest in the execution trajectories, i.e.,
rich and unstructured logs that capture natural language
reasoning, multi-step communications, and tool invocations
[11], [12]. Moreover, traditional debugging techniques such
as breakpoint inspection [13] or deterministic replay [14]
are often inapplicable due to the language-heavy nature
of LLM outputs. Thus,trajectory analysisbecomes the
primary means for failure diagnosis, attribution, and repair
of LLM agents.
In classical software engineering, similar practices fall
under the umbrella of log analysis, which has long been
employed for system diagnostics [15]–[18]. However, the
language-heavy, reasoning-driven, and context-dependent
nature of agent trajectories introduces new complexities that
challenge traditional log analysis techniques.
First, the inadequacy of structured log analysis for
language-heavy, reasoningdriven trajectories.Traditional
logs are structured and deterministic, enabling techniques
like parsing and anomaly detection [18], [19]. Agent
trajectories, by contrast, are typically recorded in structured

reasoning, inter-agent communication, and tool-related
messages, are largely expressed in natural language,
vary across runs, and may include hallucinated or
redundant steps. This makes the techniques developed
for conventional logs substantially more brittle in agent
settings.
Second, the inability of external observation to capture
internal reasoning.Traditional analysis infers faults from
external events (e.g., error codes, performance metrics) [20].
Agent failures originate in internal decision processes, re-
quiring techniques that can reconstruct why an agent acted

Third, the mismatch between code-level fixes and
system-level repairs.Fault localization in traditional
software pinpoints code lines for patching [21]. Agent
failures can stem from prompts, workflows, or configura-
tions, where fixes are system-wide. Ineffective localization
techniques would offer little guidance for such high-level
remediation.
Fourth, the gap between ensuring stability and opti-
mizing capability.Log analysis traditionally focuses on cor-
rectness and efficiency. For agents operating in open-ended
environments, the goal extends to improving performance
in unforeseen scenarios, a shift from ensuring system sta-
bility to capability assessment that current methods cannot
fully support.
Given that established techniques for failure localization,
repair, and log analysis in traditional software can not be
directly applicable to LLM agents, a new stream of research
has emerged in recent years. This body of work focuses on
failure attribution and repair for LLM agents, leveraging
trajectory analysis to enable deep understanding and sys-
tematic optimization. In this work, we present a systematic
survey of this burgeoning field, i.e., trajectory analysis for
failure attribution and system enhancement in LLM agents.
Research in this direction only began to emerge in
2025, yet within the short span of 16 months from early
2025 to the present, we have already collected 55 relevant
papers. This rapid growth indicates the field has garnered
significant attention. These papers are published across
conferences in software engineering, artificial intelligence,
human-computer interaction, and others, reflecting broad,
interdisciplinary interest in the challenges of LLM agent
failure analysis. Among these collected studies,failure
attributionandsystem enhancement and optimization
constitute the core technical pursuits for diagnosing
and improving LLM agents. The other three,failure
taxonomy, relateddatasets and benchmarks,trajectory
monitoring and analysis toolsprovide essential support. As
demonstrated in Figure 1, we identify four complementary
taxonomic perspectives, four methodological paradigms for
attribution, and three families of enhancement strategies.
Our analysis also reveals that while the field has progressed
rapidly from simple LLM prompting to causal inference,
fine-tuned tracer models, and dynamic intervention,
the step-level attribution accuracy remains limited,
and benchmark diversity is still a bottleneck. Beyond
summarizing existing work, this survey identifies critical
gaps and future directions.
This survey thus serves not only as a structured
overview of current research but also as a strategic guide
for advancing the reliability and efficiency of LLM agents.
This survey also complements the emerging AgentOps [67]
discipline by focusing on its trajectory-centered diagnostic
and improvement foundations. While much of the existing
work has originated in the AI community, we hope this
survey serves as a clear call for increased engagement from
software engineering researchers, who bring deep expertise
in fault localization, program repair, and empirical methods
to bear on this emerging class of software. Furthermore,
by grounding diagnosis in trajectory analysis and linking
it to systemic improvement, this field moves closer to
realizing robust, self-improving agent ecosystems capable
of operating reliably in real-world environments.
2 BACKGROUND
2.1 Execution and Trajectory of LLM Agents
We consider an LLM agentMcomposed of a finite set of
agentsA={a 1,a 2,...,a N}that collaboratively perform
a taskτ. The system executes in discrete steps. At each
step, a single agent is selected to act, possibly through
a dispatcher, router, or planning component that is part
of the system. At stept, the acting agent is selected as
a(t)=g(h t−1), whereg(⋅)represents the system-level
agent selection mechanism andh t−1 denotes the system
context at stept−1, summarizing the execution history.
The selected agent receives an inputx t =ϕ(h t−1),and
produces an outputy t =π a(t)(xt),whereπ a(t) denotes the
policy of agenta(t). The system context is then updated
ash t =u(h t−1,a(t),x t,y t).The execution terminates after
Tsteps, producing an execution traceT=⟨s 1,s 2,...,s T⟩.
Each execution steps t is associated with a structured
observable recordo t = (step idt,agent idt, a(t), xt, yt, ).

low; for a more comprehensive illustration, readers may re-
fer to benchmark studies like [11], [46].

2.2 Failure Attribution and Enhancement
Given a completed execution traceT, the system produces
a task outcome. We define a task outcome function
Ω(T)∈{0,1},whereΩ(T)=1indicates successful
task completion andΩ(T)=0indicates failure. Failure
attribution aims to identify the agent and the execution
step responsible for a task failure based on observable
execution traces. We define failure attribution at two
levels.Step-level attribution.LetT ≤t denote the prefix
of the execution trace up to stept. We define the set
of feasible continuations fromT ≤t under systemM
asC(T ≤t)={T ′ ∣T ′ is a valid continuation fromT ≤t}.
Failure is said to become inevitable at steptif all feasible
continuations result in failure:∀T ′ ∈C(T ≤t),Ω(T ≤t⊕T ′)=0.
The failure step is defined as the earliest inevitable step
t∗ =min{t∈{1,...,T} ∣∀T ′ ∈C(T ≤t),Ω(T ≤t⊕T ′)=0}.
Agent-level attribution.Given an execution traceTand
its failure stept ∗, agent-level attribution identifies the
agent whose action at the failure step gives rise to the task
failure. Formally, the failure-responsible agent is defined
asa ∗ =arg max a∈A I[∃s t∗ ∈Ts.t.a(t ∗)=a ],wherea(t ∗)
denotes the agent selected by the system to act at stept ∗ in
the execution traceT.
Given an agentMand a performance objectiveJ(M)
that quantifies its overall capability, such as task success
rate, execution efficiency, or robustness in uncertain envi-
ronments, system enhancement and optimization refers to
the process of systematically transformingMinto an im-
proved systemM′ by modifying its constituent components
(e.g., the agent policiesπ a, the selection mechanismg(⋅), the
context-update functionu(⋅), or the input-formation func-
tionϕ(⋅)). The goal is to maximize the objectiveJ(M ′)sub-
ject to constraints on allowable modifications, often guided
by insights derived from the analysis of execution traces
T1,T 2,...produced by the original system.
Note that,the above formalization is intended mainly
as a conceptual scaffold for this survey rather than a com-
prehensive model of all LLM agents. It adopts a simplified
sequential view of execution because this matches the dom-
inant form of systems studied in the current literature.

Moreover, our notion of the failure step is role-aware and
recoverability-aware, rather than purely based on chrono-
logical counterfactual precedence, following common prac-
tice [26], [46]. In multi-agent workflows, earlier mistakes
may remain recoverable if later verifier or supervisory com-
ponents are explicitly responsible for detecting and correct-
ing them. We therefore attribute failure to the point where a
designated recovery opportunity was still available but not
taken, i.e., where failure became effectively inevitable within
the systems architecture.
2.3 Demonstration of LLM Agent Trajectory Analysis
Figure 2 demonstrates an example LLM Agent trajectory,
related failure attribution and enhancement.
The task is to split the last three Amazon orders among
the user and three roommates, then create one Venmo
payment request per roommate. The failure occurs atstep
S4, where the agent attempts to call the Venmo API to
create payment requests. The root cause is that the agent
omits the required user email argument when invoking
venmo.create payment request, causing an exception
that is silently swallowed. To fix this, an enhancement
prompt is added: before calling any state-changing API,
the agent must inspect the exact API documentation, read
the documented parameter list, explicitly identify every
required parameter, and provide all of them explicitly. This
ensures that the required user email argument is no longer
missed.
Note that this is a highly simplified example intended
only to help readers intuitively understand the concept; real-
world scenarios are considerably more complex.
3 PAPERSELECTION ANDREVIEWSCHEMA
3.1 Paper Collection Methodology
To ensure comprehensive coverage of relevant literature,
we employed both automated search (across academic
databases) and manual search (within major software
engineering and artificial intelligence venues). Our search
period spans from January 2023 to February 2026, with a
supplementary search conducted for recent publications
from March 2026 to April 2026. The paper collection process
is demonstrated in Figure 3.
3.1.1 Automated and Manual Search
To capture research from diverse subfields, we performed
an extensive search across four major scientific databases:
ACM Digital Library, IEEE Xplore, arXiv, and DBLP .
We initially searched for papers whose titles contained
keywords related to LLM agents and trajectory analysis
(listed below) in the first three databases. For DBLP , we
added keywords related to failure analysis and debugging
to filter out irrelevant studies, as relying solely on
agent-related keywords would yield an excessively large
candidate set. While using two keyword sets for DBLP may
omit some studies, we consider this a feasible strategy since
many relevant papers from this database are also indexed
in the other three databases.
●Keywords related to both LLM agents and trajectory
analysis:agent trajectoryORLLM agentORmulti-agent
systemORagent failureORagent traceORagent debug-
gingORagent monitoringORagent interactionORagent
coordinationORagent workflow.
●Keywords related to failure analysis and debugging:
failure attributionORerror localizationORroot cause anal-
ysisORdebuggingORfault diagnosisORtrajectory visu-
alizationORagent observabilityORsystem enhancement.
We further filtered papers based on their content, re-
taining only those that mention “LLM”, “language model”,
“agent trajectory”, or specific LLM names. This step helps
eliminate studies not involving neural or generative agents.
To complement automated searches and reduce omission
risk, we conducted a manual search within the proceedings
of top-tier software engineering conferences and journals, as
well as the major artificial intelligence venues considering
interdisciplinary nature of LLM agent research.
More than that, after completing the searches and qual-
ity assessment, we performed backward snowballing by re-
viewing the references of collected papers.
3.1.2 Inclusion and Exclusion Criteria
Our search strategy was intentionally broad to maximize
initial coverage. To ensure relevance, we defined the fol-
lowing inclusion and exclusion criteria, applied manually
to each paper.
Inclusion Criteria:
●The paper proposes or evaluates methods for failure
attribution, trajectory analysis, or debugging of LLM
agents.
●The paper introduces datasets, benchmarks, or tools for
analyzing or visualizing agent trajectories.
●The paper presents empirical studies or frameworks
for enhancing or optimizing LLM agents via trajectory
analysis.
●The paper focuses on multi-agent coordination, inter-
action protocols, or system-level observability in LLM
agent contexts.
Exclusion Criteria:
●The paper does not involve LLM agents (e.g., focuses
solely on traditional software or single-model applica-
tions)1.
●The paper uses non-generative or encoder-only models
(e.g., BERT) without agentic reasoning or interaction.
●The paper only mentions LLM agents tangentially (e.g.,
in future work or background sections).
●The paper focuses on testing LLM performance (e.g.,
fairness, security) rather than agent behavior.
●The paper is a tool evaluation without proposing ana-
lytical or diagnostic methods for agent trajectories.
Two authors independently reviewed each paper against
these criteria. Disagreements were resolved by a third au-
thor.
1. This survey focuses on “LLM agents” in which the model partici-
pates in multi-step task execution with at least some combination of the
following properties: 1) iterative reasoning or planning; 2) interaction
with tools, environment, or external memory; 3) multi-step state evolu-
tion across a trajectory; 4) collaboration/orchestration among multiple
components or agents. By contrast, we exclude “single-turn or purely
generative single-model applications” where the LLM produces an
answer without trajectory-like execution or agentic interaction.

3.1.3 Quality Assessment
We further applied a quality assessment checklist to exclude
low-quality studies. Specifically, two authors independently
assessed the quality of the candidate papers using the 10-
item checklist. They have research experience in software
engineering, LLM agents, and empirical literature analysis.
For each paper, the annotators first scored the items inde-
pendently as yes (1), partial (0.5), or no (0). They then com-
pared their assessments and discussed discrepancies. If con-
sensus could not be reached directly, the disagreement was
resolved through discussion with an additional author act-
ing as an adjudicator.
●Is the research goal clearly stated and relevant to LLM
agent trajectory analysis or failure diagnosis?
●Is the proposed technique or framework clearly defined
and repeatable?
●Does the paper make a clear contribution to the under-
standing or improvement of LLM agents?
●Are the LLM models used explicitly described?
●Is the method of applying LLMs for analysis or attribu-
tion explained?
●Is there a clear validation methodology (e.g., datasets,
benchmarks, case studies)?
●Are the selected evaluation subjects appropriate for the
research goals?
●Are baselines or control methods included to demon-
strate effectiveness?
●Are the evaluation metrics relevant to the stated objec-
tives?
●Are the results clearly presented and aligned with the
research goals?
If a question is not applicable to a given paper, we ex-
clude it from that paper’s assessment, and normalize the
final quality score over the remaining applicable questions.
This avoids unfairly penalizing papers whose methodolog-
ical design does not involve certain aspects. For example,
if a paper has two questions deemed not applicable, the
maximum achievable score becomes 8 instead of 10. The
final quality score is then normalized to a 10-point scale
(e.g., an actual score of 8 out of 8 would be recorded as
10 out of 10), ensuring fair comparison across papers with
different sets of applicable criteria. Finally, papers with a
total score below 8 were excluded.
3.2 Collection Results
Our initial search retrieved 1,652 papers. After automated
filtering, manual screening, application of inclusion/exclu-
sion criteria, and quality assessment, we retained 55 pa-
pers relevant to LLM agent trajectory analysis for failure
attribution and system enhancement. This significant reduc-
tion stems from our deliberately broad initial keyword de-
sign, i.e., intended to capture interdisciplinary work, fol-
lowed by rigorous filtering that removed papers about tan-
gential mentions of agents without substantive contribution
to trajectory analysis. Table 1 provides a detailed breakdown
of the collected papers.

4 LLM AGENTTRAJECTORYANALYSIS
We group the related studies in this field along five key
dimensions, as illustrated in Figure 6. The research on qual-
ity assurance about LLM agents is organized around two
central goals: finding out why failures happen and using
that knowledge to build better systems. In our view, the core
challenges of the field arefailure attribution(pinpointing
the location and root cause of the failure within complex
interactions) andsystem enhancement and optimization
(applying those insights to fix and improve agents). To sup-
port this core, three areas provide the necessary foundation.
First,failure taxonomiesoffer a common schema to classify
failures, which is essential for analyzing and discussing fail-
ures systematically. Second,trajectory monitoring and anal-
ysis toolssupply tools needed to observe agent behavior,
enabling both automated analysis and human-in-the-loop
debugging. Finally, specializeddatasets and benchmarks
are vital for fairly evaluating and comparing different at-
tribution and enhancement methods, ensuring progress is
measurable and solid.
Figure 7 illustrates the distribution of research
dimensions among the 55 surveyed studies. The data
reveals a clear concentration of effort onfailure attribution,
which appears in 22 papers, underscoring its role as the
central technical challenge in diagnosing LLM agents.
Following that,enhancementaccounts for 14 papers, while
benchmarkandtaxonomyeach account for 10 and 9
papers, reflecting a balanced focus on both understanding
failure modes and improving system performance. There
are 7 papers mainly related with the empirical studies about
trajectories of such systems, and we put them into others.

4.1 Failure Taxonomy
As mentioned earlier, as an emerging form of software,
LLM agents exhibit failures whose manifestations and
characteristics are substantially different from those of
traditional software. Consequently, several researchers
have sought to analyze why or how these systems fail.
They examine the trajectories generated by these systems
to diagnose the root causes of failures. Moving beyond
individual failure instances, they also develop a structured
understanding of why or how failures occur. This effort
has led to the creation of many failure taxonomies for such
systems.
4.1.1 Categorizing Taxonomies
Researchers have proposed a variety of taxonomies to struc-
ture the understanding of failures in LLM agents. These
efforts, while diverse in their specific categorizations, can
be synthesized by examining the views through which they
analyze system failures. To provide a more streamlined com-
parative perspective, we organize existing work around four
guiding questions: (1)wherein the task pipeline did the
failure occur? (2)whatcore capability of the agent failed? (3)
who(which agent or system component) is responsible? and
(4)whydid the failure arise under the given environment
context?

(1) Taxonomies Organized by Task-Execution Phase
(WHERE).This perspective dissects agent failures by
following the natural, sequential pipeline of a task. It
asks the fundamental debugging question: “Where in
the task pipeline did it go wrong?” This perspective is
highly intuitive for developers and aligns with operational
monitoring, as it directly maps failures to observable phases
in a task trajectory.
For example, Lu et al. [22] and Guo et al. [23] both adopt
this phase-based lens to classify failures. Lu et al. develop a
three-tier taxonomy of failure causes, highlighting planning
errors, task execution issues, and incorrect response gen-
eration. Specifically, task planning related failures include
improper task decomposition, failed self-refinement lead-
ing to infinite loops, and unrealistic planning that exceeds
agent capabilities. Task execution failures include failure to
exploit external tools, production of flawed code, and im-
proper environmental setup. Response generation phase is
prone to formatting issues, context window restraint caus-
ing information loss, and exceeding the maximum interac-
tion rounds.
(2) Taxonomies Organized by Agent Capability
Module (WHAT).Moving from external workflow to
internal cognition, this perspective focuses on the agent’s
core functional components. It investigates: “What core
cognitive function of the agent failed?” Taxonomies such as
AgentErrorTaxonomy [24] and TRAIL [25] adopt this view,
organizing failures around modules like memory, reflection,
planning, action, and system execution. This perspective
is essential for research aimed at enhancing specific agent
capabilities and understanding the compositional nature of
agent intelligence.
For example, Zhu et al. [24] introduce the AgentEr-
rorTaxonomy, a modular classification of failure modes
spanning memory, reflection, planning, action, and system-
level operations. Memory failures indicate the errors in
recalling or retrieving information (false recall, omission,
retrieval failure) that distort subsequent reasoning.
Reflection failures are those in monitoring progress or
interpreting outcomes (progress misassessment, outcome
misinterpretation), blocking course correction. Planning
failures include logically unsound or infeasible strategies
(impossible actions, constraint ignorance, incoherent
subgoals) that cascade into missteps. Action failures are
mistakes in executing operations (malformed outputs,
incorrect parameters, missing arguments) that are visible
but often mask upstream errors. System-level failures
are those outside reasoning, such as tool crashes, API
mismatches, or exceeding step limits, highlighting system
robustness issues.
(3) Taxonomies Organized by System & Interaction
(WHO).This perspective scales the analysis to the level of
agent systems and their ecosystem. It addresses failures
emergent from interactions, asking: “Who is responsible -
the agent, the coordination, or the platform?” Frameworks
like MAST [28], AgentFail [27] and AgentRx [26] employ
this perspective, with top-level categories like specification
issues, inter-agent misalignment, and platform-level
failures. This view is critical for diagnosing the complex,
often non-deterministic failures that arise in multi-agent
collaboration, where the problem lies not in any single
node’s reasoning but in the communication, shared
understanding, or infrastructure governing their collective
behavior.
For example, Cemri et al. [28] present MAST (Multi-
Agent System Failure Taxonomy), and identify 14
unique failure modes, organized into 3 categories:
specification issues, inter-agent misalignment, and task
verification. Specifically, specification failures originate
from system design decisions, and poor or ambiguous
prompt specifications. Inter-agent misalignment failures
arise from breakdowns in inter-agent interaction and
coordination during execution. Task verification failures
involve inadequate verification processes that fail to detect
or correct errors, or premature termination of tasks.
(4) Taxonomies Organized by Environment Context
(WHY).This perspective focuses on failure modes shaped
by the environmental conditions under which the agent
operates. It asks: “Why do failures arise under a particular
environment context?” Such taxonomies are useful when
properties of the surrounding environment, such as limited
observability, stateful navigation, or turn/token constraints,
strongly influence agent behavior and failure patterns.
The taxonomy in Aegis-Song [29] is representative of this
perspective. It characterizes how agents fail when interact-
ing with their environments, including exploration failures,
exploitation failures, and resource exhaustion. For example,
exploration failures occur when the agent cannot gather the
critical context required from the environment; exploitation
failures arise when the agent has obtained relevant informa-
tion but fails to use it correctly under environmental con-
straints; and resource exhaustion captures failures induced
by limited turns or token budgets.

4.2 Failure Attribution
Failure attribution is the cornerstone for diagnosing and
improving LLM agents. It aims at systematically determin-
ing which agent is at fault, at which step the critical er-
ror occurred, and why. The central challenge lies in rea-
soning backwards from observed failures within complex,
heterogeneous interaction data (spanning LLM reasoning,
tool calls, and environmental feedback), to infer the internal
logic breakdown and pinpoint the root cause. This task is
particularly difficult because the point where a failure is
observed is often not its origin. Initial errors in planning,
knowledge, or coordination can propagate and transform
through multiple steps of agent reasoning and tool execu-
tion, obscuring their original source. This propagation cre-
ates a significant gap between symptoms and root causes,
demanding more sophisticated, inference-based attribution
techniques.
Current research on failure attribution for LLM agents
can be broadly organized into four categories, reflecting a
progression in analytical depth and intervention intensity.
We begin with pattern analysis-based approaches (Section
4.2.1), which passively mine statistical regularities from
execution traces to localize faults. Building on observational
data, LLM reasoning-based methods (Section 4.2.2) leverage
the innate analytical capabilities of foundation models to
simulate human-like diagnostic reasoning. To overcome
the limitations of general-purpose LLMs, model fine-
tuning-based techniques (Section 4.2.3) train specialized
tracer models on curated failure datasets, aim at achieving
greater efficiency and accuracy. Finally, dynamic runtime-
based approaches (Section 4.2.4) adopt an interventionist
paradigm, actively testing causal hypotheses through
runtime edits and simulations. We introduce each category
in detail in the following subsections.
4.2.1 Pattern Analysis-Based Attribution
As the most observational approach among attribution tech-
niques, pattern analysis-based methods localize faults by
mining recurring signals across numerous execution traces,
relying purely on data-driven statistical analysis without
runtime intervention. This family of techniques has evolved
through three progressive stages: from coarse suspicious-
ness scoring, to stage-level accountability tracing, and fi-
nally to structured error representation with causal aware-
ness.
The earliest works adapted classic fault localization ideas
from traditional SE to the agent setting. FAMAS [30] pio-
neered this technical line by adapting spectrum-based fault
localization. It systematically replaying trajectories to com-
pute a “suspiciousness” score for each agent action based
on its frequency in failing versus successful runs, with a tai-
lored formula integrating both agent-level and action-level
activation patterns. Barrak et al. [31] approached the same
goal through a Planner→Executor→Critic pipeline, where
blame propagates forward until the earliest unrepaired error
is pinpointed.
Subsequent works shifted focus toward knowledge
reuse and efficiency. CORRECT [32] distills recurring
failures into compact error schemata that are reused for
real-time recognition, decoupling diagnosis from costly
trajectory replay. SDBL [33] addresses the scalability
challenge by narrowing the search space before detailed
localization, drawing on code defect manifestation patterns
to scope potential fault regions.
The most recent works enrich pattern-based attribution
with structured error modeling. AgentEval [23] constructs
a directed acyclic graph (DAG) to explicitly track how root
causes propagate through subsequent steps, moving beyond
point-wise localization to capture error cascades. PROMAS
[34] introduces causal delta representations with a vector
Markov entropy model, pinpointing the exact moment a
trace diverges from successful behavior-effectively combin-
ing pattern matching with causal change detection.
4.2.2 LLM Reasoning-Based Attribution
LLM reasoning-based approaches move from mining
correlations to simulating human-like diagnostic reasoning.
These methods leverage the analytical capabilities of
foundation models to infer root causes from complete
task trajectories through sophisticated prompting and
structured reasoning processes. The evolution within this
category follows a clear trajectory: from naive prompting, to
structured reasoning pipelines with consensus mechanisms,
to explicit causal modeling, and finally to hybrid approaches
that augment LLM reasoning with external verification or
memory.
The earliest instantiation of this paradigm used straight-
forward prompting over complete trajectories. The pioneer-
ing Who&When benchmark [11] established this paradigm
by evaluating three basic strategies, i.e., All-at-once, Step-
by-step, and Binary search, demonstrating the feasibility but
also the limited accuracy of using LLMs on this complex
task.
To enhance reliability, subsequent work introduced more
structured reasoning processes. ECHO (Error attribution
through Contextual Hierarchy and Objective consensus
analysis) [35] develops a hierarchical context representation
of the entire interaction trace, provides independent
objective analyses across these contexts and cross-validating
the findings via consensus voting. RAFFLES [36] adopts
an iterative, multi-component pipeline where a central
Judge systematically investigates faults while specialized
Evaluators assess not only system components but also
the quality of the Judge’s own reasoning, creating a
self-correcting diagnostic loop.

hallucination in the diagnostic process itself.
4.2.3 Model Fine-Tuning-Based Attribution
Unlike prompting-based methods, this paradigm focuses
on training specialized models dedicated to the failure
attribution task. The resulting specialized tracer model
learns to efficiently parse complex agent interactions,
recognize error propagation patterns, and localize faults
with improved accuracy and inference efficiency compared
to general-purpose LLM.
AgenTracer [42] established a foundational pipeline for
this direction. It first annotates failed agent trajectories via
counterfactual replay and programmed fault injection, pro-
ducing the curated dataset TracerTraj. Leveraging this re-
source, they develop AgenTracer-8B, a lightweight failure
tracer trained with multi-granular reinforcement learning,
capable of efficiently diagnosing errors in verbose multi-
agent interactions.
GraphTracer [43] moves beyond sequential trajectory
analysis to a structured graph representation. It constructs
Information Dependency Graphs (IDGs) to explicitly
capture how agents reference and build on prior outputs,
and to enable tracing fault propagation along dependency
edges rather than temporal steps. The training data is
produced through graph-aware fault injection, and the
failure tracer also trained guided by graph-structural
rewards.
Subsequently, Aegis-Kong [44] scaled and systematized
this paradigm. It created one of the largest synthetic at-
tribution datasets to date and performed a comprehensive
empirical study, directly comparing the efficacy of three dis-
tinct learning strategies, i.e., supervised fine-tuning, rein-
forcement learning, and contrastive Learning, for training
robust failure attribution models. The results showed that
reinforcement learning and contrastive learning outperform

4.2.4 Dynamic Runtime-Based Attribution
Moving beyond passive log analysis, this group of tech-
niques adopts an active, interventionist approach to attri-
bution. The key design principle is to formulate hypotheses
about the root cause and then test them through targeted
interventions, i.e., systematically testing whether modifying
a hypothesized root cause would have averted the failure.
DoVer [45] is an intervention-driven debugging
framework, which augments hypothesis generation with
active verification through targeted interventions (e.g.,
editing messages, altering plans). AgentDebug [24] applies
a similar idea by assigning fine-grained error types to each
step and module, and then guiding targeted re-rollouts
based on the diagnosed error types.
The paradigm further evolves to tightly integrate LLM
reasoning with dynamic verification. Works like TraceEle-
phant [46] and AgentFail [27] exemplify this by employ-
ing an LLM-based candidate identification step followed by
counterfactual verification.

attribution performance in terms of all investigated tech-

Generally speaking, agent-level accuracy is significantly
higher than step-level accuracy, which is well understood
because identifying the responsible agent is inherently
easier. For algorithm-generated systems, step-level
accuracy tends to be higher than for hand-crafted systems,
likely because algorithm-generated systems follow more
consistent patterns, making it easier to discern underlying
regularities, whereas hand-crafted trajectories tend to
be longer and more variable, increasing the difficulty of
accurate step-level attribution. Furthermore, fine-tuning-
based methods achieve relatively better performance, as
they leverage additional training data that enables the
model to learn the organizational patterns of trajectories
and the failure modes. Additionally, some LLM reasoning-
based approaches, such as CHIEF and A2P , also deliver
competitive results through detailed causal analysis of
trajectories.
In terms of reported accuracy, on the Who&When
benchmark, reported step-level attribution accuracy varies
substantially across techniques, ranging from about 25% [11]
to 52% [39]. Meanwhile, TraceElephant is a more recent
benchmark and has so far been evaluated by relatively
fewer methods; the currently reported step-level accuracy
is about 33% [46]. This indites the step-level attribution
accuracy is still limited. Also note that, the comparability
across studies remains limited due to differences in datasets,
observability settings, and evaluation protocols.
4.3 System Enhancement and Optimization
The ultimate goal of diagnosing failures is to enable
improvement. Once the root cause of a failure is attributed,
the next critical step is to leverage this insight to enhance
the system’s capabilities, reliability, and efficiency. This
section focuses on approaches that utilize trajectory
analysis to drive the enhancement and optimization.
This can be achieved by reshaping the external structure
and environment in which agents operate (Section 4.3.1),
by innovating the internal drivers and mechanisms of
the agents themselves (Section 4.3.2), or by adding a
lightweight layer for process management or supervision at
runtime (Section 4.3.3).
4.3.1 Structural & Workflow Optimization
This paradigm focuses on enhancing overall performance
and robustness by re-designing the collaborative architec-
ture and interactive environment of multi-agent systems
from the outside. Existing works can be organized by the
depth of their intervention, targeting progressively deeper
layers of the system stack.
Environment-level optimizationrepresents the shallow-
est form of intervention, modifying only the conditions un-
der which agents operate without touching their core logic.
Song et al. [29] design Aegis, which enhances environment
observability, offloads common computations, and specu-
lates agentic actions.
Workflow-level optimizationmoves the target inward
to the collaborative graph structure and its associated
configurations. Wang et al. [47] introduce Maestro, a
framework-agnostic optimizer that jointly searches over
graph topologies and agent configurations under explicit
rollout and token budgets, guided by reflective textual
feedback from execution traces. CE-Graph [48] adopts
a diagnosis-driven variant: it first estimates the failure
distribution from counter-examples, identifies dense failure
regions as recurring modes, and then applies targeted,
operator-constrained graph edits. ILWS [49] pushes this
level further by treating system-level instructions as
versioned, editable pseudo-parameters that are evolved
by a reflection engine after each session. Unlike Maestro
and CE-Graph which optimize the graph topology, ILWS
refines the shared guiding principles that govern all agent
behavior, enabling post-hoc self-improvement without
modifying the underlying models.
4.3.2 Agent Internal Optimization
In contrast to modifying external frameworks, this line of
research focuses on optimizing agents’ internal decision-
making logic to enhance their performance. Approaches
can be organized by the granularity of what they modify:
from high-level prompts down to model mechanism and
reusable skills.
Prompt-level optimizationis the least invasive. SCOPE
[50] frames prompt evolution as an online learning problem,
balancing tactical error resolution with strategic principle
refinement. Fangs [69] takes a complementary, attribution-
driven approach: it first identifies which decisions or rea-
soning steps caused a failure, then generates contextaware
guidance to steer future behavior.

4.3.3 Runtime & Supervisory Optimization
The third paradigm instead enhances efficiency and robust-
ness by optimizing the data flow of the execution process or
attaching a lightweight external supervisory layer.
Input-space optimizationreduces noise in the agents
context. AgentDiet [56] removes useless, redundant, or ex-
pired information from trajectories, cutting token cost with-
out altering decision logic.
Behavior-space optimizationinjects external steering
signals during execution. SUPERVISORAGENT [57] uses
an LLMfree adaptive filter to detect critical junctures
and proactively correct errors. Wink [58] prioritizes
low overhead by periodically nudging agents out of
misbehavior, making it suitable for continuous background
monitoring. Lius [54] triggers interventions based on
processcentric metrics (e.g., progress rate, action entropy),
enabling adaptive, goaldriven steering.

4.4 Trajectory Monitoring and Analysis Tools
The observability of an agent system, i.e., enabling the cap-
ture and understanding of its internal states and interac-
tions, is essential for failure diagnosis and system improve-
ment. This section reviews approaches that enhance observ-
ability by making execution traces interpretable, allowing
both automated analysis and human-in-the-loop inspection.
The works in this area can be broadly grouped by their pri-
mary focus: tools for low-level, non-invasive system moni-
toring and passive diagnosis (Section 4.4.1), versus those for
high-level, interactive analysis and active debugging (Sec-
tion 4.4.2).
4.4.1 System-Level Monitoring and Passive Diagnostic
Tools
This category targets at the passive, transparent, and com-
prehensive collection of execution data from agent systems.
The first set of tools focuses on external, non-invasive
instrumentation that observes agent behavior without mod-
ifying application code. AgentSight [59] is an observabil-
ity framework which monitors agents from outside their
application code at stable system interface, which is used
for identifying resource-wasting reasoning loops, revealing
hidden coordination bottlenecks.
Building on passive data collection, another line of work
embeds structured diagnostic analysis directly into the mon-
itoring pipeline. Moshkovich et. al. [60] present the Agen-
tOps automation pipeline, a six-stage process encompassing
behavior observation, metric collection, issue detection, root
cause analysis, optimized recommendations, and runtime
automation.
A third direction prioritizes human interpretability,
building interactive visualizations that make trajectories
accessible to developers. AgentDiagnose [61] provides a
framework for quantitative visualization and diagnose.
It has (i) an evaluation module that quantifies five core
agentic competencies, i.e., backtracking and exploration,
task decomposition, observation reading, self-verification,
and objective quality, and (ii) a visualization module
that highlights trajectory semantics through t-SNE action
embeddings, interactive word clouds, and state-transition
timelines. Similarly, Agent Trajectory Explorer [62] provides
an intuitive interface to support visual inspection and
manual annotation of agent execution trajectories.
4.4.2 Interactive Analysis and Active Debugging Tools
Moving beyond data collection, this category focuses on
building interactive tools that empower developers to ex-
plore and intervene in agent trajectories.
AGDebugger [63] is an interactive debugging tool, which
allows users to reset to previous states and modify past
agent messages, so as to support iterative, hypothesisdriven
debugging. XAgen [64] bridges automated judgment with
human-in-the-loop feedback. It can turn execution traces
into an interactive flowchart for trajectory visualization,
and also allows users to annotate outputs which serves as
feedback for failure attribution and iterative improvement.
DiLLS [65] is designed to reveal and structure the
behaviors of multi-agent systems, and it organizes execution
information into three layers, i.e., overall planning and
execution, action arrangement and outcomes, and logs for
concrete operations.

Beyond research prototypes described in the literature, the
broader ecosystem also includes widely used practitioner-
oriented observability platforms for tracing and analyzing

4.5 Datasets and Benchmarks
Benchmarks and datasets provide foundational support
for research in this field: they serve as objective, unified
evaluation standards for measuring and comparing the
performance of different attribution techniques, and as
sources of high-quality training data for powering data-
driven diagnostic models. Existing studies can be broadly
categorized into two types: evaluation-centric benchmarks
collected from real-world failures, and synthetic, error-
injected datasets designed for both training and evaluation.
4.5.1 Benchmarks from Real-World Failure Collection
These datasets collect naturally occurring failures from ac-
tually deployed agents, thus closely reflecting real-world
application scenarios.
Zhang [11] introduce the Who&When benchmark, the
pioneering benchmark in this field, being utilized by almost
all failure attribution studies. Each failure trajectory is an-
notated with failure-responsible agent, the corresponding
failure step, and some with the reasons for failure in natural
language. AgentRx [26] focuses on the first unrecoverable
failure step, arguing that recoverable steps are less meaning-
ful for attribution. Chen et al. [46] note that existing bench-
marks rely on partial observability (agent outputs only), so
they propose TraceElephant with full execution traces and
reproducible environments. This aligns with real-world de-
veloper facing scenarios where complete traces, rather than
only outputs, are accessible for diagnosis.
Other benchmarks offer finer-grained or multi-
perspective annotations. TRAIL [25] and Agent Error
Benchmark [24] provides finer-grained root cause, to
facilitate the better understanding of the failures. MPBench
[66] introduces multi-perspective attribution by annotating
an ideal action alongside the faulty step and failure reason,
enabling richer diagnostic signals.
Several benchmarks target specific agent types rather
than generic LLM agents. AgentFail [27] focuses on
agentic workflow agents, providing fine-grained, lifecycle-
spanning annotations (precise location, root cause, and
repair strategy), which enables deeper analysis of the
entire failure process beyond simple error detection.
CodeTraceBench [40] focuses on software engineering
agents (SWEAgent, OpenHands, etc.).
4.5.2 Synthetic Datasets via Error Injection
These datasets are constructed by actively injecting errors
into successful trajectories, resulting in precise error local-
ization and annotation. Besides evaluation, they are also
suitable for model training.
Kong et al. [44] construct Aegis, a large dataset of 9,533
trajectories with annotated faulty agents and error modes.
This is achieved using a LLM-based manipulator that
can adaptively inject context-aware errors into successful
execution trajectories. Yu et al. [32] construct CORRECT-
Error, a large-scale collection of over 2,000 multi-agent
trajectories with fine-grained, step-level error annotations.
It is built using a error-injection pipeline guided by
real-world failure distributions, yielding trajectories that
balance controlled coverage with the realism of natural
MAS failures.

agent information is never consumed by any enhancement
method. This may be because such coarse-grained infor-

how to fix it, and therefore offers little actionable guidance
for subsequent repair. Even for faulty step and root cause,
the flow from attribution to enhancement is sparse, with
only a handful of techniques, such as CEGraph [48] and
Fang’s [69], utilizing them.

an execution trace, but does not directly point to which
part of an agent should be modified. Consequently, it can-
not provide targeted guidance for enhancement techniques.

5.2 Guidance for Method Selection
While the previous sections have organized existing tech-
niques along multiple dimensions, practitioners seeking to
apply these methods in real-world scenarios may face high-
level decisions, such as whether the target environment is
production or research, what budget constraints (e.g., to-
ken consumption, training overhead) apply. This subsection
synthesizes the current evidence to try to offer actionable
guidance.
Production vs. research environments. Several ap-
proaches originate from industrial research labs (e.g.,
ECHO [35] from Amazon Web Services, AgentRx [26]
from Microsoft Research). However, their evaluations are
almost exclusively conducted on academic benchmarks
such as Who&When, using agents (e.g., CaptainAgent,
MagneticOne) that may not fully represent real production
deployments.
Nevertheless, we have identified at least two methods
that have been successfully deployed in production and re-
port concrete operational benefits. Wink [58] (from Meta) re-
solves 90% of single-intervention misbehaviors in live A/B
tests, and AgentDiet [56] (ByteDance) reduces token cost by
4060% while maintaining performance in the real codinga-
gent environment Trae Agent.
Budget constraints.we analyze the resource consump-
tion patterns of different attribution techniques based
on data reported in the original papers [39]. 1) LLM
reasoning-based methods (e.g., CHIEF [39], ECHO [35])
incur a moderate token overhead, typically 2-3x compared
to single-pass prompting. 2) The typical pattern-based
methods FAMAS [30] involve repeated replay, leading to
significantly higher token consumption (e.g., 6-8x more
than reasoning-based approaches). 3) Fine-tuning-based
methods (e.g., AgenTracer [42], GraphTracer [42]) can
achieve lower inference cost per trace once deployed,
but require substantial investment for model training. 4)
Dynamic runtime-based methods (e.g., DoVer [45]) typically
incur the highest per-diagnosis cost because they actively
re-execute or intervene in the agent, and also demand
online access to the execution environment. However, they
often achieve the best attribution accuracy (as shown in
Figure 8), as active hypothesis testing can disambiguate
root causes more effectively than passive analysis.
Overall, no single method dominates across all
dimensions. Practitioners should choose based on their
accuracy requirements, budget (one-time vs. per-trace cost),
and whether online intervention is feasible.

we summarize the challenges and opportunities for future
research.
6.1 Improving Attribution Accuracy via Enhanced
Causal Understanding

due to the non-deterministic reasoning and intricate inter-

inspection to the structured understanding of the agent’s in-
ternal decision logic. CHIEF [39], which achieves the highest
performance so far, begin to address this by transforming
flat execution logs into hierarchical causal graphs, explic-
itly modeling data transitions and error propagation. This
demonstrates that formalizing the latent logical and causal

6.2 Rethinking Evaluation for LLM Agent Failure Anal-
ysis
The evaluation of failure attribution techniques must align
with their intended use in debug and repair. We identify
three key dimensions where current practices fall short.
6.2.1 From Accuracy to Utility: The Need for Repair-Driven
Metrics
As shown in Section 5.1, failure attribution techniques
predominantly output responsible agents, faulty steps, or
root causes, yet enhancement methods rarely consume these
structured results and they still rely on raw traces. This
disconnect suggests that the current evaluation centered
on step-level or agent-level accuracy may not reflect a
techniques actual utility in enabling system repair.
Therefore, we advocate for repair-driven metrics that as-
sess how well attribution outputs (e.g., root cause descrip-
tions) can be directly used by enhancement methods or how
much debugging effort they save. Such metrics would incen-
tivize attribution techniques to produce information that is
actually actionable, thereby helping to close the attribution-
to-enhancement gap.
6.2.2 Beyond Partial Observability: The Demand for Com-
prehensive Benchmarks
Who&When [11] is almost the only benchmark specifically
designed for failure attribution of LLM agents for a consid-
erable period in the past. It provides partially observable ex-
ecution traces that include only the agents outputs, without
the corresponding inputs such as original task instructions,
prompts, or contextual messages. This restricted setting can
be suitable for evaluating attribution methods under certain
black-box scenarios, where internal inputs or intermediate
states are inaccessible (e.g., debugging deployed agents on
external platforms). However, in many practical developer-
facing debugging scenarios, developers typically have ac-
cess to substantially richer execution information, including
task instructions, prompts, intermediate messages, tool in-
vocations, and environment states.
The recent introduction of benchmarks like TraceEle-
phant [46], which offers complete execution traces and
reproducible environments, addresses this gap and
represents a necessary step forward. Future opportunities
include creating more diverse, large-scale benchmarks
from real-world deployments to robustly evaluate both
attribution and enhancement methods under realistic
conditions.
6.2.3 From Binary Outcomes to Capability Assessment:
Evaluating in Open-Ended Scenarios
Most existing failure diagnostic methods provide only
coarse-grained outputs, such as binary failure labels, and
heavily rely on the availability of task-specific oracles (e.g.,
test cases) to determine success. However, LLM agents
are increasingly deployed in open-ended scenarios (e.g.,
creative tasks) where clear oracles are scarce, moving
beyond simple pass/fail judgments toward assessing agent
capabilities in open-ended scenarios.
An initial step in this direction is demonstrated by
AgentDiagnose [61], which provides a preliminary attempt
to evaluate agents across five competency dimensions using
LLM-as-a-judge. A critical opportunity lies in developing
trajectory-based analysis that delivers fine-grained, multi-
dimensional assessments of agent capabilities (e.g., planning
fidelity, tool usage, state tracking). Such detailed diagnostics
would not only aid developers in pinpointing weaknesses
but could also serve as intermediate supervision signals to
improve agent training.
6.3 Toward Systematic AgentOps: From Fragmented
Tools to Integrated Governance
Despite progress in attribution, enhancement, and monitor-
ing, these capabilities remain fragmented, i.e., there is no
integrated framework to govern LLM agents from offline
evaluation to production operation. Emerging industrial ini-
tiatives such as AgentOps SDK [86] and IBM Telemetry [87]
signal the need for a systematic discipline, yet academic
research lags behind. As pointed by a recent survey [88],
AgentOps typically includes four key stages: monitoring,
anomaly detection, root cause analysis, and resolution, to-
gether contributing to the accountable, observable agents.
To achieve this, we need open observability standards,
attribution methods that work online, benchmarks that
reflect real-world conditions, and governance frameworks
that keep humans in the loop. Progress has been made on
individual fronts, but an integrated, system-level solution
remains absent. We believe AgentOps should be a first-class
research focus, not a tooling afterthought, if we are to move
from brittle prototypes to reliable production systems.
6.4 Expanding the Horizon: Trajectory Analysis in the
Wild
Beyond controlled settings, three directions connect trajec-
tory analysis to real-world failure diagnose.
6.4.1 Learning from Production Deployments
Current benchmarks and datasets are predominantly con-
structed from controlled environments or synthetic error in-
jection. While valuable for establishing baselines, they may
not capture the full diversity and unpredictability of failures
encountered in real-world deployed agents. Production en-
vironments introduce complexities that controlled settings
cannot replicate: ambiguous user requests, evolving exter-
nal APIs, fluctuating latency, and unanticipated edge cases
[89]. Moreover, failures in deployment often intertwine with
system-level issues (e.g., resource constraints, network in-
stability) that are absent from laboratory evaluations.

6.4.2 Domain-Specific Failure Diagnose
Different application domains impose unique requirements
and introduce distinct failure modes that generic trajectory
analysis methods may overlook. Consider coding agents
(e.g., SWE-agent [90], AutoCodeRover [91]), which navigate
large codebases, generate patches, and interact with version
control systems. Their trajectories contain rich structural
code snippets, dependency graphs, test outputs which
generic natural language methods fail to exploit. Similarly,
GUI agents [92] interact with dynamic visual interfaces,
interpreting screen layouts, handling UI events, and
adapting to application state changes. Their failures often
stem from misinterpreting visual elements, incorrect action
sequences, or inability to handle unexpected interface
transitions.
Other domains, such as web navigation agents and em-
bodied agents in robotics, each exhibit characteristic failure
patterns. Developing specialized diagnostic tools that in-
corporate domain knowledge (e.g., code structure, screen
layouts, dialogue acts) could significantly improve the ac-
curacy and actionability of attribution methods. Moreover,
cross-domain transfer learning might reveal generalizable
principles of agent failure, informing the design of more
robust diagnose techniques.
6.4.3 Beyond Task Completion: Constraint Fulfillment,
Alignment, and Safety
Most existing failure attribution and enhancement
techniques frame success and failure solely in terms of
task completion, i.e., whether the agent achieved the
stated objective. However, in real-world deployments, an
agent may accomplish the task while violating important
constraints, compromising safety, or acting against human
values. For example, an agent might delete backup data to
free disk space, or remove encryption to improve execution
speed, thereby satisfying the immediate goal but creating
unacceptable risks. Such behaviors are rarely captured by
current benchmarks.
Addressing this gap opens several promising research
directions. Future benchmarks could extend beyond binary
task outcomes to include multi-dimensional annotations.
And attribution techniques could be adapted to identify not
only where a failure occurs but also what kind of behavioral
violation has taken place, and whether the violation was
recoverable. By expanding the notion of failure beyond
task success, the community can build agents that are not
only effective but also trustworthy and aligned with human
expectations.
7 RELATEDWORK
7.1 LLM Agents for Software Engineering Tasks
The software engineering community has rapidly embraced
LLMbased agents to automate a wide spectrum of
development activities. Multiagent frameworks such as
ChatDev [93] and MetaGPT [94] simulate collaborative
software teams that write code, conduct code reviews, and
manage projects from highlevel specifications. Specialized
agents like SWEagent [90], AutoCodeRover [91] and
ExpeRepair [95] tackle realworld GitHub issues by
navigating repositories, reproducing bugs, and generating
patches, achieving stateoftheart results on benchmarks such
as SWEBench. Beyond coding, agents have been deployed
for unit test case generation [96], fault localization [97],
and automated software testing [98], demonstrating their
potential to reshape software engineering workflows.
However, the adoption of these agents introduces
new reliability challenges as demonstrated in Section 1.
Bouzenia and Pradel [12] conducted the first empirical
study of thought-action-result trajectories of software
engineering agents, revealing recurrent failure modes
such as repeated identical actions without follow-up,
and debugging anti-patterns, such as generating a fix
without testing it. Their work highlights a pressing need for
systematic, automated techniques to diagnose why an agent
fails and how to repair its behavior. This survey directly
addresses that need.
7.2 Automatic Construction and Self-Evolution of LLM
Agents
Parallel to the software engineering communitys focus on
deploying agents for development tasks, the artificial intel-
ligence community has intensively explored how to auto-
matically construct, optimize, and evolve LLM agents from
scratch or from minimal seeds.
Early work framed agent customization as prompt tun-
ing or incontext learning, but recent advances treat the en-
tire agent its instructions, policies, tool use patterns, and
even collaborative workflows as optimizable parameters.
For example, SCOPE [50] formulates prompt evolution as
an online learning problem, balancing tactical error reso-
lution with strategic principle refinement via a dualstream
mechanism and perspectivedriven exploration. Another line
of research focuses on optimizing the multiagent collabora-
tion structure through systematic exploration of the design
space, driven by diagnostic signals extracted from trajecto-
ries.. For example, Maestro [47] jointly searches over graph
topologies and agent configurations under token or rollout
budgets, guided by reflective textual feedback from traces.
Despite their diversity, all these automatic construction
techniques depend critically on understanding why an
agent succeeds or fails precisely the focus of this survey.
7.3 AgentOps: Observability and Operational Manage-
ment for LLM Agents
Parallel to the technical advances in failure attribution
and system enhancement surveyed in this paper, a
complementary discipline has emerged at the intersection
of software engineering, DevOps, and AI infrastructure:

8 CONCLUSION
Trajectory analysis has rapidly emerged as the central lens
through which LLM agents can be understood, diagnosed,
and improved. This survey has provided a systematic
overview of the emerging field of trajectory analysis for
failure attribution and system enhancement in LLM agents.
By collecting and synthesizing 55 relevant papers published
between early 2025 and April 2026, we have mapped
the research landscape along five key dimensions: failure
taxonomy, failure attribution, system enhancement and
optimization, trajectory visualization and analysis tools, as
well as datasets and benchmarks.
Our analysis reveals a field in rapid formation, driven
by the recognition that traditional software diagnosis
techniques are ill-suited for the non-deterministic, language-
heavy, and interaction-intrinsic nature of agent failures. By
highlighting both achievements and persistent gaps, we
aim to guide researchers and practitioners toward the next
generation of robust, accountable, and self-improving agent
ecosystems. The journey from todays brittle prototypes to
reliable, deployable agentic systems will depend critically
on our ability to analyze, attribute, and act upon the rich
information embedded in every agent trajectory. We hope
this work accelerates that journey.
