Reducing Cost of LLM Agents with Trajectory Reduction
YUAN-AN XIAO,Peking University, China
PENGFEI GAO,ByteDance, China
CHAO PENG,ByteDance, China
YINGFEI XIONG∗,Peking University, China
Multi-turn agent systems based on Large Language Models (LLMs) have become increasingly popular for
software engineering tasks. While LLM agents demonstrate promising effectiveness, the high computational
cost of input tokens due to ever-growing trajectories remains a significant efficiency concern. Efficiency
has been largely overlooked in existing studies and agent products, and this paper addresses this gap by
introducing an inference-time trajectory reduction approach that reduces computational costs.
By analyzing existing agent trajectories, we demonstrate that useless, redundant, and expired information
is widespread across trajectories. Such waste can be identified and reduced without compromising the agent’s
performance. We propose a simple yet effective trajectory reduction approach, AgentDiet, which automatically
removes such waste during agent execution. We implement AgentDiet on a top-performing coding agent,
and our evaluation on two LLMs and two benchmarks shows that AgentDiet can reduce input tokens by
39.9%–59.7% and the total computational cost by 21.1%–35.9%, while maintaining the same agent performance.
These results indicate that inference-time trajectory reduction is a promising direction for agent systems.

1 Introduction
Large Language Models (LLMs) have been widely used for various software engineering tasks such
as code generation, testing, and repair [1, 10, 12, 20, 39, 40]. A prominent trend in the application of
LLMs is agent-based approaches [5, 14, 29, 35, 43, 46], where LLMs are asked to complete complex
tasks through multi-step reasoning and tool calling. For example, mini-SWE-agent [43] achieves a
single-shot performance of 65% in SWE-bench Verified [13] using Claude 4 Sonnet [3], indicating
that agents can fix real-world GitHub issues with basic tools such as file editing and bash scripting.
Given their promising performance, LLM agents are integrated into various AI products [2, 7], and
24% of professional developers already use LLM agents daily or weekly in 2025 [25].
Although these agent approaches demonstrate promising performance in terms of effectiveness,
efficiency remains a concern for their application [9]. In a recent survey by StackOverflow [25],

The root cause of this efficiency issue lies in the workflow of LLM agents, specifically the ever-
growing trajectory. In a typical agent system, once the LLM calls a tool, the tool call and its result
are kept in the trajectory until the agent completes the entire task. Therefore, if the LLM opens
a large file or runs a command that generates verbose output, the computational cost of these
tokens snowballs in each subsequent step [8]. This results in non-negligible waste. For example, in
September 2025, the daily token usage of Claude 4 Sonnet reached 100 billion on the OpenRouter
platform [24], and 99% of them were input tokens accumulated in the trajectory, while only the
remaining 1% were generated by the LLM.
To address the above efficiency issue, this paper focuses on reducing trajectory tokens for coding
LLM agents. In academia, most existing papers on token reduction focus on single-turn tasks, such
as trimming the retrieved input for question-answering [6, 22, 27, 37, 47]. These tasks differ from
agentic coding in multiple aspects, limiting the applicability of existing approaches. Specifically: (1)
these approaches reduce all input tokens at once, whereas trajectory tokens gradually accumulate in
agents, making the timing of reduction a new research question; (2) these approaches reduce tokens
in natural language, while coding agents process structured information such as software source
code; (3) some approaches require modifying the LLM inference process or even the model itself,
which is impractical and unsuitable for proprietary LLMs that do not provide such capabilities. To
the best of our knowledge, there is no existing publication on inference-time trajectory reduction
for coding agents. In industry, agent products such as Claude Code and Cursor [ 2, 7] sparingly
apply LLM-based trajectory reduction (often called “compaction”) only when the context window
is full or the user explicitly requests it, focusing on improving robustness rather than efficiency.
As a result, the potential for efficiency improvement via trajectory reduction remains unknown.
This paper reveals this potential by designing an LLM-based trajectory reduction approach and
evaluating it on multiple benchmarks and LLMs.
In Section 2, we analyze the problem and investigate the potential for cost reduction, revealing that
the trajectories of LLM agents contain a significant amount of waste, including useless, redundant, or
expired information. Based on this empirical finding, we propose a prototype approach to reduce this
waste using an LLM. In Section 3, we instantiate this design into a concrete algorithm, AgentDiet.
Section 4 discusses the integration of AgentDiet into agents and the effect of hyperparameter
settings through a quantitative experiment. Section 5 evaluates AgentDiet on two LLMs and
two benchmarks, showing that it can steadily reduce input tokens by 39.9%–59.7%, or the final
computational cost by 21.1%–35.9%, while maintaining the same agent performance. Section 6
discusses possible future work and threats to the validity of the evaluation. Section 7 reviews related
work.
The contributions of this paper are summarized as follows:
• We reveal that inference-time trajectory reduction of coding agents is a promising direction,
with evaluation results showing that significant cost reduction is possible without harming
agent performance through frequent trajectory reduction during agent execution;
• We propose AgentDiet, a simple yet effective trajectory reduction approach, which is open-
source and can be easily integrated into coding agents;
• We discuss the design of possible trajectory reduction approaches through case studies and
large-scale quantitative experiments.

2 Problem Analysis
In Section 2.1, we first discuss preliminary concepts related to this paper, i.e., the typical workflow
of LLM agents and the contents of their trajectories. We motivate our approach in Section 2.2 and
Section 2.3 by empirically identifying typical waste in trajectories and then designing a prototype
trajectory reduction approach to address it.
In particular, we aim to answer a series of questions:
•Is there waste in the trajectories?(Yes, there is a lot.)→Section 2.2
• Can we automatically identify and reduce the waste in trajectories?(Yes, it is possible to use an
LLM for trajectory reduction.)→Section 2.3.1
• Do LLMs know when to perform trajectory reduction on their own?(No, so we enforce the
trajectory reduction step with a separate reflection module.)→Section 2.3.2
• Is calling an LLM for this purpose ideal and efficient?(Not really, but the overhead is under
control with simple optimizations.)→Section 2.3.3
2.1 Preliminaries
“Agents are models using tools in a loop. ”
- Hannah Moran from Anthropic,Prompting for Agents
In recent years, Large Language Models (LLMs) have demonstrated the ability to assist with a
wide variety of tasks. Following established approaches such as Chain-of-Thought [38], ReAct [44],
and CodeAct [34], LLM agents have emerged as a promising paradigm for integrating LLMs into
such tasks by equipping the LLM with tools to interact with the environment. In the field of software
engineering, this means that the LLM can operate on the codebase autonomously with the ability
to read files, make edits, execute commands, commit changes, etc.
Fig. 1 shows the typical workflow of an LLM agent. The core of an agent is itstrajectory, which
records all the necessary context that will be given to the LLM. An agent starts with an initial
trajectory that contains the instruction to the LLM (in a system message) and the current task (in a
user message). The LLM then analyzes the current situation and predicts the next action to take
in a standard tool call format (in an assistant message). The agent system parses the generated

tool call, executes the action, and returns the output to the LLM (in a tool message). In this loop,
assistant and tool messages are continuously concatenated into the trajectory, which will be the
input to subsequent LLM predictions. The loop continues until the LLM decides to finish the task
with a special indicator, or when the agent system reaches the step limit.
From this workflow, we can identify an obvious efficiency issue in such agent systems: Once
the LLM calls a tool, the corresponding assistant and tool messages will be concatenated into
the trajectory and will be kept forever until the task finishes. A long message is included in each
subsequent LLM prediction, even if its content is irrelevant (or no longer relevant) to the task,
leading to inefficient use of computational resources. As a quantitative result, the average trajectory
for solving a single GitHub issue that we collected from the SWE-bench Verified [13] benchmark
contains 48.4K tokens in 40 steps. Breaking down these tokens, tool messages (containing the
results of tool calls) use 30.4K tokens, assistant messages use 13.7K tokens (of which 11.9K are
the arguments of tool calls), and system/user messages (containing the initial instructions) use
4.4K tokens. Since each token concatenated into the trajectory is included in every subsequent
input to the LLM, the accumulated token usage per issue reaches 1.0M, which requires excessive
computational and memory resources.
Recent LLMs are equipped with the KV Cache mechanism, which mitigates the issue of high
computational cost by caching repeated calculations of the Key and Value matrices in the Trans-
former [33] architecture. However, this does not eliminate the need for trajectory reduction because:
(1) KV Cache only caches part of the computations, and the remaining calculations are still costly
as the trajectory grows rapidly; (2) KV Cache consumes hardware resources like VRAM and I/O
bandwidth, so reducing the trajectory length conserves these valuable resources. In fact, the ex-
istence of KV Cache makes designing trajectory reduction approaches more challenging, since
modifying a token in the trajectory invalidates the cache for all subsequent tokens.
Long messages in the context window not only harm the efficiency but also cause the performance
of LLMs to degrade [16, 21]. Therefore, removing content from trajectories does not necessarily
lead to a drop in the agent’s performance. Instead, it has the potential to maintain or even slightly
improve the performance of agents by removing waste.
2.2 Waste in Trajectories
This subsection presents a pilot study where we analyze the feasibility of trajectory reduction by first
identifying typical waste in trajectories. For this purpose, we use SWE-bench Verified [13], a popular
benchmark requiring agent systems to solve GitHub issues in well-known Python repositories.
The benchmark makes the logs and trajectories of all participants available for download. We
downloaded and manually inspected 100 trajectories from Trae Agent [ 11], which is based on
Claude 4 Sonnet and ranked top on SWE-bench Verified.
By qualitatively inspecting the contents of the trajectories, we found that waste is widespread in
almost all trajectories. We categorized the waste into three typical scenarios in which tokens could
be removed or compressed from a human perspective:
2.2.1 Useless Information.Some information is irrelevant to the task and can be safely removed
with minimal information loss. For example, nearly all trajectories begin with a tool call to enumerate
all files in the repository, and the tool response includes cache and resource files (e.g., files under
the __pycache__ and .egg-info directories). In all trajectories, the agent also executed commands to
build and test the project, which may generate verbose output (e.g., GNU make prints the message
“make[2]: Entering/Leaving directory'...' ” for each visited location by default). Although Trae
Agent has a mechanism to truncate output to the first 16KB, a fixed threshold only avoids extreme
cases, and we still frequently observed useless information within this threshold.

2.2.2 Redundant Information.When a piece of information appears multiple times in the trajectory,
redundant copies can be removed without losing information. The most typical case of redundant
information involves thestr_replace_editor tool, a standard file editing tool designed by Anthropic
that is frequently used in all trajectories. The tool call arguments forstr_replace_editor are passed
as JSON, such as {"command": "str_replace", "path": "F", "old_str": "P", "new_str": "Q"} ,
where P is a unique fragment of file F that typically contains multiple lines, and will be replaced by
Q. The tool will perform the string replacement and then respond with the replaced result. There
are multiple redundancies in such a tool call: (1) Q in the argument is repeated in the replaced
result in the tool response; (2) Q may contain the same components (e.g., shared statements) as P;
(3) the agent must have retrieved the context to edit prior to this tool call, so P repeats code from
previous steps in the trajectory.
2.2.3 Expired Information.Information relevant to a local step may no longer be necessary after
the step is completed. A typical case is where the agent loops through many items to find the
relevant one. For example, in the process of diagnosing the root cause of the issue, the agent often
searches for a symbol with the grep shell command, and then opens each file to read as it appears
in the search results. This process takes a few steps in the trajectory, and once the agent identifies
the faulty file, most content in other files becomes unnecessary.
2.3 A Prototype Approach to Trajectory Reduction
2.3.1 Reducing the Waste.In this subsection, we discuss how to automatically identify and reduce
waste in trajectories. A straightforward approach would be to maintain a set of rules (such as
regular expressions) for each typical kind of waste, but such rules are unlikely to cover the variety
of scenarios. For example, it is difficult to write a rule to identify all verbose output in test logs,
since every project has its own output format.
Given the heuristic nature of this task, we chose to identify and reduce waste with the help of an
LLM. We designed a prompt for trajectory reduction consisting of four parts:
Prompt outline for AgentDiet
[1. High-level job description]
You will analyze and compress a given step in the trajectory of an LLM agent solving a software
bug. Your job is to . . .
[2. Input/output format]
In the trajectory, each step is wrapped in <step id="... "></step>. You should process . . .
[3. Summary and examples of the three kinds of typical waste]
Typical examples:
- (Useless information) If the step opens a huge file but only one part is necessary . . .
- (Redundant information) If the step uses str_replace_editor to modify a file . . .
- . . .
[4. Guidelines to prevent information loss after reduction]
- Replace the text to remove with a short takeaway, e.g., . . .
- You should keep the original structure unchanged, e.g., XML tags, . . .
- . . .

2.3.2 Agent Integration.After showing that trajectory reduction is possible with an LLM, the next
natural topic is how to integrate this into an agent system.
Ideally, if the agent system is powerful enough, it could reduce its own trajectory given a tool
for that purpose. We tested this hypothesis by implementing a tool called erase, which allows the
agent to override existing steps in the trajectory. We assigned a numeric ID to each segment in the
trajectory, and the LLM could call the erase tool with arguments such as {"id": 17, "takeaway":
"unrelated content"} to replace the segment with a short takeaway. However, based on our
preliminary experiments, even with powerful LLMs such as Claude 4 Sonnet and Gemini 2.5 Pro,
the agent often persisted with the original task without calling erase, despite explicit prompts.

2.3.3 Controlling the Overhead.In terms of efficiency, the current design with a separate reflection
module is not ideal due to the additional cost overhead. Passing the full agent trajectory to the
reflection module at each step would double the token usage, defeating the whole purpose of
cost reduction. Making the situation worse, the KV Cache cannot be shared between the target
agent and the reflection module due to differences in the system prompts and tools. Furthermore,
modifying a step in the trajectory invalidates all subsequent caches. Therefore, controlling the
overhead becomes an essential topic.
The first approach to consider is the choice of LLM in the reflection module. Since trajectory
reduction is arguably easier than the agent’s primary task, we can significantly reduce overhead
by choosing a more cost-efficient LLM for the reflection module. In the case study illustrated
in Fig. 2, the trajectory was generated by the agent using Claude 4 Sonnet, while the reduction
was performed by GPT-5 mini, which is 12 times cheaper than Claude 4 Sonnet, minimizing the
overhead concern. We will discuss more about the choice of LLM in Section 4.2.

3 Algorithm
In Section 2.3 and Fig. 3, we have established the design of AgentDiet with three technical insights:
• Prompting a cost-efficient LLM with the three types of waste is enough to achieve an effective
trajectory reduction.
• Manually invoking the reflection module after a long step is necessary, because agents are
incapable of using the erase tool autonomously.
•The sliding window balances the overhead while retaining reduction effectiveness.

4 Implementation
4.1 Integration in Agents
AgentDiet is a general approach that can be readily applied to any LLM agent fitting the definition
“agents are models using tools in a loop”. For a typical agent system similar to the example in
Algorithm 1, we can add a call to the reflection module (highlighted by the orange box) after each
step in the agentic loop.
Following this procedure, we integrated AgentDiet into Trae Agent, which is open-source and
ranked first on SWE-bench Verified at the time of our research (July 2025). We did not further
integrate or experiment with AgentDiet in other LLM agents, based on the observation that current
agent systems are generally homogeneous and employ a similar set of prompts and tools. For
example, Trae Agent is equipped with four tools: bash to execute Bash commands, str_replace_
editor to view or edit files, think to analyze the issue, and task_done to finish the task. This
set of tools is semantically similar to those in other systems, such as mini-SWE-agent [ 43] and
OpenHands [35]. Therefore, the results with Trae Agent are likely to generalize to a variety of
similar agent systems.
Note that there are variants of agent systems, such asensembledsystems that call the LLM agent
multiple times and decide the final answer by majority voting or an LLM, andmulti-agentsystems
that simultaneously spawn multiple LLM agents with a communication mechanism. AgentDiet can
be integrated into such systems by adding the reflection module to the LLM agent in an ensembled
system, or to all LLM agents in a multi-agent system. To maintain the generality of the approach,
this paper does not focus on optimizations specific to these systems. We leave the evaluation of
such applications for future work.
4.2 Hyperparameter Settings
In this subsection, we discuss the effect of different hyperparameter settings ( LLMreflect, 𝜃, 𝑎,
and𝑏, as shown in Algorithm 1) based on the Trae Agent integration. Note that the other two
hyperparameters (LLMagent and𝑠max) already exist in the original Trae Agent, so we exclude them
from the discussion and set them to standard default values: LLMagent = Claude 4 Sonnet, and
𝑠max =50.
4.2.1 The Process.Since the search space of hyperparameters is multidimensional, we used the
standard hill climbing algorithm to find an ideal setting, which is arguably more rigorous than
determining each parameter independently.
The process began by setting each hyperparameter to an initial default value. Then, we quan-
titatively compared efficiency and agent performance via a small experiment involving variants.
Each variant adjusted one hyperparameter to a different value in the search space while keeping
other hyperparameters at their default values. If a variant demonstrated a better overall result, it
was selected as the new default value for that hyperparameter in the next iteration. The process
repeated until the hyperparameters converged to a local optimum.
4.2.2 Benchmark.In this process, we used a random subset of 100 instances from SWE-bench
Verified [13] as the benchmark for deciding hyperparameters. This was the same set used in the
manual analysis in Section 2.2. We did not use the full benchmark because the remaining instances
will be used exclusively for evaluation in Section 5.

module. These variants are selected to cover a variety of cost-efficient LLMs from various ven-

5 Evaluation
In this section, we empirically evaluate AgentDiet with the following research questions.

5.2.2 RQ2. Performance Impact.From the “Pass%” row in Table 4, we can compare the numbers be-
tween Original and AgentDiet to assess its impact on the agent’s performance. On two benchmarks
and two LLMs, the performance of AgentDiet is comparable (-1.0%–+2.0%) to that of Original. These
results show that AgentDiet does not harm the agent’s performance while improving efficiency,
which contradicts the common belief of “test-time compute” [4] that there is a trade-off between
token efficiency and model performance. As discussed in Section 2.1, a possible explanation is that
the performance of LLMs degrades as the length of the context increases [16] or when the context
is of low quality [15]. Therefore, the removal of waste information from the agent trajectory may
cause less degradation to the model’s performance.
Additionally, from the “Step” and “PStep” rows, we observe that AgentDiet does not cause the
steps required to resolve a task to increase. This is an additional indicator confirming that AgentDiet
does not disturb the agent.
We see an unexpected case in the last column in Table 4, where AgentDiet significantly reduces
the average steps from 57.20 to 43.90 when Gemini 2.5 Pro works on the Multi-SWE-bench Flash
benchmark. We identify the reason by inspecting the trajectories: Gemini 2.5 Pro shows increasingly
abnormal behavior when the context is too long, often resulting in repeated invalid tool calls until
the step limit is reached. Therefore, AgentDiet reduces this probability by reducing the length of
the trajectory by half. Fig. 5 presents the histogram of the step distribution in the experiment with
Gemini 2.5 Pro + Multi-SWE-bench Flash, where AgentDiet reduces the number of instances that
reach the step limit (100 steps) from 66 to 26. As a result, the average steps are significantly reduced.
This interesting observation highlights a side effect of AgentDiet: improving the robustness of LLM
agents in corner cases.
Finding 2.The ratio of successfully resolved instances for AgentDiet is comparable (-1.0%–
+2.0%) to that of the Original baseline. AgentDiet also does not cause the agent to take more
steps to resolve a task. Therefore, trajectory reduction does not harm the agent’s performance.

6 Discussion
6.1 Future Work
6.1.1 Improving the Latency of Agents.In Algorithm 1, AgentDiet adds an additional reflection step
to the agent loop, which introduces an increase in latency. This increase is expected to be minimal,
as we use a cost-efficient model for LLMreflect, and the latency is reduced for LLMagent due to the
reduction in trajectory length. We do not quantitatively compare latency between AgentDiet and
the Original agent because the experiment relies on commercial LLM APIs, where latency is highly
unstable due to server load. In latency-critical scenarios, Algorithm 1 can be modified to perform
the reflection and agent steps in parallel. This modification would eliminate the latency increase, at
the cost of reducing the context available to the reflection module (hyperparameter𝑎) by one step.

6.1.2 Exploring Different Designs for Trajectory Reduction.This paper presents a preliminary study
on the efficiency of LLM agents and proposes AgentDiet as a simple yet effective approach for
trajectory reduction. Moreover, we only consider off-the-shelf LLMs as LLMreflect, incurring a cost
overhead of 5%–10%. Future work could replace off-the-shelf LLMs with more efficient customized
models to reduce this overhead.
For agent systems that route tasks of varying difficulty to different LLMs, it is also possible to
automatically adjust the hyperparameters of AgentDiet to balance efficiency and performance
across tasks.
6.2 Threats to Validity
6.2.1 Generalization Across Agents.The main threat to external validity comes from the general-
ization of our findings. We employ two benchmarks and two LLMs to mitigate this threat. However,
due to effort and cost constraints, AgentDiet is implemented only for the Trae Agent. In fact,
the existing experiments have already incurred an LLM cost of approximately US$ 2000, making
experimentation with additional agent systems financially prohibitive. As discussed in Section 4.1,
current agent systems are generally homogeneous, employing a similar set of prompts and tools.
Therefore, we believe this threat has a limited impact on our findings.
6.2.2 Data Leakage in LLMs.Another potential threat to internal validity is data leakage in LLMs.
Since the experiment utilizes proprietary LLMs, benchmark instances may have been included in
their training data. We have no control over their training process. There are existing studies on
this threat that readers can refer to. For example, the authors of SWE-bench empirically compared
the performance of multiple LLMs before and after their knowledge cutoff date and concluded that
“for most models there’s little difference in performance before or after this date” [13]. Thus, we
believe this threat does not significantly affect the validity of our findings.
To further mitigate this threat, we included Multi-SWE-bench Flash [45], a recently published
benchmark collected by a third party and not mentioned in the technical report of any evaluated
LLM.
6.2.3 Correctness of Patches.Both SWE-bench Verified and Multi-SWE-bench Flash validate
the correctness of agent-generated patches using developer-written test cases. An instance is
deemed successfully resolved if it passes all test cases. However, a patch that passes all test cases
(“plausible”) may not be semantically equivalent to the ground truth patch written by the developer
(“correct”). Consequently, overfitting to test cases poses a potential threat to validity for all test-
based approaches, including ours. However, prior work [ 28] suggests that overfitting is not a
severe threat in program repair. Additionally, since each instance in SWE-bench Verified and
Multi-SWE-bench Flash includes at least one held-out test case, the threat of overfitting is mitigated.
Furthermore, our experiment compares AgentDiet with the Original agent, both of which are
exposed to the same degree of overfitting threat. Therefore, we believe this threat does not affect
the validity of our findings.
7 Related Work
7.1 Prompt Reduction
Previous approaches to prompt reduction improve the efficiency of LLMs by reducing the number
of tokens in the prompt. The majority of prompt reduction work aims at Retrieval-Augmented
Generation (RAG), where the system retrieves documents related to the user query from a database
used as a reference by the LLM. FilCo [37] filters the retrieved documents to retain only useful parts
based on information-theoretic approaches. Selective Context [17] calculates the self-information

of each token in the document with ground truth generated by a teacher LLM. CPC [19] trains a
context-aware sentence encoder to judge similarity based on the user query. These approaches
target prompts in natural language, so they do not preserve the important structure in code and

There are also approaches to prompt reduction specifically designed for code input. Suneja et al.
[32] and Rabin et al. [30] minimize the input code while preserving the output based on program
simplification approaches. Zhang et al. [47] and Wang et al. [36] prune tokens in the code based
on heuristic rules. Yang et al . [42] compresses the docstring in the source code. Pan et al . [26]
reformats the code to remove tokens related to whitespace and indentation.
However, all approaches mentioned above aim to reduce prompts in theinitialinput to the
LLM, and do not consider the iterative nature of agent systems. Since trajectories are generated
iteratively in agent systems, the timing of reduction becomes an important factor that can affect the
efficiency and performance of the agent (as we show in Section 4.2). Therefore, these approaches
cannot be directly applied to agent trajectories without discussing the timing of prompt reduction.
Lindenbauer et al. [18] propose an approach to trajectory reduction in parallel with our work.
Their approach can be considered a variant of the Delete baseline (in Section 4.2.3) that deletes only
the tool message but not the assistant message after a delay of 10 steps. Our results in Table 2 show
that the Delete baseline is inferior to all LLM variants, with a severe decrease in Pass% by 7% and
an increase in Step and PStep by 14%. Furthermore, the choice of𝑎= 10would cause significant
overhead due to KV Cache invalidation.
7.2 Context Management in Agent Systems
Various agent systems employ some form of context management mechanism. For example, Cur-
sor [7] and Claude Code [2] compress the context with an LLM when the context window is full.
Trae Agent [11] truncates each tool response to the first 16 KB. SWE-agent [43] has multiple con-
figurable mechanisms such as removing text identified by a regular expression. These mechanisms
are often ad-hoc and applied sparingly, aiming to improve the robustness of the agent in corner
cases. In comparison, AgentDiet aims to improve the overall efficiency of the agent by applying
trajectory reduction aggressively. Such context management mechanisms are also not reported or
evaluated as a first-class research question in existing papers [18]. In contrast, this paper provides
an in-depth discussion and a large-scale evaluation of AgentDiet.

7.3 Efficiency Improvement for White-Box LLM Systems
Some approaches improve the efficiency of LLMs by fine-tuning the model structure or optimizing
the inference process. DMC [ 23] combines adjacent KV Cache entries, which has the effect of
merging multiple tokens into one token, thus saving computational cost. PISCO [22] distills RAG
documents into embedding vectors with minimal cross-entropy to save tokens. Prune-on-Logic [48]
prunes the Chain-of-Thought tokens during model training to improve the reasoning efficiency of
the trained model. MEM1 [49] trains an LLM that can modify the content in fixed-length memory.
Alpine [31] adds a pruning layer in each Transformer block to reduce computational cost.
Since these approaches modify the LLM’s training or inference process, they require white-box
access to the model. However, many state-of-the-art LLMs for agent systems are proprietary and
do not permit such modifications. In comparison, AgentDiet does not depend on the internal
mechanisms of the LLM and can be applied to a wider range of agent systems.
8 Conclusion
This paper addresses the efficiency concerns of coding LLM agents, an aspect often overlooked in
existing studies. Through an analysis of trajectories in SWE-bench Verified, we identify typical
sources of waste in these trajectories. We then propose AgentDiet, an inference-time trajectory
reduction approach designed to reduce the token cost of agent systems with a reflection module. We
integrate AgentDiet into a top-performing coding agent and investigate hyperparameter settings
for the reflection module through quantitative experiments. Finally, we evaluate AgentDiet on both
SWE-bench Verified and Multi-SWE-bench Flash using Claude 4 Sonnet and Gemini 2.5 Pro. The
results show that AgentDiet consistently reduces input token usage by 39.9%–59.7%, resulting in
significant computational cost savings of 21.1%–35.9%. Moreover, AgentDiet maintains performance
parity with the Original agent (ranging between -1.0% and +2.0%). This work demonstrates that the
cost of LLM agents can be reduced without compromising performance using a simple approach.
This approach benefits the practical application of agent systems and serves as a foundation for
future research.
