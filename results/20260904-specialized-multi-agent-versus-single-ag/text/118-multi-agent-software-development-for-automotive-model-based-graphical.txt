ABSTRACT The automotive industry is experiencing an unprecedented growth in software complexity
driven by electrification, autonomy, and connectivity. Model-Based Design (MBD) using graphical
development tools such as Simulink from MathWorks has become standard in the industry, but the
translation of natural language software requirements into compliant, tested control models remains a
largely manual and time-consuming task. This paper presents a multi-agent large language model (LLM)
framework tailored for automotive model-based software development. Our framework orchestrates a set
of specialized AI agents to cover the implementation and model-level verification phases of the software
development lifecycle, including Simulink model generation, test case creation, compliance checking, test
case execution, and automated refinement. To rigorously assess our approach, we introduce the Automotive
Software Engineering Benchmark (ASWE-Bench), a new benchmark suite with 38 automotive software
requirements categorized into data transformations, combinational logic, stateful logic with timers, and
closed-loop control. Our results demonstrate a substantial improvement in generative AI performance:
the rulebook-equipped single-agent baseline achieve only a 47.4% model-level pass rate, while our full
multi-agent framework attains 73.7% across generated models. This work advances generative AI from
isolated prompting to automation in complex development environments and sets a foundation for scalable
AI-driven software pipelines in model-based systems engineering. To support reproducibility and future
benchmarking, the proposed ASWE-Bench, including requirements and unit tests, is publicly available at:
https://git-ce.rwth-aachen.de/mmp-rwth-aachen/aswe-bench

Recently, generative AI has made remarkable strides in
many domains. State-of-the-art LLMs such as GPT-4 can
achieve near-human performance on diverse professional
and academic exams. For example, GPT-4 passed a sim-
ulated bar exam within the top 10% of test takers [7].
LLMs have demonstrated a substantial impact on software
development by enabling the automation of tasks such as
coding, debugging, documentation, and test creation. This
capability contributes to a reduction in the time required for
software development [8]. To support this claim, a study
presented in [8] divided developers into two groups, each
tasked with implementing an HTTP server in JavaScript. The
experimental group, which had access to GitHub Copilot,
an AI-assisted programming tool, completed the task 55.8%
faster than the control group. This shows that generative
AI could significantly accelerate the software development
process.
Despite this promise, automotive software development
imposes unique challenges. V ehicle functions are both safety
and performance critical and must integrate tightly with
real-time hardware (multiple ECUs, sensors, communication
buses) under strict standards (e.g. ISO 26262, AUTOSAR)
[9]. To manage complexity, engineers rely on model-based
systems engineering (MBSE), linking requirements to archi-
tecture and finally to implementation [10]. In practice,
many automotive functions are modeled graphically in
environments like Simulink [11], where block diagrams
represent control logic. However, LLMs are trained primarily
on text and traditional code, not on specialized graphical
representations [12], [13]. We use the term ‘‘modality
gap’’ to denote the mismatch between text-native LLMs
and Simulink’s graph-structured block-diagram semantics.
Together with the need for rigorous testing and compliance
checking, this makes automotive software more challenging
than general programming tasks. In this work, the modality
gap is addressed by using MA TLAB scripts as a text-based
intermediate representation through which LLM agents can
construct, configure, and revise graphical Simulink models
programmatically.
Existing generative-AI approaches for Simulink remain
limited and do not yet provide an end-to-end, requirement-
centric engineering workflow. Early work such as SLGPT
focuses on directly generating Simulink artifacts from model
corpora and is not driven by requirement reasoning [20].
Sim-Instruct advances requirement-to-model generation via
fine-tuning on synthetic Simulink data, but it does not
incorporate a closed feedback loop based on systematic
unit-test generation and execution [12]. SimuGen demon-
strates an agentic workflow, but it relies on existing
Simulink diagram images as input and primarily reconstructs
diagrams rather than generating models directly from textual
requirements [13]. In contrast, our approach starts solely from
software requirements and treats functional correctness as the
primary objective: it generates MA TLAB code to construct
the Simulink model, automatically derives requirement-based
unit tests, executes them, diagnoses failures, and applies
targeted fixes in an iterative refinement loop. We further
integrate an explicit compliance review agent to enforce
modeling constraints and detect nonconformities, enabling
a self-correcting pipeline tailored to graphical automotive
control logic. This end-to-end, requirements-to-tested-model
workflow can reduce manual engineering effort and iteration
cycles, improve traceability from specification to verification
evidence, and thereby accelerate time-to-market for safety-
and performance-critical automotive functions.
In this work, we introduce AutoMAS-SL, a multi-agent
framework that automates selected phases of the V -Model
for Simulink-based development from textual requirements.
The framework decomposes the workflow into specialized
agent roles and is inspired by multi-agent code generation
architectures [14], [15].
Our key contributions include:
• Multi-agent framework for Simulink development: We
propose a coordinated framework of specialized agents
that automates the software lifecycle. The process
consists of a Function Developer Agent, equipped
with a comprehensive ‘‘rulebook’’ of domain-specific
knowledge, that translates the software requirements
into executable MA TLAB code to generate Simulink
models. Crucially, the framework implements a fully
automated, iterative refinement loop. A Testing Agent
generates test cases directly from the requirements,
which are executed by a MA TLAB Test Runner.
Upon failure, a Diagnosis Agent employs a structured
reasoning process to identify the root cause, and a fixer
agent implements the necessary corrections, enabling
the system to iterate until the model’s behavior aligns
with the specifications.
• Integrated compliance: To ensure the generated mod-
els adhere to requirements, we incorporate dedicated
agents for governance. A Compliance Agent serves as
an automated peer reviewer, validating the generated
model against the software requirements, flagging
non-conformities in logic patterns.
• ASWE-Bench: To rigorously evaluate LLM perfor-
mance on graphical programming tasks, we developed
ASWE-Bench, a new benchmark suite comprising
38 diverse and realistic automotive software require-
ments. To ensure their relevance to automotive practice,
the requirements were developed with support from
FEV domain experts and reflect representative control-
logic tasks encountered in automotive model-based
development. These requirements span four critical
categories: data transformation, combinational logic,
stateful logic with timers, and closed-loop control. Each
entry includes a ground-truth set of unit tests to assess
functional correctness, not just syntactical validity. This
benchmark provides the first standardized means of
measuring and comparing the ability of generative
models to produce correct, working control models in
Simulink, filling a significant gap in existing evaluation
frameworks. Our results demonstrate that the proposed

II. RELATED WORK
A. GENERATIVE AI IN SOFTWARE ENGINEERING
Large language models have dramatically impacted software
engineering by automating coding tasks. For example, mod-
els like Codex (GPT-based) [16] and CodeGen[17] which are
trained on large-scale code corpora, have demonstrated sub-
stantial improvements to generate textual code. Instruction-
finetuned code models have also emerged: Salesforce’s
WizardCoder uses an evolutionary ‘‘Evol-Instruct’’ method
to fine-tune code LLMs using synthetic generated data,
achieving state-of-the-art performance on standard coding
benchmarks. This model ‘‘surpassed all other open-source
Code LLMs at the time’’ [18] on one of the most
popular code benchmarks HumanEval. While fine-tuned
and pretrained code LLMs such as Codex, WizardCoder
and Code-Llama [19] have shown strong capabilities in
generating textual code, they often suffer from limitations
such as hallucinations, lack of error correction, and difficulty
handling complex multi-step development workflows. These
shortcomings highlight the need for approaches that move
beyond a single-model paradigm.
Recent progress in code-oriented LLMs builds on a
broader line of pretraining research that explicitly targets
the interaction between natural language and programming
languages. Encoder-only and encoder–decoder models such
as CodeBERT and CodeT5 demonstrate how large-scale
pretraining on Natural Language Programming Language
(NL–PL) pairs and code corpora can yield transferable
representations for code search, summarization, translation,
and defect-related tasks, while highlighting the importance of
identifier semantics and code-specific token types [22], [23].
A complementary perspective is provided by PLBART,
which uses sequence-to-sequence denoising pretraining for
program understanding and generation across multiple tasks,
reinforcing that downstream Software Engineering (SE)
performance depends not only on model scale but also on
pretraining objectives and task framing [24].
In parallel, prior work has emphasized standardized
evaluation beyond single-task benchmarks. CodeXGLUE
provides a broad benchmark suite covering multiple code
understanding and generation tasks, enabling more system-
atic comparisons of models and prompting strategies across
problem types and languages [25]. For end-to-end ‘‘real-
world’’ maintenance tasks, Software Engineering Bench-
mark (SWE-bench) operationalizes GitHub issue resolution
as a benchmark requiring repository context, multi-file
edits, and test-based validation, which aligns closely with
agentic workflows that integrate generation with execution,
debugging, and patch refinement [26]. Finally, systematic
reviews of LLMs in software engineering and software
testing consolidate evidence on strengths and failure modes
(e.g., reliability and hallucinations) and recurring mitigation
patterns, providing a literature anchor for workflow-centric
contributions [27], [28].
B. MUL TI-AGENT SYSTEMS IN SOFTWARE ENGINEERING
Recent approaches compose multiple LLM-based agents
in a collaborative pipeline to overcome the shortcomings
of a single LLM, by distributing roles across specialized
agents, enabling iterative feedback and more reliable
software generation. For example, MetaGPT [15] is a
meta-programming framework that incorporates human
workflows into LLM-based multi-agent collaborations.
MetaGPT assigns agents specialized roles (e.g. architect,
product manager, engineer, . . . ) in an assembly-line fashion
to decompose complex tasks and verify intermediate results.
The authors report that MetaGPT generates more coherent
solutions than previous chat-based multi-agent systems
(MAS). Likewise, AgentCoder [14] proposes a three-agent
pipeline for code generation: a programmer agent writes
code, a test-designer agent creates test cases, and a test-
executor agent runs these tests to provide feedback. This
iterative loop enables automatic refinement. The authors
show that AgentCoder achieves pass@1 accuracy (correct on
the first attempt) of 96.3% with GPT-4 on HumanEval, versus
85.8% for MetaGPT and 67.0% for standard GPT-4 [14].
Although MAS have proven improved performance and
ability on solving more complex tasks, their application has
so far been largely focused on text-based tasks. Thus, while
multi-agent systems have demonstrated clear benefits for
textual software engineering, their transfer to automotive
development remains non-trivial because the target artifacts
are often graphical Simulink models rather than conventional
source code, creating a gap that existing MAS frameworks do
not explicitly address.
C. MODEL-BASED TESTING AND V&V FOR SIMULINK
Model-based development in cyber-physical and automotive
contexts has long relied on systematic verification and
testing of Simulink/Stateflow models, including automated
test generation and coverage-driven exploration. A widely
used conceptual basis is model-based testing (MBT), where
tests are derived from behavioral or structural models
and executed against the system under test; classic MBT
taxonomies provide a vocabulary to compare approaches

oracle assumptions) [29]. In the context of Simulink/
Stateflow models, prior work has investigated automated
test generation and coverage-driven verification using both
search-based and formal techniques. Oh et al. proposed
a messy genetic algorithm for transition-coverage testing
of Simulink/Stateflow models, showing improved coverage
compared with random search and a commercial testing

generation, traceability has also been studied as a central
concern in heterogeneous automotive model-based devel-
opment; Dubois et al. proposed a traceability metamodel
linking requirements, solution models, and verification
and validation artifacts [34]. Together, these studies show
that Simulink-based engineering requires not only model
generation, but also systematic testing, coverage analysis, and
traceability between requirements, models, and verification
evidence.
D. GENERATIVE AI IN AUTOMOTIVE SOFTWARE
LLMs generally struggle with Simulink code generation
because training data from block-diagram models are
scarce [13]. Early attempts like SLGPT (a GPT-2 fine-
tuned on just 400 simulink models) proposed a promising
approach for the generation of simulink models but was
limited in corpus size and model complexity [20]. More
recent efforts [12] propose Sim-Instruct which fine-tunes
open-source LLMs on synthetic generated Simulink models.
Sim-Instruct used GPT-3.5 to generate thousands of synthetic
Simulink models for training and applied a repair algorithm
to improve their quality. The resulting 7B fine-tuned Mistral
LLM have substantially outperformed GPT-3.5 and GPT-4
by 53% and 20% respectively, but was also limited in model
complexity. Another approach is SimuGen [13], a multi-
modal multi-agent framework for Simulink. SimuGen feeds
both the requirement text and the Simulink diagram images
into specialized agents (investigator, code generator, unit
test reviewer, an executer, a debug locator, and a report
writer) along with a domain knowledge base. These agents
coordinate to iteratively build and validate the block diagram
model. Although this approach is promising, it still relies
on the availability of Simulink diagram screenshots as
input, essentially rebuilding an existing model rather than
generating one directly from software requirements. In con-
trast, AutoMAS-SL takes a requirement-centric perspective:
starting solely from textual software requirements, it gen-
erates, tests, refines Simulink models through tool-based
access, without requiring pre-existing diagram artifacts.
Accordingly, AutoMAS-SL differentiates itself from prior
Simulink-oriented generative approaches by combining
requirement-centric model generation, specialized agent
collaboration, and execution-based refinement in a unified
workflow, thereby moving closer to the needs of automotive
V -model development than approaches focused only on
generation, reconstruction, or fine-tuning.

A. AUTOMATED MODEL GENERATION AND REFINEMENT
This workflow transforms a natural-language software
requirement into an executable Simulink model (.slx).
The goal is syntactic correctness and compliance with the
requirement. The workflow is iterative and multi-agent.
It performs code generation, review, and repair. This process
is illustrated in Figure 3.
1) FUNCTION DEVELOPER AGENT
The process begins with the Function Developer Agent,
whose persona is an expert Simulink developer. Its behavior
is governed by a system prompt. The prompt acts as a
‘‘rulebook’’. It enforces best practices and prevents common
errors. The prompt is dynamically assembled.
It includes:
• Structured Requirement Data: The requirement’s ID,
name, description, inputs, outputs, and parameters are
formatted into a clean text block.
• Mandatory Templates: A boilerplate template is
injected to enforce a consistent script structure for model
initialization and saving.
• Domain-Specific Rules: The rulebook contains explicit
instructions distilled from expert knowledge. For
instance, to prevent a common class of runtime errors,
it mandates a specific syntax for parameter assignment:
CRITICAL RULE: Parameter Syntax
Enforcement
ALWAYS use: set_param(block, ‘Param’,
num2str(var))
NEVER use: set_param(block, ‘Param’,
‘var’)
The prompt also prescribes design patterns. For stateful
logic, it requires a Set–Reset latch using a Memory
block. This pattern avoids illegal algebraic loops.
A representative excerpt of the Function Developer Agent
prompt is provided in Appendix.
2) THE AUTONOMOUS REFINEMENT LOOP: COMPLIANCE
AND CORRECTION
The generation workflow follows an autonomous ‘‘generate–
check–refine’’ cycle. The Function Developer Agent first
produces a candidate MA TLAB script. The script then enters
a refinement loop. Two specialized agents orchestrate this
loop:
• Compliance Agent: This agent acts as an automated
peer reviewer, performing static analysis of the gener-
ated script. Its prompt is a technical checklist designed
to verify structural integrity and adherence to the
requirement’s logic and automotive modeling standards.
• Fixer Agent: If the Compliance Agent flags a non-
conformity, or if a subsequent execution attempt fails,
the Fixer Agent is invoked. It receives a dossier with
the original requirement, the faulty code, and the
compliance report. It also receives any runtime error
messages from the MA TLAB Engine. This context
enables targeted repair instead of regeneration from
scratch.
The loop continues until the script passes static compliance
checks. It must also execute successfully in the MA TLAB
Engine. The output is a valid Simulink model (.slx).
B. AUTOMATED VERIFICATION AND VALIDATION
The right-hand branch of the V -Model covers verification
and validation (V&V). Here, the generated model is tested
against its requirements (Figure 4). The workflow follows an
autonomous ‘‘test–debug–refine’’ cycle.
1) AGENT ROLES IN THE V&V WORKFLOW
• Testing Agent creates JSON test bundles (boundary +
temporal coverage).
• MATLAB Test Runner executes tests with clean state
between runs and emits [PASS]/[FAIL] logs.
• Diagnosis Agent classifies failures as MODEL_ERROR
or TEST_CASE_ERROR and produces a minimal
fix_proposal.

3) EXECUTION AND FAILURE DIAGNOSIS
The MA TLAB Test Runner executes the generated JSON
test cases. It uses the MA TLAB Engine API to simulate the
model. It captures console output with standardized PASS
and FAIL messages.
If a test fails, the Diagnosis Agent is activated. Its persona
is an expert V&V root-cause analyst. The Diagnosis Agent
receives an evidence dossier. It includes the requirement,
the model-generating code, the full test results, and the raw
MA TLAB console log. The agent is prompted to follow
a mandatory 4-step reasoning process. The agent produces
a structured Evidence object. It contains a classification
(MODEL_ERROR or TEST_CASE_ERROR) and a confidence
score. It also includes a concise hypothesis and a concrete
fix_proposal.
4) ITERATIVE MODEL CORRECTION
The structured output from the Diagnosis Agent enables the
final step: closing the loop. The framework’s orchestrator
dispatches the ‘Evidence’ object to the appropriate workflow
for correction:
• If classified as TEST_CASE_ERROR, the dossier is sent
back to the Testing Agent to refine the test cases.
• If classified as MODEL_ERROR, the dossier is routed
back to the Automated Model Generation workflow. The
fix_proposal is used to seed the Fixer Agent, which
then patches the model-generating script.
The V&V process iterates until all test cases pass. We also
enforce a maximum of three refinement cycles. This limit
prevents infinite loops. It also avoids cases where agents
change tests only to force a pass. Within this bound, the final
model remains compliant and functionally correct.
IV. EVALUATION
General LLM benchmarks like HumanEval evaluate text-
based code synthesis but cannot assess the construction,
simulation, or time-dependent behaviors of graphical models.
They lack the domain constraints (e.g., block-diagram
semantics, solver settings, timers) needed to determine if
a generated Simulink model is executable and functionally
correct.

C. METRICS
We report three key metrics:
• Absolute Pass Rate (APR): The percentage of the
38 requirements for which the generated model passes
all associated unit checks.
• Relative Pass Rate (RPR): The percentage of the
378 total unit checks that passed across all requirements.
• Models Missing: The number of requirements for which
no executable model could be produced.
D. MODEL CONFIGURATIONS
We compare several configurations to progressively isolate
the impact of our framework’s components:
• GPT-4.1 (RA W Model): Tests the out-of-the-box
capability of the LLM. This configuration uses a single
API call with only the textual requirement and a
minimal prompt, without the agentic framework or
the domain-specific Simulink rulebook. The minimal
prompt used for the RAW baseline is provided in
Appendix.
• GPT-4.1 (Baseline): Isolates the effect of domain
knowledge. It builds on the RAW model by providing
the LLM with our comprehensive Simulink rulebook
but does not use the multi-agent refinement loop for
compliance or error correction.
• GPT-4.1 (Function Dev): Evaluates the automated
build-and-refine process. This setup employs the Func-
tion Developer workflow including the Function Devel-
oper, Compliance, and Fixer agents to iteratively resolve
build errors until a valid model is generated, but does not
perform the final V&V testing.
• GPT-4.1 (AutoMAS-SL): Represents the complete
end-to-end system. It uses the Function Developer
workflow to generate a model and then engages the
entire V&V workflow for automated testing, failure

V. LIMITATIONS, MITIGATIONS, AND FUTURE
EXTENSIONS
A. KEY LIMITATIONS AND MITIGATIONS
1) Ambiguous or Underspecified Requirements.
A major source of errors arises from requirements that
lack sufficient precision. Missing reset or initialization
conditions, undefined threshold behavior, and vague
timing semantics (e.g., unclear whether a condition
must hold for a duration T or for N consecutive
samples) frequently cause incorrect or unstable model
behavior. In our experiments, such underspecification
was one of the most common root causes of failure,
as the LLM often has to infer intent, leading to
inconsistent or unintended interpretations.
Mitigations: To address this, requirement definitions
should follow a structured and unambiguous template.
This includes explicit power-on defaults, clear defini-
tions of thresholds and hysteresis, and precise timing
semantics (‘‘for N consecutive samples’’ vs. ‘‘after
T seconds’’). Incorporating these elements improves
determinism in both model generation and test-case
creation.
Future Framework Extension: As a future extension,
we will integrate a human-in-the-loop clarification step
that enables the framework to detect ambiguity and
query the user before committing to an implementation.
Concretely, the system will (i) automatically flag
missing or unclear elements such as reset/initialization
behavior, threshold inclusivity and hysteresis, and then
(ii) generate targeted clarification questions or explicit
candidate assumptions for user confirmation.
2) Timing Nondeterminism and Misalignment.
Another key limitation arises from timing nondeter-
minism. V ariations in solver configurations, inherited
sample times, and inconsistent unit conventions (e.g.,
mixing seconds and milliseconds) can lead to run-to-
run variance, misaligned signal updates, and off-by-one
timing errors. These issues are particularly problematic
for stateful or timer-based logic, where even subtle
deviations in the execution schedule can cause
incorrect behavior during testing or in closed-loop
operation.
Mitigations: To ensure deterministic execution,
we enforce a discrete, fixed-step solver configuration
and define a single global sample time Ts with con-
sistent unit contracts across all interfaces. Additional
protections include continuous-integration checks
for inherited sample rates, explicit clock-domain
adaptation when necessary, and the use of off-by-one
guard conditions around timer logic. Together, these
measures significantly reduce temporal ambiguity and
improve the reproducibility of model behavior across
refinement iterations.
Future Framework Extension: Specifically, the system
will generate explicit candidate assumptions about

B. HALLUCINATION MITIGATION AND TRANSPARENCY
In the context of this work, hallucination refers to
requirement-inconsistent model content generated by the
LLM, such as invented assumptions, incorrect thresholds
or timing semantics, structurally plausible but behaviorally
wrong Simulink logic, or erroneous test expectations.
Our current framework mitigates this risk through several
complementary mechanisms. First, the Function Developer
Agent and Testing Agent are intentionally decoupled and
both operate directly on the software requirement: the
model is generated from the requirement, while the test
cases are derived independently from the same requirement
rather than from the generated model. This reduces
confirmation bias and enables cross-checking between
implementation and verification. Second, the Compliance
Agent performs rule-based and requirement-oriented review
before execution, which helps detect structurally or logically
suspicious model content. Third, failed executions and
failed test cases trigger the Diagnosis and Fixer agents,
which use the requirement, generated code, compliance
feedback, and MA TLAB execution logs as evidence for
targeted corrections instead of unconstrained regeneration.
Finally, human-in-the-loop review can be enabled at each
iteration to inspect intermediate artifacts before accepting a
refinement step. Nevertheless, hallucinations are not fully
eliminated, especially for ambiguous or underspecified
requirements, where the model may still infer unintended
behavior. Future work will therefore focus on stronger
grounding mechanisms, e.g., retrieval-augmented access to
trusted Simulink/MathWorks documentation or rule checkers
specialized for safety-critical logic.
C. EXTENDABILITY BEYOND SIMULINK
Another important consideration is whether the frame-
work can be transferred beyond Simulink. The overall
AutoMAS-SL workflow is not tied to a single modeling
environment: requirement interpretation, test generation,
diagnosis, and iterative refinement are conceptually reusable.
What is specific to Simulink in the current implementation
is the rulebook and the executable interface used to con-
struct, run, and validate models through MA TLAB/Simulink.
Extending the approach to another environment would
therefore mainly require replacing this tool-specific layer,
including its modeling rules, available component libraries,
and execution hooks. The main engineering effort lies in
adapting these environment-specific interfaces, while the
overall multi-agent coordination logic can remain largely
unchanged.
VI. CONCLUSION
This paper presented a novel multi-agent LLM frame-
work that automates key phases of the automotive
model-based software development lifecycle. By decom-
posing the V -Model into specialized, collaborative agent
tasks, our system moves beyond simple code generation
to create a self-correcting pipeline capable of produc-
ing functionally correct Simulink models from textual
requirements. To validate our approach, we introduced
ASWE-Bench, the first domain-specific benchmark for
evaluating generative AI on graphical automotive control
logic.
Our results demonstrate a substantial improvement over
baseline LLM. The raw minimal-prompt configuration
achieved an absolute pass rate of 15.8%. Adding the
domain-specific Simulink rulebook increased the pass
rate to 47.4%, while the full AutoMAS-SL framework,
including automated verification, diagnosis, and refinement,
reached 73.7%. This underscores the necessity of iterative
refinement and domain-specific knowledge, codified in our
agent ‘‘rulebooks,’’ to bridge the modality gap between
text-native LLMs and graphical programming environments.
The framework automates the creation of models and test
cases for data transformations, combinational logic, and
most stateful timing logic, though complex closed-loop
control remains a challenge, defining the current capability
ceiling.
At the same time, the reliance on a static rulebook consti-
tutes a practical limitation. Automotive software standards,
modeling guidelines, and toolchain conventions evolve, and
static prompts can become stale or incomplete as new
modeling patterns, block behaviors, or best practices emerge.
This is particularly relevant for complex control logic,
where correct implementation often depends on subtle,
context-dependent constraints that are difficult to capture
exhaustively in a fixed prompt. Dynamic knowledge retrieval
can address this gap by enabling the framework to fetch up-
to-date, task-specific guidance at runtime and to ground agent
decisions in authoritative sources.
Future work will therefore explore hybrid extensions that
address the current performance ceiling while improving
adaptability. Specialized, fine-tuned models could act as
‘‘expert’’ agents for complex domains such as control
theory. In addition, replacing the static rulebook with a
Retrieval-Augmented Generation (RAG) component indexed
on authoritative sources (e.g., official MathWorks documen-
tation, internal modeling guidelines, and coding standards)
could improve scalability, reduce prompt staleness, and
support traceable, citation-backed reasoning for difficult
modeling decisions. Ultimately, this work provides a
foundation for building more capable and autonomous
AI-driven software engineering pipelines in safety-critical,
model-based domains.
